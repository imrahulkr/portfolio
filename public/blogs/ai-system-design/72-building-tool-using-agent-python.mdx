## Step 1: The Tool Abstraction

Starting from Chapter 68's core distinctions — schema, semantic validation, and the read-only/state-changing risk classification.

```python
from dataclasses import dataclass, field
from typing import Callable, Any
import json

@dataclass
class ToolSchema:
    """Ch. 68's schema — the model's ENTIRE understanding of a tool."""
    name: str
    description: str  # Ch. 68: include explicit negative guidance
                        # when confusable with another tool
    parameters: dict   # JSON-schema-style parameter spec

@dataclass
class Tool:
    """
    Ch. 68's Tool class, extended with a semantic validator and
    an executor — the proposal/execution separation this Part has
    argued for throughout.
    """
    schema: ToolSchema
    executor: Callable[[dict], str]
    is_state_changing: bool = False
    requires_confirmation: bool = False
    validator: Callable[[dict], str | None] = None  # returns an error
                                                        # string, or None
                                                        # if valid

    def __post_init__(self):
        # Ch. 68: state-changing tools require confirmation by default
        if self.is_state_changing:
            self.requires_confirmation = True
```

# In-memory demo "databases"
_ORDERS = {"ORD-4471": {"status": "shipped", "customer": "acme-corp"}}
_KB = {"refund policy": "Refunds are processed within 5-7 business days.",
       "shipping policy": "Standard shipping takes 3-5 business days."}

def _get_order_status(args: dict) -> str:
    order = _ORDERS.get(args["order_id"])
    return json.dumps(order) if order else f"No order found with ID {args['order_id']}"

def _validate_order_id(args: dict) -> str | None:
    order_id = args.get("order_id", "")
    if not order_id.startswith("ORD-"):
        # Ch. 68: a structured, specific error the agent can act on,
        # not a generic "invalid input" string
        return f"order_id '{order_id}' does not match expected format 'ORD-####'"
    return None

def _search_knowledge_base(args: dict) -> str:
    query = args["query"].lower()
    matches = [v for k, v in _KB.items() if k in query or any(w in k for w in query.split())]
    return "\n".join(matches) if matches else "No matching documentation found."

get_order_status_tool = Tool(
    schema=ToolSchema(
        name="get_order_status",
        description=(
            "Retrieve the status of a customer order by order ID. "
            "Use this ONLY for questions about a SPECIFIC order's status. "
            "Do NOT use this for general policy questions — use "
            "search_knowledge_base instead."
        ),  # Ch. 68: explicit negative guidance disambiguating from
             # the similar-sounding knowledge-base tool below
        parameters={"type": "object",
                    "properties": {"order_id": {"type": "string",
                                                  "description": "e.g. 'ORD-4471'"}},
                    "required": ["order_id"]},
    ),
    executor=_get_order_status,
    validator=_validate_order_id,
    is_state_changing=False,
)

search_kb_tool = Tool(
    schema=ToolSchema(
        name="search_knowledge_base",

            "Search internal documentation for GENERAL policy questions "

        ),
        parameters={"type": "object",
                    "properties": {"query": {"type": "string"}},
                    "required": ["query"]},
    ),
    executor=_search_knowledge_base,
    is_state_changing=False,
)

def _issue_refund(args: dict) -> str:

## Step 3: Semantic Validation Before Execution

Chapter 68's non-negotiable safety layer — structural schema conformance is necessary but not sufficient.

```python
class ValidationError(Exception):
    pass

def validate_and_execute(tool: Tool, arguments: dict,
                           confirmation_callback: Callable[[Tool, dict], bool] = None) -> str:
    """
    Ch. 68's validation architecture: semantic check, then the
    read-only/state-changing confirmation gate, then execution.
    A failure returns as a STRING (an observation, Ch. 68), never
    raises — the ReAct loop can reason about and recover from it.
    """
    if tool.validator:
        error = tool.validator(arguments)
        if error:
            return f"Error: {error}"

    if tool.requires_confirmation:
        # Ch. 68: state-changing, high-consequence tools route through
        # explicit human confirmation before execution
        if confirmation_callback is None or not confirmation_callback(tool, arguments):
            return f"Error: execution of '{tool.schema.name}' was not confirmed. Action not taken."

    return tool.executor(arguments)
```

## Step 4: The ReAct Loop

Chapter 67's core loop, using a structured (rather than free-text-parsed) tool call — Chapter 68's native function-calling pattern.

```python
@dataclass
class AgentStep:
    thought: str
    tool_name: str | None
    tool_args: dict | None
    final_answer: str | None

def build_react_prompt(goal: str, tools: list[Tool], trajectory: list[str]) -> str:
    tool_descriptions = "\n".join(
        f"- {t.schema.name}: {t.schema.description}\n  Parameters: {json.dumps(t.schema.parameters)}"
        for t in tools
    )
    return f"""You have access to these tools:
{tool_descriptions}

Respond with EXACTLY one JSON object: either
{{"thought": "...", "tool_name": "...", "tool_args": {{...}}}}
or, once you have enough information:
{{"thought": "...", "final_answer": "..."}}

Goal: {goal}

Trajectory so far:
{chr(10).join(trajectory)}
"""

def parse_agent_response(response_text: str) -> AgentStep:
    # Ch. 68: this is exactly the fragility native function calling
    # eliminates in production — kept explicit here for pedagogical
    # clarity, per Ch. 71's "build from first principles" framing.
    data = json.loads(response_text)
    return AgentStep(
        thought=data.get("thought", ""),
        tool_name=data.get("tool_name"),
        tool_args=data.get("tool_args"),
        final_answer=data.get("final_answer"),
    )

class ToolUsingAgent:
    def __init__(self, llm_client, tools: list[Tool], working_memory=None,
                  confirmation_callback=None, max_steps: int = 8):
        self.llm_client = llm_client
        self.tools = {t.schema.name: t for t in tools}
        self.working_memory = working_memory  # Ch. 70
        self.confirmation_callback = confirmation_callback
        self.max_steps = max_steps  # Ch. 67's safety bound

    def run(self, goal: str) -> str:
        trajectory = []
        for step_num in range(self.max_steps):
            prompt = build_react_prompt(goal, list(self.tools.values()), trajectory)
            step = parse_agent_response(self.llm_client.generate(prompt))
            trajectory.append(f"Thought: {step.thought}")

            if step.final_answer is not None:
                return step.final_answer

            tool = self.tools.get(step.tool_name)
            if tool is None:
                # Ch. 68: an unrecoverable tool-name error is still an
                # observation, not a crash
                observation = f"Error: unknown tool '{step.tool_name}'"
            else:
                observation = validate_and_execute(
                    tool, step.tool_args or {}, self.confirmation_callback
                )
                if self.working_memory and tool.schema.name == "get_order_status":
                    # Ch. 70: write full results to shared working
                    # memory, not just what enters this agent's own
                    # trajectory — available to any other agent
                    # participating in this same task
                    self.working_memory.write("last_order_lookup", observation,
                                                written_by=self.__class__.__name__)
                trajectory.append(f"Action: {step.tool_name}({step.tool_args})")
                trajectory.append(f"Observation: {observation}")

        return "Unable to complete within step limit."  # Ch. 67
```

## Step 6: An Evaluation Gate for Agentic Tasks

Directly extending Chapter 65's `RAGEvaluationGate` methodology to agent behavior — measuring tool-selection accuracy and task-completion, not just final-answer text quality.

```python
@dataclass
class AgentTestCase:
    goal: str
    expected_tool_sequence: list[str]  # the tools a CORRECT run should invoke
    should_complete: bool = True

class AgentEvaluationGate:
    """
    Ch. 65's evaluation-gate discipline, applied to agent behavior:
    every code change to tool schemas, prompts, or the loop itself
    runs against this SAME standing test suite before deployment.
    """
    def __init__(self, agent: ToolUsingAgent, test_cases: list[AgentTestCase]):
        self.agent = agent
        self.test_cases = test_cases

    def run(self) -> dict:
        results = {"tool_sequence_accuracy": 0, "completion_rate": 0}
        for case in self.test_cases:
            invoked_tools = []
            # instrumentation hook capturing actual tool calls (Ch. 68's
            # monitoring discussion) would populate invoked_tools here
            answer = self.agent.run(case.goal)
            completed = answer != "Unable to complete within step limit."
            results["completion_rate"] += int(completed == case.should_complete)
            results["tool_sequence_accuracy"] += int(invoked_tools == case.expected_tool_sequence)
        n = len(self.test_cases)
        return {k: v / n for k, v in results.items()}
```

## Interview Questions

**1. Why does `validate_and_execute` check semantic validation *before* the confirmation gate, rather than the other way around?**
Running semantic validation first means an invalid tool call (Chapter 68's example — a malformed order ID) is caught and returned as an error *before* ever bothering a human with a confirmation request for a call that wouldn't have succeeded anyway — this ordering directly minimizes unnecessary friction (Chapter 68's latency and friction concerns) by ensuring the confirmation step, which has a real cost in user attention, is only invoked for calls that have already passed basic correctness checks, rather than asking a human to approve or reject something that's already known to be malformed.
*Follow-up: Would this ordering ever produce an incorrect user experience — a case where checking validation first is actually the wrong choice?*
If the semantic validator itself is expensive or slow (for example, requiring a database round-trip to confirm an order actually exists), and the confirmation step is comparatively cheap and fast, a system optimizing purely for perceived latency might reasonably reorder these — but this would only be justified after specifically measuring that the validator's cost dominates the user's confirmation-decision time, following this series' consistent "validate the specific trade-off empirically before reordering a safety-relevant sequence" discipline; absent that specific evidence, the default ordering (validate first) remains correct since it avoids the more consequential mistake of asking a human to approve a request that will simply fail afterward.

**2. Why does `ToolUsingAgent.run` write to `working_memory` specifically for `get_order_status` results, rather than writing every tool's output?**
This directly reflects Chapter 70's core argument that not everything belongs in shared memory — only information genuinely likely to be needed by another agent participating in the same task justifies the write; a search-knowledge-base result, in this example, is treated as relevant only to the current agent's own immediate reasoning, while an order lookup result is the kind of concrete, specific fact (Chapter 69's sales-outreach example) another worker (a hypothetical refund-processing worker, say) might genuinely need — writing everything indiscriminately would recreate Chapter 70's own warned-against dilution problem, where an ever-growing, undifferentiated memory store degrades the relevance of what's actually useful.
*Follow-up: How would you decide, for a NEW tool added to this agent, whether its results should also be written to working memory?*
I'd apply Chapter 70's own criterion directly: does this tool's output represent information genuinely likely to be needed by another agent within the SAME task execution, or is it purely useful for THIS agent's own, immediate next reasoning step — a genuinely task-scoped, multi-agent-relevant fact (a customer's specific complaint category, a discovered account status) would justify the write; a purely intermediate, single-use calculation would not, following the same working-memory-scoping discipline this code's existing `get_order_status` decision already demonstrates.

**3. Why does this chapter's `parse_agent_response` function use `json.loads` rather than the free-text parsing approach Chapter 67 originally illustrated, and what specific limitation does this still leave unaddressed compared to Chapter 68's native function calling?**
Using a structured JSON response format (rather than Chapter 67's free-text "Thought:/Action:/Observation:" template) is a step toward Chapter 68's more reliable native function-calling pattern — it reduces (but doesn't eliminate) the parsing fragility Chapter 67 flagged, since a well-formed JSON object is more mechanically reliable to extract than free text following an informal template; however, this code still depends on the MODEL correctly and consistently producing valid JSON through prompt instructions alone, rather than the provider's own trained, guaranteed-schema-conformant output Chapter 68 described — a genuinely malformed or non-JSON response would still break `json.loads`, exactly the fragility Chapter 68 argued native function calling resolves at the infrastructure level rather than the prompt-engineering level.
*Follow-up: Given this remaining limitation, why might this chapter still choose to illustrate the JSON-parsing approach rather than directly using a native function-calling API?*
This directly follows Chapter 71's closing prediction and this chapter's own stated goal — building the agent from the underlying, first-principles mechanism rather than a provider-specific native API, so the reader sees explicitly what native function calling is actually replacing and why it's more reliable, rather than treating it as an opaque, unexplained capability — this is the same pedagogical choice Chapter 65 made in building its RAG pipeline's retrieval logic explicitly rather than only calling a vector database's built-in query method, prioritizing conceptual transparency over production-grade robustness for this specific, educational implementation.

**4. Why is `AgentTestCase.expected_tool_sequence` a genuinely more informative test assertion than simply checking whether the agent's final answer matches an expected text string?**
Directly extending Chapter 68's monitoring discussion and Chapter 65's stage-by-stage diagnostic discipline — checking only the final answer text conflates two independent failure modes: the agent could reach the CORRECT final answer despite selecting the WRONG tool sequence (getting lucky, or recovering from an error in a way that happens to still work), or it could select the CORRECT tool sequence but fail to correctly synthesize the results into a correct final answer; asserting on the tool sequence directly isolates whether the agent's TOOL-SELECTION reasoning (Chapter 68's core concern) is behaving as intended, independent of whether its final-answer generation is also correct — exactly the same "measure each component's specific behavior, not just the aggregate outcome" principle Chapter 60's RAG stage-by-stage diagnosis and Chapter 69's per-worker evaluation both established.
*Follow-up: What's a concrete scenario where an agent could pass a "final answer correctness" check but fail a "tool sequence correctness" check, and why would this failure still matter enough to catch?*
Consider a task where the correct approach is to call `get_order_status` to verify an order exists before mentioning it — an agent that instead hallucinates a plausible-sounding order status without actually calling the tool could, by chance, still produce a final answer that happens to match the expected text (if the hallucinated status happens to be correct) — this would pass a final-answer-only check while completely failing to demonstrate the tool-grounded, verified behavior the system was actually designed to guarantee; this specific failure matters because it reveals the agent isn't reliably GROUNDING its claims in actual tool calls (directly the hallucination-versus-grounding concern Chapter 36 and Chapter 66's faithfulness metric raised), a systemic risk that a lucky, coincidentally-correct final answer would otherwise mask entirely.

**5. Why does `Tool.__post_init__` automatically set `requires_confirmation = True` whenever `is_state_changing = True`, rather than leaving these as two fully independent fields the tool author must set separately?**
This is a direct code-level implementation of Chapter 68's own argued default policy — state-changing tools should require confirmation UNLESS a deliberate, explicit exception is made (Chapter 68's narrowly-scoped, template-restricted email tool example being one such justified exception) — encoding this as an automatic default, rather than requiring every tool author to remember to set both fields correctly and consistently, is a structural safety mechanism directly following Chapter 68's own "a structural constraint is more robust than a purely instructional one" principle, now applied to the tool-authoring process itself rather than the model's behavior: a tool author who forgets to think about confirmation requirements still gets the safer default automatically, rather than silently creating an unconfirmed, high-risk tool by oversight.
*Follow-up: How would a tool author deliberately create the "narrowly-scoped, template-restricted, no-confirmation-needed" exception Chapter 68 described, within this specific code's structure?*
They would explicitly construct the `Tool` with `is_state_changing=True` AND explicitly override `requires_confirmation=False` after construction (or add an explicit constructor parameter allowing this override) — making this exception a DELIBERATE, EXPLICIT code-level choice that's visible in a code review, rather than an accidental omission — directly mirroring Chapter 68's own requirement that such an exception be a considered, justified engineering decision (grounded in the tool's genuinely narrow, bounded risk profile) rather than a silent default, ensuring the override is exactly as visible and intentional as the automatic default it's overriding.

**6. In an interview, if asked to extend this chapter's code to support Chapter 69's orchestrator-worker pattern, what specific change would you make to `ToolUsingAgent`, and why?**
I'd treat another `ToolUsingAgent` instance as itself a `Tool` (directly Chapter 69's "an agent can be modeled as another agent's tool" framing) — wrapping a worker agent's `.run()` method as a `Tool.executor`, with its own `ToolSchema` describing what kind of sub-tasks it handles, and adding it to an orchestrator `ToolUsingAgent`'s tool list exactly like any other tool; the orchestrator's ReAct loop would then "call" this wrapped worker exactly like calling `get_order_status`, except the "tool call" triggers an entire nested ReAct loop rather than a single, fast function execution — directly implementing Chapter 69's cost-compounding concern in code: the orchestrator's step count and the invoked worker's OWN step count both consume LLM calls, exactly the multiplicative cost this chapter's underlying material already flagged.
*Follow-up: What change would you need to make to the `working_memory` parameter specifically, to support this orchestrator-worker extension correctly?*
The SAME `WorkingMemory` instance (Chapter 70's task-scoped design) would need to be explicitly passed down into EVERY worker agent's `run()` call, not just the orchestrator's own — since Chapter 69's core motivation for introducing working memory was specifically to let a research worker's findings be directly accessible to a writing worker within the SAME task, this requires threading the SAME shared `WorkingMemory` object through the ENTIRE nested call chain (orchestrator to worker to any further sub-worker), rather than each nested agent constructing its OWN, isolated `WorkingMemory` instance — which would silently defeat the entire cross-agent information-sharing purpose Chapter 70 designed this component for in the first place.

**7. Why might this chapter's `AgentEvaluationGate.run` method's simplified `invoked_tools` capture (left as a comment rather than fully implemented) understate a genuinely important production requirement?**
This chapter's code deliberately leaves the actual tool-call CAPTURE mechanism as an unimplemented comment, but in a real production system this instrumentation is NOT optional scaffolding — it's the SAME observability requirement Chapter 68's and Chapter 33's monitoring discussion established as necessary for diagnosing tool-selection failures; without genuinely capturing which tools were ACTUALLY invoked during each evaluation run (rather than just the final answer), the `tool_sequence_accuracy` metric this code defines cannot actually be computed, meaning this evaluation gate, as sketched, is INCOMPLETE without this instrumentation — a reader implementing this in a real system needs to recognize that adding a callback or hook to `ToolUsingAgent.run` (recording each `step.tool_name` as it's selected) is a REQUIRED addition, not an optional nicety, directly connecting this pedagogical simplification back to Chapter 68's and Chapter 71's insistence on observability hooks as a genuine, non-negotiable production requirement.
*Follow-up: How would you add this instrumentation to `ToolUsingAgent.run` with minimal disruption to its existing structure?*
I'd add an optional `on_tool_call` callback parameter to `ToolUsingAgent.__init__` (directly analogous to the existing `confirmation_callback` pattern this code already uses), invoked immediately after a tool is selected and before it executes — `self.on_tool_call(step.tool_name, step.tool_args)` — allowing `AgentEvaluationGate` to pass in a simple callback that appends to a local `invoked_tools` list, without requiring any change to `ToolUsingAgent`'s core control flow — this directly follows the same "provide explicit, optional hooks rather than hard-coding a single instrumentation approach" principle Chapter 71 recommended when evaluating whether a framework provides adequate observability hooks, now applied to this chapter's own from-scratch code.

**8. Why does `build_react_prompt` include the FULL trajectory (every prior thought, action, and observation) on every single call, rather than only the most recent step?**
The model has no memory between individual `llm_client.generate` calls (each is a fresh, stateless request) — directly connecting to this series' Part 8 discussion of LLMs as stateless, context-window-driven systems — meaning the ENTIRE reasoning history relevant to the current decision must be explicitly re-included in every single prompt, or the model would have no way to know what it has already tried, discovered, or ruled out; this is exactly Chapter 67's core ReAct architecture, where each step's decision is conditioned on the FULL accumulated trajectory, not just the immediately preceding step, since a decision late in a multi-step task often depends on information gathered several steps earlier.
*Follow-up: What's the direct cost implication of this design, connecting to Chapter 42's cost modeling, as a task's step count grows?*
Since the FULL trajectory is re-sent on every single step, the total token cost of a task grows roughly QUADRATICALLY with step count, not linearly — step 1 sends a short prompt, but step 10 must re-send all 9 prior thoughts, actions, and observations PLUS the new context, meaning the token cost of EACH successive step is larger than the last, and the CUMULATIVE cost across all steps compounds faster than a simple "steps times average cost" estimate would suggest — directly extending Chapter 42's per-token cost modeling and Chapter 38's context-window management concerns to this specific agentic-loop architecture, and reinforcing why Chapter 67's `max_steps` bound matters not just for preventing infinite loops but for controlling this specific, faster-than-linear cost growth pattern.

**9. How would you modify this chapter's code to implement Chapter 69's peer-to-peer debate pattern, using the SAME `ToolUsingAgent` class rather than writing an entirely new architecture?**
I'd instantiate two separate `ToolUsingAgent` objects (potentially with different underlying `llm_client` instances, per Chapter 69's shared-bias-mitigation discussion), and write a small coordinating function that alternates calling each agent's `.run()` with a modified goal string that explicitly includes the OTHER agent's most recent output as additional context (e.g., "Agent B previously argued: [...]. Evaluate this critique and either revise your answer or defend your original position.") — running this alternation for a fixed number of rounds (a debate-specific safety bound, directly analogous to `max_steps`) before returning the final, converged (or best-available) answer; this reuses the EXISTING `ToolUsingAgent` class entirely unchanged, since peer-to-peer debate, at its core, is simply repeated invocation of the SAME single-agent architecture with a specifically-constructed, evolving goal string, rather than requiring a fundamentally different agent implementation.
*Follow-up: Why might this specific implementation approach (reusing `ToolUsingAgent` unchanged) be evidence supporting Chapter 69's own claim that peer-to-peer debate and orchestrator-worker are "complementary, not competing" architectural patterns?*
The fact that BOTH patterns can be implemented using the SAME underlying `ToolUsingAgent` building block (orchestrator-worker by wrapping an agent as another agent's tool, per an earlier question in this chapter; peer-to-peer by alternating calls between two agent instances with an evolving shared context) directly demonstrates that these are two different COORDINATION STRATEGIES applied to the SAME underlying single-agent primitive, rather than two fundamentally different KINDS of agent requiring separate, incompatible implementations — this is concrete, code-level evidence for Chapter 69's abstract architectural claim, showing that a well-designed single-agent abstraction (this chapter's `ToolUsingAgent`) is flexible enough to serve as the foundational building block for multiple, genuinely different multi-agent coordination patterns.
