## How to Use This Chapter

Each question describes a scenario. Name the pattern, then check the answer's one-line
justification against your own reasoning — the justification matters more than getting the name
right, per this series' running theme (Chapter 15).

---

**1. "I need exactly one instance of a configuration manager shared across the whole
application."**
Singleton (Ch. 16) — though in a real app, prefer a DI-framework-managed singleton bean over a
manual `getInstance()`.

**2. "I need to construct different vehicle subtypes based on a string input at runtime."**
Factory Method (Ch. 17) — defers which concrete class to instantiate.

**3. "Selecting a vehicle type should also determine a consistent ticket format and fee
strategy."**
Abstract Factory (Ch. 18) — a family of related products created together, guaranteed consistent.

**4. "This object has 8 optional fields and only 2 required ones."**
Builder (Ch. 19) — avoids telescoping constructors; put required fields in the Builder's own
constructor.

**5. "Constructing this object involves an expensive network call, and I need 50 nearly-identical
copies."**
Prototype (Ch. 20) — clone a pre-built instance; watch for shallow vs. deep copy on mutable
fields.

**6. "I need to integrate a third-party SDK whose method names don't match my own interface."**
Adapter (Ch. 21) — bridges a genuine interface incompatibility; prefer object adapters
(composition) in Java.

**7. "Remote control tiers (Basic/Advanced) and device types (TV/Radio) both vary
independently."**
Bridge (Ch. 22) — decouples two independent hierarchies to avoid combinatorial explosion.

**8. "I need to treat a single file and an entire folder of files uniformly."**
Composite (Ch. 23) — leaves and composites share one interface, enabling recursive uniform
treatment.

**9. "I want to add optional toppings to a coffee, in any combination, without a class per
combination."**
Decorator (Ch. 24) — same interface as the wrapped object, stackable, adds behavior.

**10. "Placing an order requires coordinating inventory, payment, shipping, and notifications in
sequence."**
Facade (Ch. 25) — one simplified entry point over a multi-class subsystem.

**11. "I have a million small, mostly-identical objects and memory usage is a real concern."**
Flyweight (Ch. 26) — share intrinsic (common) state; keep extrinsic (unique) state per object.

**12. "I want to defer loading an expensive image until it's actually displayed."**
Proxy, specifically virtual proxy (Ch. 27) — controls access, deferring expensive work.

**13. "I want to enforce access control before allowing an operation on a document."**
Proxy, specifically protection proxy (Ch. 27).

**14. "Customers can pay by credit card or UPI — one way, chosen once per checkout."**
Strategy (Ch. 28) — one interchangeable algorithm, selected once, mutually unaware
implementations.

**15. "Multiple parts of the system need to react when a stock price changes, and I don't know how
many listeners there will be."**
Observer (Ch. 29) — one-to-many, asymmetric broadcast, no return value expected.

**16. "I need undo/redo for user actions in a remote-control-style app."**
Command (Ch. 30) — turns a request into an object; pairs with Memento when there's no clean
inverse.

**17. "An order's legal actions change automatically as it moves from Pending to Shipped to
Delivered."**
State (Ch. 31) — the object itself drives transitions; implementations reference each other.

**18. "Several report formats share the same overall generation steps but differ in formatting
logic."**
Template Method (Ch. 32) — fixed algorithm skeleton in a base class, subclasses override specific
steps.

**19. "An expense needs approval from whichever tier (Manager/Director/VP) is appropriate for its
amount."**
Chain of Responsibility (Ch. 33) — passes along a chain until a handler accepts it.

**20. "I need to traverse a custom collection without exposing its internal array/list/tree
structure."**
Iterator (Ch. 34) — sequential access without exposing representation; watch for fail-fast
`ConcurrentModificationException`.

**21. "A chat room has many users who all need to send messages to each other without holding
direct references."**
Mediator (Ch. 35) — centralizes symmetric peer-to-peer communication, O(n²) coupling collapses to
O(n).

**22. "I need to snapshot a text editor's state for undo, without exposing its internal
content field publicly."**
Memento (Ch. 36) — Originator creates/reads its own opaque snapshot; Caretaker stores it without
seeing inside.

**23. "I keep needing to add new operations (export, compress, scan) to a stable set of file-
system node types."**
Visitor (Ch. 37) — trades cheap-new-element-types for cheap-new-operations; uses double dispatch.

**24. "I need to evaluate simple boolean rule expressions like 'age > 18 AND hasLicense'."**
Interpreter (Ch. 38) — Composite applied to a grammar; fine for small, fixed grammars, but reach
for a real parser for anything more complex.

**25. "Producers generate work faster than consumers can process it, and I need backpressure."**
Producer-Consumer with a bounded `BlockingQueue` (Ch. 39).

**26. "Database connections are expensive, and I want to reuse a fixed pool of them across
requests."**
Object Pool (Ch. 39) — exclusive borrow/release, unlike Flyweight's simultaneous sharing.

**27. "This map is read far more often than it's written, and I want concurrent reads."**
`ReentrantReadWriteLock` (Ch. 40) — multiple concurrent readers, exclusive writer.

**28. "I need to 'find an available spot and reserve it' as one indivisible operation across
concurrent threads."**
Atomic check-then-act, protected by a single write lock covering the whole operation (Ch. 40, 45)
— not two separate locked calls.

**29. Distinguish, in one line each, Strategy vs. State vs. Command.**
Strategy: one algorithm, selected once, computes a result. State: behavior changes automatically
over an object's lifecycle, implementations reference each other. Command: a request becomes a
storable, undoable object.

**30. Distinguish, in one line each, Adapter vs. Decorator vs. Proxy.**
Adapter: different interface, bridges incompatibility. Decorator: same interface, adds behavior,
always fully delegates. Proxy: same interface, controls or gates access, may not fully delegate.

**31. Distinguish, in one line each, Facade vs. Mediator vs. Observer.**
Facade: external caller into an unaware subsystem, one-directional. Mediator: symmetric peers
that know about and route through the coordinator. Observer: asymmetric, one broadcasts, many
listen with no return value.

**32. "I need surge pricing that multiplies whatever base fare calculation is currently active."**
Decorator (Ch. 24, 53) — an adjustment layered on top of a base Strategy, not a separate Strategy
implementation itself.

**33. What's the one universal question to ask before applying any pattern?**
"What specific problem does this pattern solve, and does my current problem actually exhibit that
shape?" — recognize the shape in the requirements first; never start with a pattern name and
search for somewhere to apply it (Ch. 15, 43).
