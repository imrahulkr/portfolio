## How to Use This Chapter

This is not a teaching chapter — it assumes you've worked through Parts 1 and 2 already. Use this
for final review in the days before an interview: read through the questions, answer them
yourself first, then check against the answer. Where a question connects to a specific earlier
chapter, that's noted so you can go back for the full depth if a gap surfaces.

---

**1. What's the difference between encapsulation and abstraction?**
Encapsulation protects an object's internal state (private fields, controlled mutation).
Abstraction lets callers depend on behavior without knowing implementation details. (Ch. 2)

**2. When do you choose an interface over an abstract class?**
Interface when there's no shared implementation, just a shared contract. Abstract class when
subtypes share real state or method bodies. (Ch. 3)

**3. State the Liskov Substitution Principle in one sentence.**
A subtype must be fully substitutable for its base type in every context, without breaking
correctness — not just compiling. (Ch. 9)

**4. Why does the classic Rectangle/Square inheritance example violate LSP?**
`Square`'s overridden setters break `Rectangle`'s invariant that width and height are
independently settable — code written against `Rectangle` gets wrong results when handed a
`Square`. (Ch. 9)

**5. What's the difference between aggregation and composition?**
Aggregation: weak ownership, the part can outlive the whole. Composition: strong ownership, the
part's lifecycle is bound to the whole. (Ch. 4)

**6. Define coupling and cohesion, and state which direction is good for each.**
Coupling: how entangled classes are — aim low. Cohesion: how focused a single class's
responsibility is — aim high. (Ch. 5)

**7. What's the Single Responsibility Principle, precisely?**
A class should have one reason to change — one axis of change, not literally one method. (Ch. 7)

**8. What's the classic violation pattern for the Open/Closed Principle?**
An `if/else` or `switch` chain over a type, requiring modification every time a new case is
added. (Ch. 8)

**9. What does "programming to an interface, not an implementation" actually mean?**
Depending on an abstraction (interface or abstract class) rather than a concrete class, so
callers don't need to change when the concrete implementation changes. (Ch. 3, 11)

**10. State the Interface Segregation Principle.**
No client should be forced to depend on methods it doesn't use — split fat interfaces into
focused ones. (Ch. 10)

**11. What's the difference between the Dependency Inversion Principle and Dependency Injection?**
DIP is a design principle: depend on abstractions, not concretions. DI is a technique: supply a
dependency from outside rather than constructing it internally. You can do DI while still
violating DIP. (Ch. 11)

**12. What does YAGNI stand for and what does it guard against?**
"You Aren't Gonna Need It" — guards against building speculative functionality for requirements
that haven't actually been asked for. (Ch. 12)

**13. State the Law of Demeter informally.**
Only call methods on objects you directly hold a reference to — don't chain through the internal
structure of objects you don't own (`a.getB().getC().getD()`). (Ch. 13)

**14. Why is "favor composition over inheritance" the default guidance in modern OOP design?**
Composition avoids LSP risk (no substitutability promise made), avoids combinatorial subclass
explosion across independent dimensions, and keeps behavior swappable at runtime. (Ch. 13)

**15. What's a "God class," and which principle does it violate most directly?**
A class accumulating many unrelated responsibilities — the most direct, cumulative violation of
SRP. (Ch. 2, 7)

**16. Give the one-sentence test for whether a class violates SRP.**
Can you describe its job in one sentence without using the word "and"? (Ch. 5, 7)

**17. What's the difference between method overloading and method overriding?**
Overloading: same name, different parameters, resolved at compile time (static polymorphism).
Overriding: subclass redefines a parent method, resolved at runtime (dynamic polymorphism). (Ch.
2)

**18. Why does a fat interface often cause an LSP violation too, not just an ISP violation?**
Implementers who can't honestly support every method either throw exceptions or provide
meaningless no-ops — both are LSP violations. Fixing the interface's shape (ISP) fixes both at
once. (Ch. 10)

**19. What's the "Hollywood Principle"?**
"Don't call us, we'll call you" — a higher-level component calls into lower-level, pluggable
code, rather than the reverse. Most directly associated with Template Method. (Ch. 32)

**20. Why is `Stack extends Vector` in the JDK considered a design flaw?**
It breaks the stack abstraction's discipline by inheriting all of `Vector`'s general list
methods, allowing callers to bypass push/pop-only access — a real-world composition-over-
inheritance cautionary tale. (Ch. 13)

**21. What's the difference between a checked and unchecked exception, and which one is relevant
to LSP?**
Checked exceptions must be declared/handled; Java's compiler prevents an override from adding new
checked exceptions beyond the parent's contract — directly enforcing one LSP rule at the language
level. Unchecked exceptions face no such compiler enforcement, which is why patterns like
`UnsupportedOperationException` remain a real LSP risk. (Ch. 9)

**22. When is a Java `record` preferable to a full class with a Builder?**
When every field is required, the count is small, and there's no meaningful optionality — records
are more concise for that specific shape. (Ch. 19)

**23. What's the difference between "association," in the strict UML sense, and "dependency"?**
Association implies a structural, often longer-lived reference (a field). A dependency can be as
brief as a single method parameter with no stored reference at all. Both are looser than
aggregation or composition. (Ch. 4, 6)

**24. Why does over-applying DRY sometimes create an SRP violation?**
Merging two pieces of code that look identical today but represent independent business
concerns creates one class with two unrelated reasons to change — coincidental similarity isn't
genuine duplicated knowledge. (Ch. 12)

**25. What's the "rule of three" for deciding when to eliminate duplication?**
Tolerate duplication the first and second time it appears; seriously consider extracting shared
logic once a third genuinely-identical instance shows up. (Ch. 12)

**26. What does "tell, don't ask" mean, and how does it relate to the Law of Demeter?**
Tell an object what to do (call a method that does the work internally) rather than asking for
its internal data and acting on it yourself externally — the practical technique for satisfying
the Law of Demeter. (Ch. 13)

**27. Why is a private constructor combined with a static factory method not automatically a
GoF Factory Method pattern?**
The GoF pattern specifically involves polymorphism — multiple implementations, with the decision
of which to construct deferred to a swappable creator. A single static method with no
polymorphic variation is just a naming/construction convenience. (Ch. 17)

**28. What specific compiler-enforced rule makes covariant return types always LSP-safe?**
A narrower (more specific) return type on an override always satisfies callers expecting the
parent's broader return type — Java permits narrowing but never widening return types on an
override. (Ch. 9)

**29. What's the key difference between "afferent" and "efferent" coupling?**
Afferent (incoming): how many classes depend on this one. Efferent (outgoing): how many classes
this one depends on. High afferent coupling on a stable abstraction is fine; high efferent
coupling anywhere is usually a smell. (Ch. 5)

**30. Summarize, in one sentence, the single biggest lesson from Part 2 as a whole.**
SOLID principles aren't independent rules to memorize in isolation — they reinforce each other
(fixing SRP often simplifies applying OCP and DIP), and KISS/YAGNI exist specifically to prevent
SOLID-driven reasoning from becoming unjustified over-engineering. (Ch. 14)
