## Why These Three Belong Together

SOLID tells you how to structure classes well. DRY, KISS, and YAGNI act as a **counterweight** —
they stop SOLID-driven thinking from spiraling into unnecessary complexity. Nearly every "how would
you avoid over-engineering this?" follow-up question in an LLD interview is really asking whether
you know these three guidelines.

## DRY — Don't Repeat Yourself

> **Every piece of knowledge must have a single, unambiguous, authoritative representation within
> a system.**

DRY is about duplicated *knowledge* (business rules, logic), not merely duplicated *text*. Two
methods that happen to look similar but represent genuinely different business rules are not a DRY
violation, even if the code looks alike.

**Violation:**
```java
class OrderValidator {
    boolean isValidDiscount(double discount) {
        return discount >= 0 && discount <= 100;
    }
}

class PromotionValidator {
    boolean isValidPercentage(double percentage) {
        return percentage >= 0 && percentage <= 100;
    }
}
```

Both methods encode the exact same rule — "a percentage must be between 0 and 100" — under two
different names, in two different classes. If that rule ever changes (say, discounts can now
exceed 100% for special promotions but percentages can't), you have to remember to find and update
both, and it's easy to update one and forget the other.

**Fix:**
```java
class PercentageValidator {
    static boolean isValidPercentage(double value) {
        return value >= 0 && value <= 100;
    }
}
```

Now there's exactly one authoritative definition of "valid percentage," referenced from both
places that need it.

**The trap: not every similar-looking block of code is a DRY violation.** If `OrderValidator` and
`PromotionValidator` happen to have identical-looking logic today purely by coincidence, but
represent genuinely independent business rules that could diverge in the future for unrelated
reasons, merging them prematurely creates false coupling — a change to one rule could then
accidentally affect the other. **DRY is about duplicated *knowledge*, not duplicated *characters*.**

## KISS — Keep It Simple, Stupid

> **Most systems work best if they are kept simple rather than made complex; simplicity should be
> a key goal in design, and unnecessary complexity should be avoided.**

KISS is the direct antidote to using a design pattern (or three) where a plain method would do.

**Over-engineered:**
```java
interface GreetingStrategy {
    String greet(String name);
}

class EnglishGreetingStrategy implements GreetingStrategy {
    public String greet(String name) { return "Hello, " + name; }
}

class GreetingContext {
    private GreetingStrategy strategy;
    GreetingContext(GreetingStrategy strategy) { this.strategy = strategy; }
    String executeGreeting(String name) { return strategy.greet(name); }
}
```

If there's genuinely only ever going to be one greeting format, with no signal of needing multiple
languages or styles, this is the Strategy pattern applied to a problem that didn't ask for it.

**Simple:**
```java
class Greeter {
    String greet(String name) { return "Hello, " + name; }
}
```

**The KISS test:** could a competent developer unfamiliar with this specific code understand what
it does and why, in under a minute? If a design pattern's indirection makes that harder rather than
easier for a problem this small, it's the wrong tool.

## YAGNI — You Aren't Gonna Need It

> **Don't add functionality until it's actually needed.**

YAGNI is the guideline most directly responsible for the "don't build extensibility for axes of
change the problem doesn't signal" advice repeated throughout Chapters 3, 8, and 11.

**Violation:**
```java
class ParkingLot {
    // "just in case we need multiple currencies someday"
    private Map<String, ExchangeRateProvider> currencyConverters;

    // "just in case we support subscription-based parking someday"
    private SubscriptionManager subscriptionManager;
}
```

Nothing in a "design a parking lot" problem statement mentioned multiple currencies or
subscriptions. Building for them now means writing, testing, and maintaining code that may never
be used — and worse, guessing wrong about what the *actual* future requirement will look like when
it does arrive, potentially making the real future change harder, not easier.

**The discipline:** build exactly what's needed for the stated requirements, structured cleanly
enough (via SOLID) that *genuine* future requirements can be added without a rewrite — but don't
pre-build features nobody asked for.

## How These Three Interact With SOLID

| Principle | What it optimizes for | Risk if taken to an extreme |
|---|---|---|
| SOLID (esp. OCP, DIP) | Extensibility, low coupling | Over-engineering, unnecessary abstraction |
| DRY | No duplicated knowledge | False abstraction from coincidental similarity |
| KISS | Readability, minimal complexity | Under-engineering, code that's hard to extend later |
| YAGNI | Building only what's needed now | Under-building genuinely-signaled requirements |

The skill isn't picking one column and maximizing it — it's a constant, judgment-driven balance.
An interviewer asking "why didn't you make this more generic?" is testing YAGNI/KISS awareness;
one asking "what if we need to add a new type here?" is testing OCP/DIP awareness. Good candidates
recognize which question is being asked and respond accordingly, rather than defaulting to always
maximizing flexibility or always minimizing it.

## Summary

- **DRY** eliminates duplicated *knowledge* — not merely similar-looking code that represents
  genuinely independent rules.
- **KISS** favors the simplest design that correctly solves the stated problem — patterns and
  abstractions should earn their complexity, not be applied by default.
- **YAGNI** means building for today's actual, stated requirements — not speculative future ones
  you're guessing at.
- All three act as a counterweight to SOLID: SOLID tells you how to structure things well; these
  three stop that structuring from spiraling into premature, unjustified complexity.

## Interview Questions

**1. State the DRY principle and clarify the common misconception about what counts as a
violation.**
DRY states every piece of knowledge (a business rule, a calculation, a policy) should have a
single, authoritative representation in the codebase. The common misconception is treating any
visually similar code as an automatic DRY violation — two blocks of code can look nearly identical
while representing genuinely independent business concerns that happen to coincide today but could
diverge for unrelated reasons in the future; merging those prematurely creates a false, harmful
coupling rather than fixing a real duplication problem.
*Follow-up: How do you tell the difference between "genuine duplicated knowledge" and
"coincidental similarity" in practice?* Ask whether the two pieces of logic would always need to
change together for the same underlying business reason — if a policy change to one would logically
imply the same change to the other (like "valid percentage range" applying universally), it's
genuine duplication; if they could plausibly diverge because they represent different concerns
that just happen to share a formula today, it's coincidental similarity.

**2. Give an example of merging two similar-looking pieces of code that turns out to be a
mistake, and explain why.**
Merging `OrderValidator.isValidDiscount()` and `PromotionValidator.isValidPercentage()` into one
shared method is correct if both genuinely represent "a percentage must be between 0 and 100" as
one universal rule. But if the business later decides promotional discounts can legitimately exceed
100% for special "buy one get two free" style promotions while regular percentages still cannot,
the merged method now has to awkwardly branch internally to handle two different rules — a sign the
original duplication was actually coincidental, not genuine, and the premature merge introduced
unwanted coupling between two rules that needed to evolve independently.
*Follow-up: How would you recover from this situation once discovered?* Split the merged method
back into two independent methods (or classes) representing the now-clearly-distinct rules,
undoing the premature DRY application — this kind of course-correction is a normal part of software
evolution, not a sign of an unrecoverable original mistake.

**3. State the KISS principle and give an example of violating it via unnecessary design pattern
usage.**
KISS states that simplicity should be a primary design goal, and unnecessary complexity should be
avoided even when a "more sophisticated" solution is available. Introducing a full Strategy pattern
with an interface, multiple implementing classes, and a context class for a `Greeter` that will
only ever produce one, fixed greeting format is a KISS violation — the added indirection (extra
files, an extra layer of abstraction to navigate) provides no real benefit over a single, plain
method, since there's no genuine variability to manage.
*Follow-up: How would you recognize, live in an interview, that you're about to over-engineer a
KISS violation?* If you notice you're reaching for an interface or a pattern purely out of habit
("this is how you're supposed to do it") rather than because the problem statement signals a real
need for multiple implementations or variability, pause and ask whether a plain class or method
would solve the stated problem just as well with less ceremony.

**4. State the YAGNI principle and explain its relationship to the Open/Closed Principle from
Chapter 8.**
YAGNI states you shouldn't build functionality until it's actually needed — don't implement
features, extension points, or configurability for requirements that haven't been stated or
strongly signaled. This directly tempers OCP: OCP says to build extensibility along axes of change
a problem signals, and YAGNI is the check that prevents you from building extensibility along axes
the problem *doesn't* signal, purely out of general "what if" thinking. The two principles work
together — OCP where signaled, YAGNI everywhere else.
*Follow-up: Can you give an example where following OCP correctly still requires restraint from
YAGNI?* If a problem statement says "fee calculation varies by vehicle type," OCP justifies a
`FeeStrategy` interface for vehicle-type-based fee variation — but YAGNI says not to also add a
configurable currency-conversion extension point, a pluggable tax-jurisdiction system, or a
discount-stacking framework unless the problem statement signals those too, even though they're
all "plausible future needs" in the abstract.

**5. In the `ParkingLot` example with the "just in case" currency converter and subscription
manager fields, what's the concrete cost of building these speculative features, beyond just
wasted time?**
Beyond the wasted implementation and testing effort, speculative features built without real
requirements are frequently *wrong* when the actual future need eventually materializes — you're
guessing at a shape for a requirement that hasn't been specified yet, and the guess is often
different enough from the eventual real requirement that the speculative code has to be
significantly reworked or discarded anyway, meaning the upfront investment provided little to no
actual benefit while still adding complexity and cognitive overhead for every developer who reads
the code in the meantime.
*Follow-up: Is there ever a case where "guessing right" about a future requirement and building it
early is actually the correct call?* In rare cases where a future requirement is not just plausible
but explicitly confirmed or contractually committed to (e.g., a client has already signed a
contract requiring multi-currency support in phase two), building toward it early can be reasonable
— the distinction YAGNI draws is between genuinely confirmed near-term requirements versus
speculative "might need this someday" guessing.

**6. How would you apply KISS when deciding between a `HashMap`-based lookup and a full Strategy
pattern with multiple classes for a simple mapping of vehicle type to fee?**
If the mapping is a simple, static lookup of vehicle type to a fixed fee amount with no
per-type *behavioral* variation (just different numbers, not different logic), a
`Map<VehicleType, Double>` populated once is simpler, more readable, and entirely sufficient — a
full Strategy pattern with a `FeeStrategy` interface and one class per vehicle type would be
justified only if each vehicle type's fee *calculation logic* genuinely differed (e.g., one type
uses flat fees, another uses hourly rates with rounding rules), not just the numeric constant.
*Follow-up: What's the tipping point where you'd switch from the simple map-based approach to the
full Strategy pattern?* The moment the fee "calculation" for at least one vehicle type needs actual
logic beyond a constant lookup (conditional rules, calculations involving multiple factors like
duration or day of week) — at that point, a uniform interface with per-type implementing classes
becomes the cleaner, more consistent solution across all vehicle types, even the simple ones.

**7. Explain how DRY, applied incorrectly, can actually violate the Single Responsibility
Principle.**
If you eliminate apparent duplication by merging two methods that represent genuinely different
business responsibilities into one shared method (because they look similar today), that merged
method now has multiple reasons to change — one whenever either of the two originally-independent
business rules changes — which is a direct SRP violation. This is the practical mechanism behind the
"coincidental similarity" trap: chasing DRY compliance too aggressively, without checking whether
the duplication is genuine, can accidentally create an SRP violation in the resulting merged code.
*Follow-up: Does this mean DRY and SRP can be in direct tension with each other?* In this specific
misapplication scenario, yes — but when DRY is applied correctly (only merging genuinely identical,
single-reason-to-change knowledge), the two principles are actually complementary, since a properly
DRY-compliant piece of shared knowledge naturally has exactly one clear reason to change, which is
exactly what SRP asks for.

**8. How would an interviewer's follow-up question "what if we need to support 50 vehicle types
instead of 3?" test your understanding of YAGNI versus OCP simultaneously?**
This question is checking two things at once: whether your current design (ideally already using
polymorphism/Strategy per OCP) scales cleanly to more types without structural changes — validating
your OCP compliance — and whether you'd resist the urge to prematurely over-engineer extra
configurability (like a fully data-driven, externally-configurable rules engine) if the interviewer
hasn't actually asked for that level of dynamism — validating your YAGNI discipline. A strong answer
confirms the existing polymorphic design already handles the scale-up cleanly (just more classes,
no structural change) without volunteering unnecessary additional complexity unless further
pressed.
*Follow-up: If the interviewer then says "actually, these vehicle types need to be configurable at
runtime by an admin, not hardcoded," how would your design need to change, and is that still
YAGNI-compliant to build now?* At that point, the requirement has become explicit and stated, so
building runtime configurability (perhaps loading `FeeStrategy` implementations dynamically via a
registry keyed by a string identifier, or externalizing them into configuration) is no longer
speculative — YAGNI doesn't apply once a requirement is actually confirmed; it only cautions against
building for *unconfirmed*, guessed-at future needs.

**9. Can KISS and SOLID be in direct conflict? Give a scenario where following SOLID rigorously
seems to violate KISS.**
Yes, in cases with genuinely low complexity and no real signal of future variation — introducing a
`DiscountPolicy` interface with three separate one-line implementing classes for what is, in
reality, a fixed, unlikely-to-change three-way discount table is technically SOLID (satisfies
OCP/DIP) but arguably violates KISS, since a simple `Map<CustomerType, Double>` lookup would be
just as maintainable and far less code for a genuinely static, small set of values. The resolution
in most real cases is to favor KISS unless the problem statement or realistic domain knowledge
signals actual future variability (per YAGNI's litmus test) — SOLID's flexibility is meant to be
applied where it earns its keep, not as an unconditional default.
*Follow-up: How would you decide, live in an interview, which of the two principles should win in
an ambiguous case like this?* Explicitly weigh the signals: does the problem statement mention or
imply the discount rules might grow more complex or numerous over time? If yes, lean toward the
SOLID-compliant interface design; if there's no such signal and the values are genuinely simple and
static, lean toward the simpler map-based KISS approach, and be ready to explain your reasoning
either way if the interviewer probes it.

**10. What's a real consequence of violating YAGNI that goes beyond "wasted effort" — how can it
actively make a codebase worse?**
Speculative, unused flexibility (interfaces with only one real implementation ever written,
configuration options nobody uses, extension points nothing ever plugs into) adds permanent
cognitive overhead for every future developer who has to read through and understand that
unnecessary indirection to figure out what the code actually does, even though none of that
flexibility is ever exercised. It also increases the surface area for bugs (more code paths to
maintain and potentially break) without any corresponding benefit, and can actively mislead future
developers into thinking a feature is more configurable or dynamic than it's ever actually used to
be in practice.
*Follow-up: How would you identify and safely remove unused speculative flexibility from an
existing, real production codebase?* Use static analysis or IDE tooling to find interfaces with
only one implementation and configuration options that are never actually varied in practice
(always set to the same value across every deployment), then evaluate whether removing that
unnecessary abstraction (collapsing an interface into a concrete class, hardcoding a
never-varied configuration value) is safe given current and realistically near-term requirements —
essentially applying YAGNI retroactively as a form of simplifying refactor.

**11. How would you apply DRY to shared validation logic across multiple LLD case-study
problems in this series — for instance, "must be a positive number" checks appearing across a
parking lot's fee calculation, a vending machine's price validation, and an ATM's withdrawal
amount validation?**
If these three checks genuinely represent the exact same rule ("this numeric value must be
positive") with no domain-specific nuance beyond that, extracting a shared, small utility method
(or even just consistently using existing validation utilities) is a reasonable DRY application.
However, if "positive number" validation for an ATM withdrawal also needs to check against an
account balance or daily limit — additional domain-specific rules beyond the generic
positivity check — that domain-specific validation shouldn't be forced into the same shared method
as the simpler parking-fee or vending-machine checks, since those represent genuinely different,
independently-evolving business rules beyond the shared generic core.
*Follow-up: How would you structure code to share the generic part while keeping the
domain-specific parts separate?* Have a shared, generic `Validators.isPositive(double value)`
utility method used by all three, while each domain's more specific validation logic
(`WithdrawalValidator`, `FeeValidator`) calls that shared utility as one part of its own broader,
domain-specific validation logic — sharing the genuinely common piece of knowledge while keeping
each domain's independently-evolving rules separate.

**12. Is "simple" in KISS the same as "few lines of code," or can a design be simultaneously
simple and involve a moderate amount of code?**
"Simple" in KISS refers to conceptual clarity and ease of understanding, not raw line count — a
design with slightly more code that clearly separates concerns and is easy to follow can be
"simpler" in the meaningful sense than a shorter but densely clever piece of code that's hard to
parse mentally. A single, deeply nested conditional expression that fits on one line but requires
significant mental effort to trace through is less KISS-compliant than a slightly longer, clearly
named set of methods that achieve the same result more legibly.
*Follow-up: Give an example where a "clever," compact piece of code actually violates KISS
despite being shorter.* A single Java stream chain with five nested `.map()`, `.filter()`, and
`.reduce()` operations packed onto one line, versus breaking the same logic into a few named
intermediate variables or a short, clearly-named private method — the stream version might be
"more elegant" by some measures but can genuinely violate KISS if it takes a reader noticeably
longer to understand what it's actually doing.

**13. How do you communicate a YAGNI-driven decision to an interviewer who explicitly asks "what
about future extensibility?" without sounding like you're dismissing legitimate design
concerns?**
Acknowledge the concern directly and explain that your current design already uses interfaces and
polymorphism where the problem statement signals genuine variability (demonstrating OCP/DIP
awareness), and that you're deliberately not adding further speculative flexibility beyond what's
been asked for, to keep the design focused and avoid guessing incorrectly at unstated future
requirements — while being explicit that you'd readily extend the design in a specific, concrete
direction if a particular future requirement were confirmed.
*Follow-up: What if the interviewer responds with a specific hypothetical future requirement right
after you say this?* Treat it as the requirement becoming stated/confirmed, which is exactly the
signal YAGNI says to watch for — walk through concretely how your existing polymorphic structure
would accommodate that specific new requirement (ideally with minimal or no changes to existing
code, per OCP), demonstrating that keeping things simple now didn't compromise your ability to
extend cleanly once a real need actually appears.

**14. Can DRY, KISS, and YAGNI ever conflict with each other, not just with SOLID?**
Yes, in some cases — aggressively eliminating even coincidental duplication (an overly strict
reading of DRY) can sometimes require introducing extra abstraction (a shared interface or a
generic parameterized method) to unify two things that are structurally similar today, which can
work against both KISS (added complexity) and YAGNI (building generalized shared infrastructure
before it's clear the "duplication" being eliminated is real, ongoing shared knowledge rather than
coincidence). The practical resolution is generally to favor the simpler, non-abstracted version
(KISS/YAGNI) unless the duplicated knowledge is clearly, confidently genuine (true DRY), rather
than defaulting to always removing every visible instance of repeated code on sight.
*Follow-up: What's a good rule of thumb for when to tolerate a small amount of duplication rather
than immediately abstracting it away?* A commonly cited informal rule (sometimes called the "rule
of three") suggests tolerating duplication the first time, and even the second time it appears, but
seriously considering extraction once a third genuinely-identical instance shows up — by then
there's much stronger evidence the duplication represents real, shared, stable knowledge rather than
coincidence, making the abstraction more likely to be worth its added complexity.
