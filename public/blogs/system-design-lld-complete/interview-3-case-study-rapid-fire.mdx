## How to Use This Chapter

Every entry is a curveball an interviewer might add to a case study from Part 8. Answer with:
which class(es) change, which classes stay untouched, and why. This is the exact skill Chapter 1
identified as the real test of an LLD interview — use this chapter to rehearse it across every
case study at once, right before an interview.

---

**1. Parking Lot: "Add electric vehicle charging spots."**
Add `ELECTRIC` to `VehicleType`, a new `ChargingSpot` variant, and an
`ElectricVehicleServiceFactory`. `EntryGate`, `ExitGate`, and `ParkingFloor.findAndReserveSpot()`
are untouched — the Abstract Factory structure absorbs it. (Ch. 45)

**2. Parking Lot: "Two drivers request the last compatible spot simultaneously."**
Already handled — `findAndReserveSpot()` is one write-locked, atomic operation. This curveball
tests whether you recognize the design already satisfies it. (Ch. 45)

**3. Elevator: "Add an express elevator that skips certain floors."**
New `DispatchStrategy` implementation plus a `servesFloor()` check on `Elevator`. `ElevatorState`
implementations and the SCAN algorithm are untouched. (Ch. 46)

**4. Elevator: "Add a fire-emergency override that takes priority over all requests."**
A `PriorityDispatchStrategy` decorator wrapping the normal strategy. No changes to
`NearestElevatorDispatchStrategy`. (Ch. 46)

**5. Library: "A physical copy is reported lost while a member is holding it."**
`BookCopy.status` transitions to `LOST`; the inventory/return flow needs a new case, but
`HoldQueue` and `Checkout` structures are untouched.

**6. Library: "Support multiple branches sharing one catalog."**
Add a `Branch` entity that `BookCopy` associates with; `Book` (catalog metadata) stays shared and
unchanged. (Ch. 47)

**7. Vending Machine: "Add a cancel button before dispensing."**
Genuinely touches every `VendingMachineState` implementation — a new interface method is an
acknowledged, non-free cost. (Ch. 48)

**8. Vending Machine: "Notify a restocking system when quantity gets low."**
`Slot` implements `Subject`, notifies on `dispense()`. No changes to `PaymentMethod` or the state
machine. (Ch. 29, 48)

**9. ATM: "Add a daily withdrawal limit."**
`WithdrawalStrategy.execute()` gains a check. `DepositStrategy` and `AtmState` are untouched —
isolated by the Strategy structure. (Ch. 49)

**10. ATM: "What if the network fails mid-PIN-validation?"**
Points to a gap — worth naming a `NetworkErrorState` that safely ejects the card without
completing a transaction, even though network integration itself is out of scope. (Ch. 49)

**11. Chess: "Add castling."**
Doesn't fit `MovementStrategy`'s single-piece signature — handled as a special case inside
`Game.makeMove()`. Naming this honestly is the stronger answer. (Ch. 50)

**12. Chess: "Support a full move-history replay feature."**
Already nearly free — `Game` already saves a `Board.Memento` before every move; stepping forward
through the history reuses existing infrastructure. (Ch. 50)

**13. Splitwise: "Support editing or removing an expense after it's added."**
Works cleanly because balances are additive deltas — reverse by recording the exact negative
adjustment. Fails if balances were instead recomputed aggregates. (Ch. 51)

**14. Splitwise: "Split by shares (roommate A pays 2 shares, B pays 1)."**
One new `SharesSplitStrategy`. `Expense` and `BalanceSheet` untouched. (Ch. 51)

**15. BookMyShow: "Support group bookings where either all seats lock or none do."**
Already handled — `BookingFacade`'s rollback loop already releases every previously-acquired
lock on any failure. Recognizing this needs no new code is the stronger answer. (Ch. 52)

**16. BookMyShow: "Payment succeeds but confirming one seat fails afterward."**
A genuinely harder, distinct failure mode (money already moved) — needs a refund or retry path,
worth naming as different from pre-payment rollback rather than conflating the two. (Ch. 52)

**17. Cab Booking: "The matched driver doesn't respond within 30 seconds."**
A scheduled timeout re-runs `DriverMatchingStrategy` excluding the non-responsive driver.
`RideState` implementations are untouched — it's dispatcher orchestration logic. (Ch. 53)

**18. Cab Booking: "Add a promotional discount that stacks with surge pricing."**
Stack decorators: `new PromotionalDiscountDecorator(new SurgePricingDecorator(base, 1.5), 0.1)`.
No changes to any existing decorator or the base strategy. (Ch. 24, 53)

**19. Food Delivery: "A menu item goes out of stock after ordering but before confirmation."**
A genuine gap — needs a new availability re-check inside `PlacedState.confirm()`, possibly a new
state. Not something the existing states already cover for free. (Ch. 54)

**20. Food Delivery: "Notify the customer at each order stage."**
`Order` implements `Subject`, notifies inside `setState()`. No changes to `OrderState`
implementations themselves. (Ch. 29, 54)

**21. LRU Cache: "Add a TTL so entries expire after N seconds."**
Add `expiryTime` to `Node`, check it in `get()`. Core doubly-linked-list eviction mechanics
untouched. (Ch. 55)

**22. LRU Cache: "Switch to an LFU eviction policy instead."**
Not a free extension — LFU needs frequency tracking, typically frequency-bucketed lists, a
meaningfully different structure from LRU's single recency-ordered list. (Ch. 55)

**23. Logging Framework: "Support per-appender log levels" (console shows WARN+, file logs
everything).**
Breaks the "filter once, centrally" design — threshold logic must move from `Logger` to each
`LogAppender`. A genuine architectural shift, not a free extension. (Ch. 56)

**24. Logging Framework: "Add asynchronous file logging."**
Wrap `FileAppender` with a queue-backed wrapper (Producer-Consumer, Ch. 39) — `Logger` itself is
untouched, since it depends only on the `LogAppender` interface. (Ch. 56)

**25. E-commerce Checkout: "Reorder the checkout pipeline steps via configuration."**
Only the chain-assembly code changes (`setNext()` wiring) — zero changes to any individual
handler class, since Chain of Responsibility was the right structural choice. (Ch. 57)

**26. E-commerce Checkout: "Inventory becomes unavailable between validation and reservation."**
A genuine race condition across two separate pipeline steps — the fix is combining validation and
reservation into one atomic step, mirroring `findAndReserveSpot()`. (Ch. 40, 45, 57)

**27. Text Editor: "Group several autocomplete-inserted characters into one undoable action."**
A `MacroCommand` wrapping the individual insert commands, undone in reverse order. `UndoManager`
needs zero changes — it already treats every `EditCommand` uniformly. (Ch. 30, 58)

**28. Text Editor: "Support undo across multiple simultaneously open documents."**
Each `Document` needs its own independent `UndoManager` — a single shared one would incorrectly
mix unrelated documents' histories. (Ch. 58)

**29. Across every case study: what's the one design smell that most reliably predicts a
curveball will require a disruptive rewrite rather than a clean extension?**
A conditional (`if/else` or `switch`) branching on type scattered through business logic, rather
than the relevant variation being isolated behind an interface — exactly the OCP violation
pattern from Chapter 8, the first structural lesson this entire series was built around.

**30. What's the one process habit, more than any specific pattern, that makes a candidate look
strong when handling any of these curveballs live?**
Actually tracing the change through the real structure — naming the specific class(es) that
change and explicitly confirming which ones don't — rather than a vague verbal assurance that "it
would just work." (Ch. 1, 43, 44)
