## Java Is Statically and Strongly Typed

Every variable in Java has a declared type, checked at compile time, and that type cannot change. This is different from dynamically-typed languages (Python, JavaScript) where a variable can hold any type at runtime. Static typing catches a large class of bugs before the program ever runs.

## The Eight Primitive Types

Primitives store raw values directly, not references to objects, and live on the stack when they're local variables.

| Type      | Size    | Range / Notes                                  | Default |
|-----------|---------|-------------------------------------------------|---------|
| `byte`    | 8 bits  | -128 to 127                                     | 0       |
| `short`   | 16 bits | -32,768 to 32,767                               | 0       |
| `int`     | 32 bits | ~-2.1B to 2.1B                                  | 0       |
| `long`    | 64 bits | ~-9.2 quintillion to 9.2 quintillion             | 0L      |
| `float`   | 32 bits | IEEE 754 single-precision                       | 0.0f    |
| `double`  | 64 bits | IEEE 754 double-precision                       | 0.0d    |
| `char`    | 16 bits | single UTF-16 code unit, 0 to 65,535             | '\u0000'|
| `boolean` | JVM-dependent (typically 1 bit of info, size unspecified) | `true`/`false` | false |

```java
int age = 30;
long population = 8_100_000_000L;   // underscore separators for readability (Java 7+)
double price = 19.99;
char grade = 'A';
boolean isActive = true;
```

## Reference Types

Everything that isn't a primitive — objects, arrays, `String`, custom classes — is a **reference type**. A reference-type variable holds a pointer to an object on the heap, not the object itself.

```java
String name = "Rahul";     // name holds a reference to a String object
int[] scores = {90, 85};   // scores holds a reference to an array object
```

The default value of any uninitialized reference-type field is `null` — the absence of a reference.

## Variable Scope

- **Local variables** — declared inside a method; must be explicitly initialized before use; live only for the method call's duration (on the stack).
- **Instance variables (fields)** — declared in a class, outside any method; one copy per object; automatically initialized to the type's default value.
- **Static variables** — declared with `static`; one copy shared across all instances of the class; also default-initialized.

```java
public class Counter {
    static int totalCounters = 0;   // static: shared across all instances
    int id;                          // instance: one per object

    public Counter() {
        id = ++totalCounters;
    }

    public void increment(int by) {
        int result = id + by;        // local: exists only during this call
    }
}
```

## Wrapper Classes, Autoboxing & Unboxing

Every primitive has a corresponding wrapper class (`int` → `Integer`, `boolean` → `Boolean`, etc.) so primitives can be used where an object is required — in collections, generics, or when `null` is a meaningful state.

```java
List<Integer> scores = new ArrayList<>();
scores.add(90);              // autoboxing: int 90 -> Integer.valueOf(90)
int first = scores.get(0);   // auto-unboxing: Integer -> int
```

**Integer caching** is a common interview trap: `Integer` values from -128 to 127 are cached and reused by `Integer.valueOf()`, so `==` comparisons can behave unexpectedly:

```java
Integer a = 100, b = 100;
System.out.println(a == b);   // true — both point to the same cached instance

Integer x = 200, y = 200;
System.out.println(x == y);   // false — outside the cache range, separate objects
```

Always use `.equals()` to compare wrapper values, never `==`, unless you specifically intend reference comparison.

## Type Casting

**Widening (implicit)** — converting a smaller type to a larger one happens automatically, with no data loss:

```java
int i = 100;
long l = i;      // int -> long, implicit
double d = l;    // long -> double, implicit
```

**Narrowing (explicit)** — converting a larger type to a smaller one requires an explicit cast, and can lose data or precision:

```java
double d = 9.99;
int i = (int) d;        // 9 — fractional part truncated, not rounded

long big = 3_000_000_000L;
int overflowed = (int) big;   // overflow — result wraps around unpredictably
```

## Key Takeaways

- Java has 8 primitive types; everything else is a reference type backed by objects on the heap.
- Local variables must be explicitly initialized; fields get default values automatically.
- Autoboxing/unboxing is convenient but has real costs (object allocation) and traps (`Integer` caching with `==`).
- Widening casts are implicit and safe; narrowing casts are explicit and can silently lose data.

## Interview Questions

**1. What's the difference between primitive types and reference types in Java?**
Primitives (`int`, `boolean`, `double`, etc.) store their actual value directly and are not objects — they have no methods, and comparing them with `==` compares values. Reference types (objects, arrays, `String`) store a reference (pointer) to data on the heap; comparing references with `==` compares whether two variables point to the *same object*, not whether their contents are equal.

**2. Why does `Integer a = 100; Integer b = 100; a == b` return `true`, but the same code with `200` returns `false`?**
The JVM caches boxed `Integer` values in the range -128 to 127 (`IntegerCache`), so `Integer.valueOf(100)` returns the same cached object both times, making `==` true. Values outside that range create new `Integer` objects each time, so `==` compares different object references and returns false.
*Follow-up:* How would you correctly compare two `Integer` objects for value equality regardless of range? (Answer: use `.equals()`, or unbox both to `int` before comparing.)

**3. What are the default values of instance variables versus local variables?**
Instance (and static) variables are automatically initialized to a default value based on type — `0`/`0.0` for numeric types, `false` for `boolean`, `'\u0000'` for `char`, `null` for references. Local variables receive **no default value** and must be explicitly assigned before use, or the compiler raises a "variable might not have been initialized" error.

**4. What is autoboxing, and what's a real performance cost of relying on it heavily?**
Autoboxing is the compiler automatically wrapping a primitive in its corresponding wrapper object (e.g., `int` → `Integer`) when an object is required, such as adding to a `List<Integer>`. Each boxing operation outside the cached range allocates a new object, so autoboxing inside tight loops (e.g., summing millions of values into an `Integer` accumulator) creates significant, avoidable garbage-collection pressure compared to using a primitive accumulator directly.

**5. What's the difference between widening and narrowing conversions?**
Widening converts a smaller-range type to a larger-range type (e.g., `int` to `long`) and happens implicitly since no data can be lost. Narrowing converts a larger-range type to a smaller one (e.g., `double` to `int`) and requires an explicit cast because it can lose precision or overflow.

**6. What happens when you cast a `double` like `9.99` to an `int`?**
It truncates the fractional part rather than rounding — `(int) 9.99` yields `9`, and `(int) -9.99` yields `-9` (truncation toward zero, not toward negative infinity).

**7. What happens if you cast a `long` value larger than `Integer.MAX_VALUE` down to an `int`?**
It overflows silently — the bits are truncated to fit 32 bits, producing a value determined by two's-complement wraparound, not an exception. This is a classic source of subtle bugs, since Java doesn't throw on numeric overflow by default.

**8. Why does Java need both primitives and their wrapper classes instead of just objects for everything?**
Primitives exist for performance and memory efficiency — no object header overhead, no heap allocation, direct value storage on the stack. Wrapper classes exist because generics, collections, and any API requiring `Object` can't work with primitives directly; wrappers bridge that gap while primitives remain the default choice for raw computation.

**9. What is the size and default value of a `boolean` in Java, and why is it not precisely specified?**
The JVM specification doesn't mandate an exact bit size for `boolean` — the JVM is free to represent it however is efficient internally (often as an `int` in bytecode, since the JVM has no dedicated boolean bytecode type). Its default value is `false`. This is different from most primitives, which have JVM-specification-mandated sizes.

**10. Can you assign a `char` to an `int` without an explicit cast? What about the reverse?**
Yes — `char` to `int` is a widening conversion (a `char` is an unsigned 16-bit value, which fits safely in a 32-bit `int`), so it's implicit: `int code = 'A';` compiles fine (yielding `65`). Going the other way, `int` to `char`, is narrowing and requires an explicit cast: `char c = (char) 65;`.

**11. What's the difference between `float` and `double`, and which does Java use by default for decimal literals?**
`float` is 32-bit single precision; `double` is 64-bit double precision with roughly twice the significant digits of accuracy. Java treats any decimal literal (e.g., `3.14`) as a `double` by default — assigning it to a `float` variable requires either an `f` suffix (`3.14f`) or an explicit cast, because it's otherwise a narrowing conversion.

**12. Why should `==` never be used to compare `float`/`double` values for equality?**
Floating-point types can't exactly represent most decimal fractions in binary, so two values that are mathematically equal (or the result of equivalent computations) can differ by tiny rounding errors. Comparisons should use a tolerance/epsilon check (e.g., `Math.abs(a - b) < 1e-9`) instead of exact `==`.

**13. What's the difference between a local variable, an instance variable, and a static variable in terms of memory and lifetime?**
Local variables live on the thread's stack, scoped to the method call, and are destroyed when the method returns. Instance variables live on the heap as part of an object, one copy per instance, and are destroyed when the object becomes eligible for garbage collection. Static variables live in the JVM's method area (metaspace), one copy shared across all instances of the class, and persist for the lifetime of the class being loaded in that JVM.
