## A Class Is a Blueprint, an Object Is an Instance

A **class** defines the shape of something — its fields (state) and methods (behavior) — without allocating any memory itself. An **object** is a concrete instance of that class, created at runtime and living on the heap.

```java
public class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double balance) {
        this.owner = owner;
        this.balance = balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}
```

```java
BankAccount acc1 = new BankAccount("Rahul", 1000.0);
BankAccount acc2 = new BankAccount("Priya", 500.0);

acc1.deposit(250.0);
System.out.println(acc1.getBalance());  // 1250.0
System.out.println(acc2.getBalance());  // 500.0 — independent state
```

`acc1` and `acc2` are two separate objects, each with its own copy of `owner` and `balance` — this is what "state" means per-instance.

## What Happens on `new`

```java
BankAccount acc1 = new BankAccount("Rahul", 1000.0);
```

![Diagram: stack frame holding reference variable acc1, arrow pointing to a BankAccount object on the heap containing owner and balance fields](/diagrams/ch07-object-creation-stack-heap.svg)

1. The JVM allocates memory on the heap for a new `BankAccount` object.
2. Fields are set to their default values first (`null`/`0`).
3. The constructor runs, assigning the actual field values.
4. The reference to the new object is stored in the local variable `acc1` (on the stack).

`acc1` never holds the object itself — only a reference (a pointer) to where it lives on the heap.

## Fields (State) vs. Methods (Behavior)

- **Fields** represent an object's data — what it *knows*.
- **Methods** represent an object's operations — what it *does*, often operating on its own fields.

Grouping related state and behavior together, and controlling access to that state (Chapter 9 covers encapsulation in depth), is the core discipline of object-oriented design.

## Instance Members vs. the Class Itself

Every object created from `BankAccount` gets its own `owner` and `balance`, but they all share the *same* method code — the JVM doesn't duplicate method bytecode per object. Instance methods implicitly receive a reference to the specific object they're called on (accessible inside the method as `this`).

```java
public void deposit(double amount) {
    this.balance += amount;   // "this" refers to the specific object deposit() was called on
}
```

## Key Takeaways

- A class is a compile-time blueprint; an object is a runtime instance living on the heap.
- Each object has its own independent copy of instance fields, but shares method code across all instances.
- Reference variables point to objects — they aren't the objects themselves.
- `this` inside an instance method refers to the specific object the method was invoked on.

## Interview Questions

**1. What's the fundamental difference between a class and an object?**
A class is a compile-time construct — a blueprint describing what fields and methods instances of it will have, but it occupies no memory for object state itself. An object is a runtime instance of a class, allocated on the heap when you call `new`, with its own independent copy of the class's instance fields.

**2. When you write `BankAccount acc = new BankAccount(...)`, what exactly does the variable `acc` hold?**
It holds a *reference* (essentially a memory address, though the JVM doesn't expose it directly) to the `BankAccount` object on the heap — not the object's data itself. This is why assigning `acc` to another variable copies the reference, not the object (as covered with arrays in Chapter 6, and revisited for objects generally here).

**3. Do two objects of the same class share their instance field values?**
No — each object gets its own independent copy of every instance field, initialized either to defaults or via the constructor. Changing a field on one object has no effect on any other object's copy of that field.

**4. Do two objects of the same class share their method implementations?**
Yes — the JVM stores method bytecode once per class (in the method area/metaspace), not once per object. Every object of that class executes the same method code; what differs between calls is which object's state (`this`) the method operates on.

**5. What is `this` inside an instance method, and when is it necessary to use it explicitly?**
`this` is an implicit reference to the specific object the current method was invoked on. It's required explicitly when a parameter or local variable shadows a field name of the same name (`this.balance = balance;` disambiguates the field from the parameter), or when passing the current object as an argument to another method/constructor.

**6. Can a class exist without ever being instantiated? Give an example of when that's actually the point.**
Yes — a class made entirely of `static` members (like a utility class such as `java.lang.Math`) is never meant to be instantiated; its methods are called directly on the class itself. Such utility classes conventionally have a private constructor to explicitly prevent instantiation.

**7. What is the difference between an object's "state" and its "behavior"?**
State refers to the values held in an object's instance fields at a given moment — what the object currently *is*. Behavior refers to the methods defined on its class — what the object can *do*, typically by reading or modifying its own state.

**8. Where do object instances live in memory, and where do the reference variables pointing to them live?**
Objects themselves live on the heap, a shared memory region managed by the garbage collector. Reference variables that point to those objects live wherever they're declared — local variable references live on the calling thread's stack, while reference-type instance fields live inside whatever object contains them (also on the heap).

**9. What happens to the memory occupied by an object once no reference to it exists anymore?**
It becomes eligible for garbage collection — the JVM's garbage collector will eventually reclaim that memory, since an unreachable object can never be used again by the running program. Exactly *when* this happens is not deterministic or immediately guaranteed (covered in depth in Chapter 46), unlike languages with manual memory management.

**10. Can multiple reference variables point to the same object? What's the implication if they do?**
Yes — assignment (`BankAccount acc2 = acc1;`) copies the reference, not the object, so both variables end up pointing to the exact same object on the heap. Modifying state through either variable is visible through the other, since there's really only one underlying object being shared.

**11. Why is grouping fields and methods together in a class considered better design than having free-floating functions operating on separate data structures?**
Bundling state and the operations that act on it lets a class enforce its own invariants — for example, `BankAccount` can guarantee `balance` never goes negative by controlling all mutation through its own methods, rather than trusting every piece of external code that touches a raw `balance` variable to behave correctly. This is the foundation for encapsulation, covered in depth in Chapter 9.
