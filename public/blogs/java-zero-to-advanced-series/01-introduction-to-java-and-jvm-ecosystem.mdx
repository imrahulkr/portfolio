## Why Java, and Why It Still Matters

Java was released by Sun Microsystems in 1995 with one radical promise for its time: **write once, run anywhere (WORA)**. Instead of compiling source code directly into machine code tied to one operating system, Java compiles into an intermediate form called **bytecode**, which any machine running a Java Virtual Machine (JVM) can execute — Windows, Linux, macOS, or embedded hardware, all from the same `.class` file.

Three decades later, Java (now on a 6-month release cadence with an LTS release every two years — this series targets **Java 21 LTS**) still underpins the majority of enterprise backend systems, Android app internals, and large-scale distributed platforms. Understanding *why* it was built this way is the foundation for everything else in this series, including your Spring Boot work.

## JDK vs JRE vs JVM

These three acronyms get confused constantly, so let's separate them clearly:

- **JVM (Java Virtual Machine)** — the runtime engine that actually executes bytecode. It's a specification, and multiple implementations exist (HotSpot, from Oracle/OpenJDK, is the most common).
- **JRE (Java Runtime Environment)** — the JVM plus the core class libraries (`java.lang`, `java.util`, etc.) needed to *run* a compiled Java program. It has no compiler.
- **JDK (Java Development Kit)** — the JRE plus development tools: `javac` (compiler), `javadoc`, `jar`, debuggers, and profilers. This is what you install to *write and build* Java programs.

![Diagram: JDK contains JRE contains JVM, with javac/tools sitting alongside the JRE inside the JDK boundary](/diagrams/ch01-jdk-jre-jvm.svg)

Since Java 11, Oracle stopped shipping a separate JRE download — you always install a JDK, even just to run programs. This series assumes you have a JDK 21 distribution (Eclipse Temurin, Oracle OpenJDK, or Amazon Corretto all work identically for our purposes).

## From Source Code to Running Program

Here's the full lifecycle of a Java program:

```java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}
```

1. You write `HelloWorld.java` — human-readable source code.
2. `javac HelloWorld.java` invokes the **compiler**, which produces `HelloWorld.class` — platform-independent **bytecode**, not machine code.
3. `java HelloWorld` starts the JVM, which:
   - **Loads** the class file via the class loader subsystem (covered in depth in Chapter 45).
   - **Verifies** the bytecode for safety (no illegal memory access, stack overflows, etc.).
   - **Executes** it — initially by interpreting bytecode instruction-by-instruction, then using the **JIT (Just-In-Time) compiler** to translate "hot" code paths directly into native machine code for speed (Chapter 47 goes deep on this).

![Diagram: pipeline showing .java file -> javac -> .class bytecode -> JVM (class loader, bytecode verifier, interpreter/JIT) -> native execution](/diagrams/ch01-compile-run-pipeline.svg)

This split — compile once to bytecode, let each machine's JVM handle the last mile to native code — is the entire mechanism behind "write once, run anywhere."

## Java's Platform Editions

You'll see these terms in job postings and documentation:

- **Java SE (Standard Edition)** — the core language and libraries. Everything in this series is Java SE.
- **Jakarta EE (formerly Java EE)** — enterprise APIs (servlets, JPA, CDI) built on top of SE. Spring Boot largely replaces the need to use Jakarta EE directly, which is why our Spring Boot series handles that layer.
- **Java ME (Micro Edition)** — a stripped-down version for resource-constrained embedded devices, largely niche today.

## Key Takeaways

- Java compiles to platform-independent bytecode, not native machine code — the JVM bridges the gap at runtime.
- JDK ⊃ JRE ⊃ JVM: JDK is for developers, JRE is for running programs, JVM is the execution engine itself.
- The JIT compiler is why long-running Java programs (like Spring Boot services) get *faster* the longer they run — hot paths get compiled to native code.

## Interview Questions

**1. What is the difference between JDK, JRE, and JVM?**
The JVM is the runtime engine that executes bytecode; it's a specification with multiple implementations (e.g., HotSpot). The JRE bundles the JVM with the standard class libraries needed to run compiled programs, but has no compiler. The JDK bundles the JRE with development tools like `javac`, `javadoc`, and debuggers — it's what you need to *write and build* Java software, not just run it.
*Follow-up:* Since Java 11 there's no separate JRE download from Oracle — why do you think that changed? (Answer: tooling converged around always distributing a full JDK, since even running some frameworks benefits from JDK-only tools like `jlink` for custom runtime images.)

**2. Explain "write once, run anywhere." How does Java actually achieve it?**
Java source compiles to bytecode (`.class` files) rather than platform-specific machine code. Any machine with a compatible JVM installed can execute that bytecode, so the same compiled artifact runs unmodified on Windows, Linux, or macOS. The JVM — not your code — is what's platform-specific.
*Follow-up:* Does WORA hold 100% in practice? (Answer: mostly, but subtle differences can appear — file path separators, line endings, locale-sensitive operations, and native library dependencies (JNI) can break true platform independence.)

**3. What is bytecode, and why doesn't Java compile directly to native machine code?**
Bytecode is a compact, platform-neutral instruction set that the JVM understands. Compiling to bytecode instead of native code decouples the compiler from the target hardware — a single `.class` file can run anywhere a JVM exists, and the JVM can apply runtime optimizations (like JIT compilation) that a purely static compiler couldn't, since it can observe actual runtime behavior.

**4. What is the JIT compiler, and how does it differ from the initial interpretation of bytecode?**
When a program starts, the JVM interprets bytecode line-by-line, which is slower but starts instantly. As the JVM notices "hot" methods (called frequently), the JIT compiler compiles those specific methods into native machine code, which then executes at near-native speed for the rest of the program's life. This is why the same Java program often gets measurably faster after a warm-up period.

**5. What does the bytecode verifier do, and why does it matter for security?**
Before executing any loaded class, the JVM's bytecode verifier checks that the bytecode doesn't violate JVM safety rules — no illegal type casts, no stack over/underflows, no accessing private members without permission, no jumping to invalid instructions. This matters because bytecode could come from an untrusted source (a downloaded applet historically, or a third-party library today), and the verifier prevents malformed or malicious bytecode from corrupting the JVM's memory or bypassing access rules.

**6. What's the difference between Java SE, Java EE (Jakarta EE), and Java ME?**
Java SE is the core language and standard libraries — collections, I/O, concurrency, etc. Jakarta EE builds enterprise-facing APIs (servlets, JPA, CDI, JMS) on top of SE for large business applications. Java ME is a minimal profile for resource-constrained embedded/mobile devices. In modern practice, Spring Boot has largely replaced direct Jakarta EE usage for enterprise development.

**7. Is Java a compiled or interpreted language?**
It's both, which is why it's often called a "hybrid." Source code is compiled ahead-of-time to bytecode by `javac`. That bytecode is then interpreted by the JVM at first, with the JIT compiler progressively compiling hot paths to native code as the program runs. So it's compiled once, then a mix of interpreted and JIT-compiled at runtime.

**8. Can compiled Java bytecode run on any machine without modification?**
Yes, as long as a compatible JVM is installed for that platform and the bytecode's class file version doesn't exceed what that JVM supports (e.g., bytecode compiled with `--release 21` won't run on a Java 17 JVM, but Java 17 bytecode will run fine on a Java 21 JVM due to backward compatibility).
*Follow-up:* What happens if you try to run Java 21 bytecode on a Java 17 JVM? (Answer: `UnsupportedClassVersionError` is thrown, since the class file's major version exceeds what that JVM understands.)

**9. What is the significance of the `main` method signature `public static void main(String[] args)`?**
`public` so the JVM (external to the class) can invoke it. `static` so the JVM can call it without needing to first instantiate an object of the class. `void` because it doesn't return a value to the OS in the typical case (exit codes use `System.exit()` instead). `String[] args` receives command-line arguments passed when launching the program.

**10. What's the difference between HotSpot, OpenJDK, and vendor distributions like Corretto or Temurin?**
OpenJDK is the open-source reference implementation of the Java SE specification. HotSpot is the specific JVM implementation that ships as part of OpenJDK (there are alternatives like Eclipse OpenJ9). Vendor distributions (Amazon Corretto, Eclipse Temurin, Azul Zulu) are builds of OpenJDK, often with different support timelines, patches, or licensing terms, but they're functionally the same JVM specification underneath.

**11. Why does Java use a garbage-collected, managed runtime instead of manual memory management like C/C++?**
A managed runtime automatically reclaims memory that's no longer reachable, eliminating an entire class of bugs (dangling pointers, double frees, most memory leaks) that plague manually-managed languages. The trade-off is less fine-grained control over memory and the overhead of the garbage collector itself, which is why understanding GC behavior (Chapter 46) matters for performance-sensitive Java applications.

**12. What role does the classpath play when running a Java program?**
The classpath tells the JVM where to look for compiled `.class` files and JAR dependencies needed to resolve the classes your program references. If a required class isn't found on the classpath, the JVM throws a `ClassNotFoundException` or `NoClassDefFoundError` at runtime rather than failing at compile time, which is a common source of "works on my machine" bugs.
*Follow-up:* What's the difference between `ClassNotFoundException` and `NoClassDefFoundError`? (Answer: `ClassNotFoundException` is a checked exception thrown when code explicitly tries to load a class by name, e.g. via reflection, and it isn't found. `NoClassDefFoundError` is an error thrown when a class *was* available at compile time but is missing from the classpath at runtime — often due to a dependency version mismatch.)
