## `HashSet` — Fastest Lookup, No Order Guarantee

`HashSet` is internally backed by a `HashMap` (each element is stored as a key in that map, with a shared dummy constant as the value). Uniqueness and O(1) average lookup both come from the same mechanism: `hashCode()` determines the bucket, `equals()` confirms an exact match within it.

```java
Set<String> tags = new HashSet<>();
tags.add("java");
tags.add("spring");
tags.add("java");     // ignored — already present, per equals()/hashCode()
System.out.println(tags.size());   // 2
```

Iteration order is **not guaranteed** and can even change between runs of the same program — never write code that depends on `HashSet` iteration order.

This is exactly why the `equals()`/`hashCode()` contract from Chapter 13 matters so much here: if you add custom objects to a `HashSet` without overriding both consistently, duplicate-looking objects can both get added, since the set can't recognize they're "the same" without a correct `hashCode()`/`equals()` pair.

## `LinkedHashSet` — Predictable Insertion Order

`LinkedHashSet` extends `HashSet` internally but additionally maintains a doubly-linked list threading through all entries in insertion order, giving predictable iteration order at a small extra memory and time cost per operation.

```java
Set<String> tags = new LinkedHashSet<>();
tags.add("java");
tags.add("spring");
tags.add("react");

for (String tag : tags) {
    System.out.println(tag);   // always prints: java, spring, react — insertion order preserved
}
```

Use `LinkedHashSet` when you need uniqueness *and* a stable, predictable iteration order (e.g., displaying tags to a user in the order they were added) — `HashSet`'s performance advantage over it is minor in practice.

## `TreeSet` — Sorted Order, `NavigableSet` Operations

`TreeSet` is backed internally by a **Red-Black tree** (a self-balancing binary search tree), keeping elements in sorted order at all times — either their natural order (`Comparable`, Chapter 23) or a custom `Comparator` supplied at construction.

```java
Set<Integer> scores = new TreeSet<>();
scores.add(85);
scores.add(42);
scores.add(99);

System.out.println(scores);   // [42, 85, 99] — always sorted

TreeSet<Integer> treeSet = (TreeSet<Integer>) scores;
System.out.println(treeSet.first());        // 42
System.out.println(treeSet.last());         // 99
System.out.println(treeSet.ceiling(50));    // 85 — smallest element >= 50
System.out.println(treeSet.floor(50));      // 42 — largest element <= 50
```

Because it maintains sorted order via tree rebalancing, `TreeSet` operations run in O(log n) rather than `HashSet`'s average O(1) — a direct trade of some performance for ordering guarantees and range-query capability.

## Comparison Table

| | Order | Lookup/Insert | Allows `null`? | Backing structure |
|---|---|---|---|---|
| `HashSet` | None (unspecified) | O(1) average | One `null` allowed | Hash table (via `HashMap`) |
| `LinkedHashSet` | Insertion order | O(1) average | One `null` allowed | Hash table + linked list |
| `TreeSet` | Sorted order | O(log n) | No `null` (throws `NullPointerException`) | Red-Black tree |

`TreeSet` rejects `null` because it must be able to compare every element against every other to maintain sort order, and comparing against `null` has no defined meaning (`null.compareTo(x)` would throw regardless).

## Key Takeaways

- All `Set` implementations guarantee no duplicates, differing only in ordering behavior and performance characteristics.
- `HashSet` is fastest but gives no ordering guarantee at all; never rely on its iteration order.
- `LinkedHashSet` adds predictable insertion-order iteration for a small overhead over `HashSet`.
- `TreeSet` maintains full sorted order via a Red-Black tree, at O(log n) cost, and disallows `null`.

## Interview Questions

**1. How does `HashSet` internally guarantee that no duplicate elements are stored?**
`HashSet` is backed internally by a `HashMap`, where each added element becomes a key in that map (paired with a shared dummy constant value). Adding an element that's already present, per its `hashCode()`/`equals()`, simply overwrites the existing map entry with an equal key, which has no observable effect — the set's size and contents don't change, which is exactly the "no duplicates" behavior.

**2. Why is `HashSet` iteration order described as "unspecified," and what's the practical implication?**
Element order depends on internal hash bucket placement, which is influenced by each element's hash code and the table's current capacity — neither of which relates to insertion order, and which can even change between separate runs of the same program (e.g., due to different `hashCode()` results across JVM versions, or resizing that occurred differently). Practically, this means code should never depend on `HashSet` iteration producing any particular order — if order matters, use `LinkedHashSet` or `TreeSet` instead.

**3. What does `LinkedHashSet` add on top of `HashSet`'s behavior, and at what cost?**
It maintains a doubly-linked list threading through all entries in the order they were inserted, so iteration always visits elements in that stable, predictable order. The cost is a small amount of extra memory per entry (for the linked-list pointers) and a marginally higher constant-factor overhead per insertion/removal to maintain that list — the asymptotic O(1) average complexity for core operations remains the same as `HashSet`.

**4. What data structure backs `TreeSet`, and why does that choice give it O(log n) rather than O(1) operations?**
A Red-Black tree — a self-balancing binary search tree that guarantees a maximum height of O(log n) for any number of elements. Insertion, removal, and lookup all require traversing from the root down through the tree's height to find or place the correct node, and that traversal cost is fundamentally what a search tree trades for its ordering guarantee, unlike a hash table's near-constant-time bucket lookup.

**5. Why does `TreeSet` throw a `NullPointerException` when you try to add `null`, while `HashSet` allows one `null` element?**
`TreeSet` must be able to compare every element against existing elements to determine where it belongs in sorted order, and there's no well-defined way to compare `null` against a real value using `compareTo()` (attempting it throws `NullPointerException` regardless of which side is null). `HashSet` has no such ordering requirement — it only needs `hashCode()` and `equals()`, both of which can be defined sensibly for `null` (its hash code is conventionally treated as `0`), so exactly one `null` is permitted.

**6. What must be true about elements added to a `TreeSet` if no explicit `Comparator` is provided at construction?**
They must implement `Comparable` and be mutually comparable with each other — if you try to add an element whose class doesn't implement `Comparable` (or that throws when compared against existing elements, e.g., mixing genuinely incompatible types), a `ClassCastException` is thrown at the point of insertion, not at set-creation time.

**7. Why is it important to override both `equals()` and `hashCode()` consistently when adding custom objects to a `HashSet`?**
`HashSet` relies on `hashCode()` to pick a bucket and `equals()` to detect an exact duplicate within that bucket. If `equals()` is overridden for logical equality but `hashCode()` is left as the default (identity-based) implementation, two logically-equal custom objects can produce different hash codes, land in different buckets, and both get added as if they were distinct — silently violating the "no duplicates" guarantee the `Set` interface promises.

**8. What are `ceiling()`, `floor()`, `higher()`, and `lower()` on a `TreeSet`, and what's the difference between the "ceiling/floor" pair and the "higher/lower" pair?**
These `NavigableSet` methods find the closest element to a given value without an exact match being required. `ceiling(x)` returns the smallest element `>= x` (inclusive), `floor(x)` returns the largest element `<= x` (inclusive); `higher(x)` returns the smallest element strictly `> x` (exclusive), and `lower(x)` returns the largest element strictly `< x` (exclusive). All four return `null` if no such element exists.

**9. Between `HashSet`, `LinkedHashSet`, and `TreeSet`, which would you choose for a set that needs to display unique tags to a user in the exact order they were entered?**
`LinkedHashSet` — it provides the required uniqueness guarantee of any `Set` while additionally preserving insertion order for iteration, which `HashSet` explicitly does not guarantee and `TreeSet` would override with sorted (not insertion) order instead.

**10. Can two different `HashSet` instances containing the same elements (added in different orders) be considered `.equals()` to each other?**
Yes — `AbstractSet.equals()` (inherited by all standard `Set` implementations) is defined purely in terms of set membership: two sets are equal if they have the same size and every element of one is contained in the other, entirely independent of internal storage order. This is why `new HashSet<>(List.of(1,2,3)).equals(new HashSet<>(List.of(3,2,1)))` returns `true`.

**11. What's the time complexity of checking `contains()` on a `HashSet` versus a `TreeSet`, and when might you accept the slower `TreeSet` performance anyway?**
`HashSet.contains()` is O(1) on average; `TreeSet.contains()` is O(log n). You'd accept the `TreeSet` trade-off when you also need the set to remain continuously sorted for other operations — like retrieving the minimum/maximum element, performing range queries (`subSet`, `headSet`, `tailSet`), or iterating elements in sorted order — since achieving the same result with a `HashSet` would require an explicit, potentially expensive sort every time it's needed.
