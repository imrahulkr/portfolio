## Three Major JVM Subsystems

The JVM has three broad subsystems working together to run your program: the **class loader subsystem** (loads `.class` files into memory), the **runtime data areas** (memory regions holding the program's data), and the **execution engine** (actually runs the bytecode).

![Diagram: JVM architecture overview showing Class Loader Subsystem feeding into Runtime Data Areas, with the Execution Engine reading from those areas to run bytecode](/diagrams/ch45-jvm-architecture-overview.svg)

## The Class Loader Subsystem

Loading a class happens in three phases: **Loading** (reading the `.class` file's bytecode into memory), **Linking** (verification, preparation of static fields with default values, and optional resolution of symbolic references), and **Initialization** (running static initializers and assigning actual static field values — this is when a static block from Chapter 14 actually executes).

### The Three Built-In Class Loaders and Delegation

```
Bootstrap Class Loader   (loads core java.* classes from the JDK itself, written in native code)
      ↑
Platform/Extension Class Loader   (loads classes from the JDK's extension mechanisms)
      ↑
Application (System) Class Loader   (loads YOUR application's classes from the classpath)
```

Class loading follows the **parent delegation model**: when asked to load a class, a class loader first delegates the request *up* to its parent, and only attempts to load the class itself if every ancestor fails to find it.

```java
ClassLoader loader = String.class.getClassLoader();
System.out.println(loader);   // null — String is loaded by the Bootstrap loader (represented as null in Java code)

ClassLoader appLoader = MyClass.class.getClassLoader();
System.out.println(appLoader);   // typically the Application class loader
```

**Why delegation matters for security:** it prevents a malicious application-level class from shadowing/replacing a core JDK class like `java.lang.String` — since the Bootstrap loader is always consulted first (via delegation) and already has `String` loaded, an application-defined class named `java.lang.String` would never actually be used in place of the real one for classes loaded through the normal delegation chain.

![Diagram: parent delegation model showing a class-loading request from the Application loader delegating up to Platform, then Bootstrap, before falling back down if not found](/diagrams/ch45-classloader-delegation-model.svg)

## Runtime Data Areas

- **Method Area (Metaspace since Java 8)** — stores per-class structure: runtime constant pool, field/method data, static variables, and method bytecode. Shared across all threads.
- **Heap** — stores all objects and arrays. Shared across all threads; this is where the garbage collector (Chapter 46) does its work.
- **Stack** — one per thread; stores stack frames, each containing local variables and partial results for a single method invocation. Never shared between threads.
- **PC (Program Counter) Register** — one per thread; tracks the address of the currently-executing bytecode instruction.
- **Native Method Stack** — supports execution of native (non-Java, typically C/C++) methods invoked via JNI.

(Chapter 47 covers the heap/stack/metaspace distinction in much more practical detail, including common `OutOfMemoryError`/`StackOverflowError` scenarios.)

## The Execution Engine

- **Interpreter** — executes bytecode instruction-by-instruction, starting immediately with no compilation delay, but relatively slow for repeated execution.
- **JIT (Just-In-Time) Compiler** — identifies "hot" methods (called frequently) and compiles them directly to native machine code, dramatically speeding up their subsequent execution (detailed further in Chapter 48).
- **Garbage Collector** — reclaims heap memory occupied by objects no longer reachable by the running program (detailed in Chapter 46).

## `ClassNotFoundException` vs. `NoClassDefFoundError` Revisited

Building on the brief mention in Chapter 1: `ClassNotFoundException` is a checked exception thrown when code explicitly requests a class by name at runtime (via `Class.forName()` or a class loader's `loadClass()`) and it can't be found. `NoClassDefFoundError` is thrown when a class *was* present and successfully compiled against, but is missing from the classpath at the point the JVM actually tries to load and link it at runtime — a common symptom of a missing or mismatched dependency JAR.

## Key Takeaways

- Class loading proceeds through Loading, Linking, and Initialization phases, with the parent delegation model (Bootstrap → Platform → Application) providing security and consistency.
- The Method Area/Metaspace and Heap are shared across all threads; the Stack, PC Register, and Native Method Stack are each per-thread.
- The execution engine combines an interpreter (immediate execution) with a JIT compiler (native-code compilation for hot methods) and the garbage collector.
- Delegation prevents application code from shadowing core JDK classes, since ancestor loaders are always consulted first.

## Interview Questions

**1. What are the three main subsystems of the JVM, at a high level?**
The class loader subsystem, responsible for loading, linking, and initializing classes; the runtime data areas, the memory regions holding the program's classes, objects, and per-thread execution state; and the execution engine, which actually interprets/compiles and runs bytecode, including the garbage collector's memory management.

**2. What are the three phases of class loading, and what happens in each?**
Loading reads the class's bytecode from its `.class` file (or JAR, network location, etc.) into memory as a `Class` object. Linking consists of verification (checking bytecode safety, as covered in Chapter 1), preparation (allocating memory for static fields and setting them to their type's default values), and optional resolution (converting symbolic references to other classes into direct references). Initialization actually executes static initializer blocks and assigns the real values to static fields, which is also when the static blocks discussed in Chapter 14 run.

**3. What is the parent delegation model, and why does it matter for security?**
When a class loader is asked to load a class, it first delegates that request up to its parent class loader, and only attempts loading it itself if every ancestor in the chain fails to find it — meaning the Bootstrap loader is effectively always given first opportunity to load any class. This prevents malicious or accidental application-level classes from shadowing core JDK classes (like defining your own `java.lang.String`), since the trusted, already-loaded core class from the Bootstrap loader is always what's actually used for standard library types.

**4. What are the three built-in class loaders, from most to least privileged?**
The Bootstrap class loader (loads core `java.*`/`javax.*` classes from the JDK itself, implemented natively rather than as ordinary Java code, and represented as `null` when queried via `getClassLoader()`), the Platform (formerly Extension) class loader (loads certain platform/extension classes), and the Application (System) class loader (loads your own application's classes from the classpath).

**5. What's stored in the Method Area (Metaspace), and is it shared across threads?**
It stores per-class structural information: the runtime constant pool, field and method metadata, method bytecode itself, and static variables. Yes, it's shared across all threads in the JVM, since this data represents the class definitions themselves, which are the same regardless of which thread is executing code that uses them.

**6. Why does each thread have its own separate Stack, rather than sharing one Stack across all threads?**
Each thread executes its own independent sequence of method calls, and a stack frame represents the local variables and intermediate state of one specific method invocation on one specific call chain — sharing a single stack across multiple threads would make no sense, since each thread's sequence of nested method calls is entirely independent of every other thread's; per-thread stacks are what allow threads to execute concurrently without interfering with each other's local method state.

**7. What is the PC (Program Counter) Register, and why does each thread need its own?**
It tracks the memory address of the JVM instruction currently being executed by that specific thread. Since each thread can be at a completely different point in its own execution at any given moment (especially with the JVM freely context-switching between threads on limited CPU cores), each thread requires its own independent PC register to correctly resume exactly where it left off after being scheduled again.

**8. What's the difference between `ClassNotFoundException` and `NoClassDefFoundError` in terms of when and why each occurs?**
`ClassNotFoundException` is a checked exception thrown when code explicitly attempts to load a class by name at runtime (e.g., via `Class.forName("com.example.Foo")`) and no such class can be found on the classpath. `NoClassDefFoundError` occurs when a class was successfully available and referenced at *compile* time, but is missing from the classpath when the JVM actually attempts to load and link it at *runtime* — commonly caused by a required dependency JAR being absent or a mismatched version at deployment time, even though the code compiled successfully against it earlier.

**9. What role does the interpreter play in the JVM's execution engine, and why doesn't the JVM rely on it exclusively?**
The interpreter executes bytecode directly, instruction by instruction, allowing execution to begin immediately with no compilation delay — but this comes at the cost of significantly slower repeated execution compared to native machine code. The JVM avoids relying on interpretation exclusively by using the JIT compiler (Chapter 48) to identify and compile frequently-executed ("hot") methods into native machine code, combining fast startup (via interpretation) with strong steady-state performance (via JIT compilation) for long-running programs.

**10. If two different class loaders each load a class with the exact same fully-qualified name, are the resulting `Class` objects considered the same type by the JVM?**
No — a class's runtime identity in the JVM is actually determined by the combination of its fully-qualified name *and* the specific class loader instance that loaded it. Two classes with identical names loaded by two different class loaders are treated as entirely distinct, incompatible types — attempting to cast an instance of one to the other throws `ClassCastException`, even though their source code and name are identical. This is a subtle but important mechanism used deliberately by application servers and plugin systems for classloader isolation.

**11. What is `Class.forName()` typically used for, and how does it relate to the class loading phases discussed?**
It explicitly triggers the loading (and, depending on the overload used, initialization) of a class by its fully-qualified name at runtime, commonly used for dynamically loading JDBC drivers, plugins, or other classes whose specific identity isn't known until runtime. It throws the checked `ClassNotFoundException` if the named class cannot be located by the resolved class loader — directly tying back to the loading phase of class loading described earlier in this chapter.

**12. Why might understanding class loader delegation matter when debugging a "duplicate class" or classloading-related bug in a complex application (e.g., an application server hosting multiple deployed applications)?**
Application servers and similar environments often intentionally use custom, non-standard class loader hierarchies (sometimes deviating from strict parent-first delegation) to isolate different deployed applications' dependencies from each other, even when they share the same class names and versions. Understanding the delegation model — and recognizing that a class's true identity includes its loader — helps diagnose seemingly bizarre `ClassCastException`s or "class already loaded by a different loader" errors that only make sense once you consider which specific class loader actually loaded each conflicting class.
