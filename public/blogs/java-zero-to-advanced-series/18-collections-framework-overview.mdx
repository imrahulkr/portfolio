## Why a Unified Collections Framework

Before Java 2, ad-hoc classes like `Vector`, `Hashtable`, and raw arrays had inconsistent, incompatible APIs. The Collections Framework (`java.util`) unified them under a consistent set of interfaces, so algorithms and code written against `List` or `Map` work identically regardless of the concrete implementation chosen underneath.

## The Core Hierarchy

```
Iterable
   └── Collection
         ├── List    (ordered, allows duplicates, indexed access)
         ├── Set     (no duplicates)
         │     └── SortedSet → NavigableSet
         └── Queue   (FIFO-oriented processing)
               └── Deque (double-ended queue)

Map (NOT a Collection — separate hierarchy, key-value pairs)
   └── SortedMap → NavigableMap
```

![Diagram: full Collections Framework hierarchy tree — Iterable at top branching into Collection, which branches into List/Set/Queue, with Map shown as a separate parallel hierarchy not extending Collection](/diagrams/ch18-collections-hierarchy.svg)

**`Map` deliberately does not extend `Collection`** — a map's fundamental unit is a key-value pair, not a single element, so it doesn't fit the `Collection` contract (like `add(element)`) cleanly. It's an independent top-level interface, though `Map.keySet()`, `Map.values()`, and `Map.entrySet()` each expose collection *views* over parts of the map.

## The Four Core Interfaces at a Glance

- **`List`** — an ordered sequence, duplicates allowed, indexed access (`get(i)`). Think: a shopping cart where order and repeats matter.
- **`Set`** — no duplicate elements, generally unordered (except `LinkedHashSet`/`TreeSet`). Think: a collection of unique tags.
- **`Queue`** — designed for holding elements prior to processing, typically FIFO. Think: a print job queue.
- **`Map`** — associates unique keys with values, not a `Collection` itself. Think: a phone book (name → number).

```java
List<String> names = new ArrayList<>();      // ordered, duplicates OK
Set<String> uniqueTags = new HashSet<>();    // no duplicates
Queue<String> tasks = new LinkedList<>();    // FIFO processing
Map<String, Integer> ages = new HashMap<>(); // key -> value
```

## Choosing the Right Implementation — Quick Guide

| Need | Reach for |
|---|---|
| Fast indexed access, occasional resize | `ArrayList` |
| Frequent insertion/removal at both ends | `ArrayDeque` |
| No duplicates, fastest lookup, no order guarantee | `HashSet` |
| No duplicates, insertion order preserved | `LinkedHashSet` |
| No duplicates, sorted order | `TreeSet` |
| Fastest key-value lookup, no order guarantee | `HashMap` |
| Key-value with insertion order preserved | `LinkedHashMap` |
| Key-value sorted by key | `TreeMap` |
| FIFO task processing | `ArrayDeque` (preferred over legacy `LinkedList` for queue use) |

Detailed trade-offs and internals for each of these are covered in Chapters 19–22.

## Immutable Collections (Java 9+)

`List.of(...)`, `Set.of(...)`, and `Map.of(...)` create genuinely immutable collections — any attempted mutation throws `UnsupportedOperationException`, unlike `Collections.unmodifiableList()`, which merely wraps a *view* over a still-mutable backing list that can change out from under you if the original reference is modified elsewhere.

```java
List<String> immutable = List.of("a", "b", "c");
// immutable.add("d");   // UnsupportedOperationException

List<String> mutable = new ArrayList<>(List.of("a", "b"));  // copy into a mutable list if needed
```

## Key Takeaways

- `Collection` unifies `List`, `Set`, and `Queue` under one contract; `Map` is intentionally separate.
- `List` allows duplicates and preserves order; `Set` forbids duplicates; `Queue`/`Deque` are processing-order oriented.
- Choosing the right concrete implementation (Chapters 19–22) matters far more for performance than which interface you program against.
- `List.of()`/`Set.of()`/`Map.of()` (Java 9+) create truly immutable collections, distinct from mutable-but-wrapped "unmodifiable" views.

## Interview Questions

**1. Why doesn't `Map` extend the `Collection` interface, even though it's clearly part of the Collections Framework?**
`Collection`'s contract is built around holding individual elements (`add(E element)`, `contains(Object o)`, iterating single elements), but a `Map`'s fundamental unit is a key-value *pair*, which doesn't map cleanly onto that single-element contract. Rather than forcing an awkward fit, `Map` is defined as its own top-level interface, while still offering collection-based *views* of its contents via `keySet()`, `values()`, and `entrySet()`.

**2. What's the core distinguishing characteristic of `List` versus `Set`?**
`List` is an ordered sequence that permits duplicate elements and supports indexed access (`get(index)`). `Set` explicitly forbids duplicate elements (adding an element already present has no effect) and, depending on implementation, may or may not maintain any particular order.

**3. What does `Iterable` provide, and how does it relate to `Collection`?**
`Iterable` is the root interface requiring a single method, `iterator()`, which is what makes an object usable in a for-each loop. `Collection` extends `Iterable` and adds the broader contract of a group of elements — `add`, `remove`, `size`, `contains`, and so on — so every `Collection` is inherently for-each-loop-compatible, but not everything `Iterable` is necessarily a full `Collection` (a custom data structure could implement just `Iterable` without the rest of the `Collection` contract).

**4. What's the practical difference between `Collections.unmodifiableList()` and `List.of()`?**
`Collections.unmodifiableList(list)` returns a read-only *view* wrapping the original mutable list — attempts to modify through the view throw `UnsupportedOperationException`, but if the original underlying list is modified directly (through a reference the wrapping code still holds), those changes are visible through the view, since it's not truly independent or immutable. `List.of(...)` (Java 9+) creates a genuinely immutable collection with its own fixed internal storage — there's no mutable backing list anywhere that could change out from under it.

**5. Why might you choose `Set` over `List` even if you don't currently have duplicate data?**
Choosing `Set` communicates and enforces an intent — that duplicates are conceptually meaningless or invalid for this data — at the type level, so future code (including your own) can't accidentally introduce duplicates without it being flagged by the collection's own behavior. It can also offer better lookup performance (`contains()` is typically O(1) for `HashSet` versus O(n) for `ArrayList`) when uniqueness checking is a common operation.

**6. What does the `Queue` interface represent conceptually, and what's a common gotcha with using `LinkedList` as a `Queue`?**
`Queue` models a collection designed for holding elements prior to processing, typically in FIFO order, with dedicated methods like `offer()`, `poll()`, and `peek()` that behave predictably (returning `null`/`false` rather than throwing) when the queue is empty or full. A common gotcha is that `LinkedList` implements both `List` and `Deque`/`Queue`, which can lead to confusion about which contract's method behavior (`remove()` throwing versus `poll()` returning null on empty) applies — `ArrayDeque` is generally preferred today as a cleaner, more efficient queue/stack implementation with no such dual-interface ambiguity.

**7. What is the significance of choosing to program against the `List`/`Set`/`Map` interface type rather than a concrete class like `ArrayList`/`HashSet`/`HashMap` in method signatures and field declarations?**
It decouples calling code from the specific implementation, so the implementation can later be swapped (e.g., `ArrayList` to `LinkedList`, or `HashMap` to `LinkedHashMap`) without touching any code that only relies on the interface's contract — this is a direct application of "program to an interface, not an implementation," a core object-oriented design principle also relevant to the SOLID principles covered in Chapter 57.

**8. What does a `NavigableSet`/`NavigableMap` add on top of `SortedSet`/`SortedMap`?**
`SortedSet`/`SortedMap` guarantee elements/keys are maintained in sorted order and provide basic range views (`headSet`, `tailSet`, `subSet`). `NavigableSet`/`NavigableMap` (implemented by `TreeSet`/`TreeMap`) extend that further with methods for finding the closest match relative to a given value — `floor()`, `ceiling()`, `higher()`, `lower()` — and support traversing the set/map in descending order directly.

**9. Are all collections in `java.util` thread-safe by default?**
No — the standard implementations (`ArrayList`, `HashMap`, `HashSet`, etc.) are explicitly **not** thread-safe, and concurrent modification from multiple threads without external synchronization can corrupt internal state or throw `ConcurrentModificationException`. Thread-safe alternatives exist separately, either as legacy synchronized wrappers (`Collections.synchronizedList(...)`) or as purpose-built concurrent collections (`ConcurrentHashMap`, `CopyOnWriteArrayList`), covered in Chapter 41.

**10. Why does the Collections Framework provide multiple implementations of the same interface (e.g., three implementations of `Set`) instead of one "best" implementation?**
Because different underlying data structures make fundamentally different trade-offs — `HashSet` optimizes for fastest average-case lookup at the cost of no ordering guarantee, `LinkedHashSet` adds predictable insertion-order iteration at a small extra memory/time cost, and `TreeSet` guarantees sorted order at the cost of O(log n) rather than O(1) average operations. No single implementation can be optimal for every use case simultaneously, so the framework exposes the choice explicitly.

**11. What's the difference between the `Collection` interface's `add()` throwing `UnsupportedOperationException` on an immutable list, versus a `null` element check throwing `NullPointerException`?**
`UnsupportedOperationException` signals that the operation itself isn't permitted on this particular collection instance at all (regardless of what you're trying to add), such as with `List.of(...)`'s immutable implementation. `NullPointerException` in this context would instead signal that a specific implementation doesn't permit `null` elements at all (several `List.of(...)` and `Map.of(...)` implementations explicitly reject `null` arguments outright, throwing `NullPointerException` even before the immutability question is relevant), which is a distinct restriction from general mutability.
