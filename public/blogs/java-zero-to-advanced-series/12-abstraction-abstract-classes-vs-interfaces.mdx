## Abstraction: Defining What, Not How

Abstraction means exposing *what* an object can do while hiding *how* it does it. Java gives you two mechanisms: **abstract classes** and **interfaces**. They overlap in purpose but differ significantly in what they allow.

## Abstract Classes

An abstract class cannot be instantiated directly and can mix fully-implemented methods with abstract (unimplemented) ones that subclasses must provide.

```java
public abstract class Shape {
    protected String name;

    public Shape(String name) {
        this.name = name;
    }

    public abstract double area();   // no body — subclasses must implement

    public void describe() {          // concrete method — shared by all subclasses
        System.out.println(name + " has area " + area());
    }
}

public class Circle extends Shape {
    private final double radius;

    public Circle(double radius) {
        super("Circle");
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

```java
// Shape s = new Shape("generic"); // COMPILE ERROR — cannot instantiate abstract class
Shape s = new Circle(5.0);
s.describe();   // Circle has area 78.53...
```

## Interfaces

An interface defines a contract — a set of methods implementing classes must provide — without (traditionally) any implementation or state of its own.

```java
public interface Flyable {
    void fly();
}

public interface Swimmable {
    void swim();
}

public class Duck implements Flyable, Swimmable {
    @Override
    public void fly() { System.out.println("Duck flying"); }

    @Override
    public void swim() { System.out.println("Duck swimming"); }
}
```

A class can implement **any number** of interfaces — this is Java's answer to multiple inheritance of type, sidestepping the diamond problem since interfaces (traditionally) carry no state and no conflicting concrete implementations.

## Default and Static Interface Methods (Java 8+)

Interfaces can now include actual implementations via `default` and `static` methods, which let library designers add new methods to an interface without breaking every existing implementing class.

```java
public interface Vehicle {
    void start();

    default void honk() {              // default method — has a body
        System.out.println("Beep beep!");
    }

    static Vehicle basicVehicle() {    // static method — belongs to the interface itself
        return () -> System.out.println("Generic vehicle starting");
    }
}
```

If a class implements two interfaces that both provide a *default* method with the same signature, the class **must** override that method itself to resolve the conflict explicitly — the compiler refuses to guess which default to inherit.

## Functional Interfaces

An interface with exactly one abstract method is a **functional interface**, eligible for lambda expressions (full treatment in Chapter 32).

```java
@FunctionalInterface
public interface Calculator {
    int calculate(int a, int b);
}

Calculator add = (a, b) -> a + b;
System.out.println(add.calculate(3, 4));   // 7
```

The `@FunctionalInterface` annotation isn't required, but like `@Override`, it should always be used — it makes the compiler enforce that the interface has exactly one abstract method, catching accidental additions that would break lambda compatibility.

## Choosing Between Them

| | Abstract Class | Interface |
|---|---|---|
| Instance fields with state | ✅ Yes | ❌ No (only `public static final` constants) |
| Constructors | ✅ Yes | ❌ No |
| Multiple inheritance | ❌ One superclass only | ✅ A class can implement many |
| Non-public members | ✅ Yes | Limited (private interface methods since Java 9, for internal helper use only) |
| Best for | A shared base with common state/behavior across closely related types | A capability/contract that unrelated types can all fulfill |

A common guideline: use an abstract class when subclasses share substantial common state and implementation ("is-a" with shared internals); use an interface when you're defining a capability that many otherwise-unrelated classes should be able to implement (`Comparable`, `Runnable`, `Serializable`).

## Key Takeaways

- Abstract classes support shared state and single inheritance; interfaces support multiple implementation and pure contracts.
- Default and static interface methods (Java 8+) let interfaces evolve without breaking existing implementers.
- A functional interface has exactly one abstract method and can be implemented with a lambda.
- Choose abstract classes for closely related types sharing implementation; choose interfaces for capabilities unrelated types can all fulfill.

## Interview Questions

**1. What's the core difference between an abstract class and an interface?**
An abstract class can hold instance state, constructors, and a mix of fully-implemented and abstract methods, but a class can only extend one abstract class. An interface traditionally defines a pure contract of method signatures (now also allowing default/static implementations since Java 8), holds no instance state, and a class can implement any number of interfaces simultaneously.

**2. Can you instantiate an abstract class directly?**
No — attempting `new AbstractClassName()` is a compile-time error, even if the abstract class has no abstract methods left unimplemented. It can only be instantiated indirectly, through instantiating a concrete subclass that provides implementations for all its abstract methods.

**3. Can an abstract class have a constructor if it can never be instantiated directly?**
Yes, and this is a common point of confusion — the constructor exists so that concrete subclasses can call it via `super(...)` to initialize the inherited portion of the object's state. It's never invoked by `new` on the abstract class itself, only indirectly as part of a subclass's construction chain.

**4. What are default methods in interfaces, and what problem were they introduced to solve?**
Default methods (Java 8+) are interface methods with a concrete implementation, using the `default` keyword. They were introduced primarily to let library designers add new methods to widely-used interfaces (like adding `forEach` to `Collection`) without breaking every class that already implements that interface — existing implementers automatically inherit the default behavior instead of failing to compile.

**5. What happens if a class implements two interfaces that each define a conflicting default method with the same signature?**
The compiler forces the implementing class to override that method explicitly and resolve the conflict itself — it will not silently pick one interface's default over the other. Inside the override, the class can still explicitly choose one of the parent defaults using `InterfaceName.super.methodName(...)` syntax if desired.

**6. Can an interface have static methods, and how are they different from default methods?**
Yes, since Java 8. Static interface methods belong to the interface itself and are called via `InterfaceName.methodName()`, not inherited by implementing classes — they're typically used for factory methods or utility logic related to the interface, similar to static methods on a regular class.

**7. Can interfaces hold fields? What's special about fields declared in an interface?**
Any field declared in an interface is implicitly `public static final` — a compile-time constant — regardless of whether you write those modifiers explicitly. Interfaces cannot hold genuine instance state, since they have no constructors and no object of their own to store per-instance data on.

**8. What is a functional interface, and what's the significance of exactly one abstract method?**
It's an interface with precisely one abstract method (default and static methods don't count toward this total). That single-abstract-method constraint is exactly what makes a lambda expression usable in its place, since a lambda's parameter list and body map unambiguously onto that one method's signature — if there were two abstract methods, the compiler couldn't know which one the lambda body is meant to implement.

**9. Why should you use `@FunctionalInterface` even though it isn't strictly required?**
It causes the compiler to verify the interface truly has only one abstract method, immediately flagging an error if someone later adds a second abstract method that would break every lambda expression currently implementing that interface — catching the mistake at the point it's introduced rather than at every call site that fails to compile afterward.

**10. Can a class extend an abstract class and implement interfaces at the same time?**
Yes — a class can have at most one `extends` clause (for a superclass, abstract or not) alongside any number of `implements` clauses for interfaces, e.g., `class Duck extends Bird implements Flyable, Swimmable`.

**11. Why can Java support "multiple inheritance" through interfaces but not through classes?**
Because interfaces (even with default methods) don't carry per-instance state, and any default-method conflicts between multiple implemented interfaces must be explicitly resolved by the implementing class rather than being silently inherited — this eliminates the ambiguity (the "diamond problem") that arises with genuine multiple inheritance of stateful implementation from multiple parent classes.

**12. When would you choose an abstract class over an interface, given that interfaces can now also provide default implementations?**
When the related types genuinely share significant common state (fields) and constructor-driven initialization logic, not just behavior — interfaces still cannot hold instance fields or constructors, so any shared *state* (not just shared method bodies) forces you toward an abstract class regardless of how capable interfaces have become.

**13. Are private methods allowed in interfaces? What are they used for?**
Yes, since Java 9. Private interface methods (and private static interface methods) exist purely to let default/static methods within the same interface share common helper logic without exposing that helper as part of the interface's public contract — implementing classes cannot see or call them at all.
