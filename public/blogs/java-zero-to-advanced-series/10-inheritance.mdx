## What Inheritance Models

Inheritance lets a class (the subclass/child) acquire the fields and methods of another class (the superclass/parent), modeling an **is-a** relationship: a `Dog` is an `Animal`, a `SavingsAccount` is a `BankAccount`.

```java
public class Animal {
    protected String name;

    public Animal(String name) {
        this.name = name;
    }

    public void eat() {
        System.out.println(name + " is eating");
    }
}

public class Dog extends Animal {
    public Dog(String name) {
        super(name);
    }

    public void bark() {
        System.out.println(name + " says Woof!");
    }
}
```

```java
Dog d = new Dog("Rex");
d.eat();   // inherited from Animal
d.bark();  // defined in Dog
```

`Dog` automatically gets `eat()` and the `name` field without redeclaring them — it only adds what's genuinely new to being a dog.

## Single Inheritance for Classes

A Java class can `extend` **exactly one** superclass — Java does not support multiple class inheritance, unlike C++. This avoids the "diamond problem" (ambiguity when two parent classes define conflicting members). Interfaces, covered in Chapter 12, are how Java achieves a form of multiple inheritance instead, since a class can implement many interfaces.

```java
public class Dog extends Animal { }         // OK — one superclass
// public class Dog extends Animal, Pet { }  // COMPILE ERROR — not allowed
```

Every class that doesn't explicitly extend anything implicitly extends `java.lang.Object` — so all classes ultimately share a single root of the inheritance tree.

## Overriding vs. Hiding

Instance methods can be **overridden** by a subclass to provide a specialized implementation, using the same signature:

```java
public class Animal {
    public void makeSound() {
        System.out.println("Some generic sound");
    }
}

public class Dog extends Animal {
    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}
```

The `@Override` annotation isn't required by the compiler, but it should always be used — it makes the compiler verify you actually matched a real superclass method signature, catching typos that would otherwise silently create an unrelated overload instead of an override. (Method overriding and its runtime dispatch mechanics are covered in full in Chapter 11 on polymorphism.)

## `protected` Members and Inheritance

`protected` exists specifically to expose members to subclasses (including those in other packages) while still hiding them from unrelated external code — this is why `Animal.name` above is `protected` rather than `private`: `Dog` needs direct access to it.

## Composition as an Alternative

Not every relationship should be modeled with inheritance. **Composition** ("has-a") — where a class holds a reference to another class as a field, rather than extending it — is often more flexible:

```java
public class Engine {
    public void start() { System.out.println("Engine starting"); }
}

public class Car {
    private final Engine engine = new Engine();   // Car HAS-A Engine, not IS-A Engine

    public void start() {
        engine.start();
    }
}
```

The well-known guideline "favor composition over inheritance" reflects that inheritance creates tight coupling to a superclass's implementation details, while composition lets you swap out the internal `Engine` for a different implementation without touching `Car`'s class hierarchy at all.

## Key Takeaways

- Inheritance models "is-a" relationships; a Java class can extend only one superclass directly.
- Every class implicitly extends `Object` if it doesn't extend anything else, unifying the type hierarchy.
- `protected` grants subclasses access that unrelated external classes don't get.
- Composition ("has-a") is often more flexible than inheritance and should be considered as the default choice unless "is-a" genuinely holds.

## Interview Questions

**1. What relationship does inheritance model, and how do you decide if it's appropriate for two classes?**
Inheritance models an "is-a" relationship — a subclass should genuinely be a more specific kind of the superclass, such that every operation valid on the superclass is also valid (and semantically sensible) on the subclass. If the relationship is really "has-a" or "uses-a" (a `Car` has an `Engine`, but a `Car` is not a kind of `Engine`), composition is the correct model instead.

**2. Why doesn't Java support multiple inheritance of classes?**
To avoid the "diamond problem" — ambiguity that arises when a class inherits from two parent classes that both define a member with the same signature, leaving it unclear which implementation should apply. Java sidesteps this entirely by allowing only single class inheritance, while still permitting a form of multiple inheritance of *type* (not implementation, prior to default methods) through interfaces, which a class can implement in any number.

**3. What does every Java class implicitly extend if it doesn't explicitly extend anything?**
`java.lang.Object` — every class in Java, whether it declares `extends` or not, ultimately inherits from `Object`, which is why every object has access to methods like `equals()`, `hashCode()`, and `toString()` even if their own class hierarchy never defines them (covered in Chapter 13).

**4. What is the difference between `protected` and `private` in the context of inheritance?**
A `private` member is accessible only within the exact class that declares it — not even a direct subclass can access it by name (though it's still technically present in the subclass's memory layout and reachable indirectly through inherited public/protected methods). A `protected` member is accessible to subclasses, including those in different packages, making it the appropriate choice for fields/methods a superclass wants to expose specifically for subclass use without making them fully public.

**5. What is method overriding, and what must be true about the subclass method's signature?**
Overriding means a subclass provides its own implementation for a method already defined in its superclass, replacing that behavior when called on a subclass instance. The overriding method must have the same method name, same parameter types (and count/order), and a covariant or identical return type; it also cannot reduce the visibility of the overridden method (e.g., can't override a `public` method as `protected`).

**6. Why should `@Override` always be used even though it's technically optional?**
Without it, a typo in the method signature (wrong parameter type, misspelled name) silently creates an unrelated overload in the subclass rather than an actual override — the code compiles fine but behaves incorrectly at runtime, since the intended override never actually takes effect. `@Override` makes the compiler verify a genuine superclass (or interface) method is being overridden, turning that mistake into an immediate compile error.

**7. Can a subclass access a `private` field of its superclass directly?**
No — `private` members are not inherited in the sense of being directly name-accessible from the subclass; they exist in memory as part of the object but can only be accessed through whatever `public`/`protected` methods the superclass itself exposes (like getters), if any.

**8. What is the "favor composition over inheritance" principle, and why is it widely recommended?**
It suggests defaulting to building classes by holding references to other objects (composition) rather than extending them, unless a genuine "is-a" relationship exists. Composition avoids the tight coupling that inheritance creates to a superclass's exact implementation and change history — a subtle change to superclass internals can silently break subclasses in ways that are hard to trace, whereas swapping a composed dependency is explicit and localized.

**9. Can constructors be inherited in Java?**
No — constructors are never inherited by subclasses. A subclass must define its own constructors, though those constructors are required to invoke a superclass constructor (explicitly via `super(...)` or implicitly) as their first action, effectively reusing the superclass's initialization logic without literally inheriting the constructor itself.

**10. What happens if a subclass doesn't override a superclass method at all?**
Calling that method on a subclass instance simply executes the superclass's implementation unchanged — inheritance means the subclass automatically has access to and behaves according to every non-private superclass method it doesn't explicitly override.

**11. Is it possible to prevent a class from being subclassed at all in Java? How?**
Yes — declaring a class `final` prevents any class from extending it. This is often done for immutable classes (like `String`) or security-sensitive classes, where allowing subclassing could let a malicious or buggy subclass violate assumptions the class depends on, such as immutability guarantees.

**12. What's the difference between "is-a" and "has-a" relationships, with an example of each involving a `Car`?**
"Is-a" implies substitutability — a `SportsCar` is-a `Car`, meaning anywhere a `Car` is expected, a `SportsCar` should work correctly too, which is what inheritance should model. "Has-a" implies ownership/composition without substitutability — a `Car` has-a `Engine`, but a `Car` cannot be used wherever an `Engine` is expected, so this relationship should be modeled by `Car` holding an `Engine` field, not by `Car` extending `Engine`.
