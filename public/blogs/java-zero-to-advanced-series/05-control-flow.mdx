## if / else if / else

```java
int score = 82;

if (score >= 90) {
    System.out.println("A");
} else if (score >= 80) {
    System.out.println("B");
} else {
    System.out.println("C or below");
}
```

Java has no implicit truthiness — the condition must be a `boolean` expression. `if (x)` where `x` is an `int` is a compile error, unlike C or JavaScript.

## switch: Traditional vs. Modern (Java 14+)

The traditional `switch` statement suffers from **fall-through**: without an explicit `break`, execution continues into the next case.

```java
// Traditional — fall-through risk
switch (day) {
    case MONDAY:
    case TUESDAY:
        System.out.println("Early week");
        break;
    case FRIDAY:
        System.out.println("Almost done");
        break;
    default:
        System.out.println("Midweek");
}
```

Java 14 introduced **switch expressions** with arrow syntax, which don't fall through and can directly produce a value (full syntax, including pattern matching on types, is covered in Chapter 51):

```java
String label = switch (day) {
    case MONDAY, TUESDAY -> "Early week";
    case FRIDAY -> "Almost done";
    default -> "Midweek";
};
```

Each arm executes only its own branch — no `break` needed, and no accidental fall-through.

## Loops: for, while, do-while

```java
// Classic for — best when you know the iteration count
for (int i = 0; i < 5; i++) {
    System.out.println(i);
}

// while — condition checked before each iteration
int count = 0;
while (count < 5) {
    System.out.println(count);
    count++;
}

// do-while — body runs at least once, condition checked after
int attempts = 0;
do {
    attempts++;
} while (attempts < 3);
```

## Enhanced for (for-each)

```java
int[] scores = {90, 85, 77};
for (int score : scores) {
    System.out.println(score);
}
```

The enhanced for works on arrays and anything implementing `Iterable` (all standard collections). It's simpler but gives you no index and no way to modify the underlying collection structurally during iteration (doing so throws `ConcurrentModificationException` — covered in Chapter 24).

## Labeled break and continue

Labels let you control an **outer** loop from within a nested one — otherwise `break`/`continue` only affect the innermost loop.

```java
outer:
for (int i = 0; i < 3; i++) {
    for (int j = 0; j < 3; j++) {
        if (j == 1) {
            continue outer;   // skips to the next i, not just the next j
        }
        System.out.println(i + "," + j);
    }
}
```

## Key Takeaways

- Java conditions must be genuine `boolean` expressions — no implicit truthiness.
- Traditional `switch` falls through by default; the modern arrow-based switch expression does not and can directly yield a value.
- `do-while` guarantees at least one execution of the loop body; `while`/`for` do not.
- Labeled `break`/`continue` control an outer loop from inside a nested one — use sparingly, as it can hurt readability.

## Interview Questions

**1. Why doesn't `if (x)` compile in Java when `x` is an `int`, unlike in C or JavaScript?**
Java requires the condition of an `if` statement to be exactly type `boolean` — there's no implicit conversion from numeric or reference types to boolean ("truthiness"). This is a deliberate design choice to eliminate a common class of bugs, like accidentally writing `if (x = 5)` (assignment) instead of `if (x == 5)` (comparison), which would silently compile in C.

**2. What is fall-through in a traditional `switch` statement, and how do you prevent it?**
Fall-through means that once a matching `case` label is found, execution continues into subsequent `case` blocks regardless of whether their labels match, until a `break` (or the end of the switch) is reached. You prevent it by adding an explicit `break` at the end of each case, or by using the modern arrow-based switch expression (`->`), which never falls through by design.

**3. What's the difference between a `switch` statement and a `switch` expression?**
A `switch` statement executes code as a control-flow construct and produces no value itself. A `switch` expression (Java 14+) evaluates to a value that can be assigned or returned directly, uses arrow (`->`) syntax that doesn't fall through, and the compiler enforces exhaustiveness (all possible cases, or a `default`, must be covered).

**4. When would you choose a `do-while` loop over a `while` loop?**
When the loop body must execute at least once regardless of the condition — for example, prompting a user for input and validating it: you need to show the prompt once before you can even check if the input was valid. A `while` loop checks the condition before the first execution and may never run the body at all.

**5. What does the enhanced for-each loop do internally for a collection versus an array?**
For arrays, the compiler generates a standard indexed loop under the hood. For anything implementing `Iterable`, the compiler desugars it into calls to `iterator()`, `hasNext()`, and `next()` — meaning for-each on a collection is just syntactic sugar over the Iterator pattern (covered in depth in Chapter 24).

**6. Why can't you get the current index when using a for-each loop?**
Because for-each abstracts over anything `Iterable`, not just indexed structures — a `HashSet` or `LinkedList`, for instance, has no meaningful "index" concept the way an array does. If you need the index, use a classic indexed `for` loop, or track a manual counter alongside the for-each.

**7. What happens if you modify a `List` structurally (add/remove elements) while iterating over it with a for-each loop?**
It throws a `ConcurrentModificationException` at runtime, because the underlying `Iterator` detects the list's modification count changed unexpectedly between calls to `next()`. To remove elements safely during iteration, use `Iterator.remove()` directly, or collect items to remove and process them after the loop.

**8. What does a labeled `break` do differently from an unlabeled one in nested loops?**
An unlabeled `break` exits only the innermost loop it's directly inside. A labeled `break outerLabel;` exits the loop marked with that label entirely, even if it's several levels up in nesting — useful for escaping a deeply nested search once a condition is met, without extra boolean flags.

**9. Is it good practice to rely heavily on labeled break/continue?**
Generally, no — while legal and occasionally the clearest option for early-exit search logic across nested loops, overuse tends to hurt readability. Extracting the nested loops into a separate method and using a plain `return` to exit early is often a cleaner alternative that avoids labels altogether.

**10. What's the difference in evaluation order between `while` and `do-while` loops in terms of when the condition is checked?**
`while` checks the condition *before* executing the loop body each iteration, so if the condition is false initially, the body never runs. `do-while` checks the condition *after* executing the body, guaranteeing at least one execution regardless of the initial condition.

**11. Can a switch expression be exhaustive without a `default` case? Give an example.**
Yes, if the switch is over an `enum` and every enum constant is explicitly covered by a case, the compiler considers it exhaustive without requiring a `default`. This is one reason switch expressions pair especially well with enums and, from Java 21, with sealed class hierarchies (covered in Chapter 50) — the compiler can enforce that you've handled every possible case at compile time.
