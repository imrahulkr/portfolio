## The Four Core Interfaces in `java.util.function`

| Interface | Abstract Method | Purpose |
|---|---|---|
| `Predicate<T>` | `boolean test(T t)` | Tests a condition, returns true/false |
| `Function<T, R>` | `R apply(T t)` | Transforms input `T` into output `R` |
| `Supplier<T>` | `T get()` | Produces a value, takes no input |
| `Consumer<T>` | `void accept(T t)` | Consumes a value, returns nothing |

```java
Predicate<Integer> isEven = n -> n % 2 == 0;
System.out.println(isEven.test(4));   // true

Function<String, Integer> length = String::length;
System.out.println(length.apply("hello"));   // 5

Supplier<Double> randomValue = Math::random;
System.out.println(randomValue.get());   // some random double

Consumer<String> printer = System.out::println;
printer.accept("Hello!");   // prints "Hello!"
```

A useful way to remember them: **Predicate** asks a question, **Function** transforms, **Supplier** produces (no input), **Consumer** consumes (no output).

## `BiFunction`, `BiConsumer`, `BiPredicate` — Two-Argument Variants

```java
BiFunction<Integer, Integer, Integer> add = (a, b) -> a + b;
System.out.println(add.apply(3, 4));   // 7

BiConsumer<String, Integer> printPair = (name, age) -> System.out.println(name + ": " + age);
printPair.accept("Rahul", 30);
```

## `UnaryOperator` and `BinaryOperator` — Same-Type Specializations

When input and output types are identical, these narrower interfaces (extending `Function`/`BiFunction`) communicate intent more precisely.

```java
UnaryOperator<Integer> doubleIt = x -> x * 2;         // Function<Integer, Integer> specialized
BinaryOperator<Integer> max = (a, b) -> a > b ? a : b; // BiFunction<Integer, Integer, Integer> specialized
```

## Composing Functional Interfaces

Most of these interfaces provide default methods for combining multiple instances into one, avoiding manually nested lambda calls.

```java
// Function: andThen() runs AFTER, compose() runs BEFORE
Function<Integer, Integer> addOne = x -> x + 1;
Function<Integer, Integer> square = x -> x * x;

Function<Integer, Integer> addThenSquare = addOne.andThen(square);   // (x + 1)^2
System.out.println(addThenSquare.apply(3));   // (3+1)^2 = 16

Function<Integer, Integer> squareThenAdd = addOne.compose(square);   // x^2 + 1
System.out.println(squareThenAdd.apply(3));   // 3^2 + 1 = 10
```

```java
// Predicate: and(), or(), negate()
Predicate<Integer> isPositive = n -> n > 0;
Predicate<Integer> isEven = n -> n % 2 == 0;

Predicate<Integer> isPositiveAndEven = isPositive.and(isEven);
Predicate<Integer> isPositiveOrEven = isPositive.or(isEven);
Predicate<Integer> isNotPositive = isPositive.negate();
```

```java
// Consumer: andThen() chains multiple consumers on the same input
Consumer<String> print = System.out::println;
Consumer<String> log = s -> logToFile(s);

Consumer<String> printAndLog = print.andThen(log);
printAndLog.accept("event occurred");   // both actions run, in order
```

## Primitive Specializations — Avoiding Autoboxing Overhead

Using `Function<Integer, Integer>` for purely numeric operations forces autoboxing on every call. The JDK provides primitive-specialized variants specifically to avoid this cost.

```java
IntPredicate isEvenInt = n -> n % 2 == 0;         // no boxing — takes a raw int
IntFunction<String> intToString = n -> "Value: " + n;
ToIntFunction<String> stringLength = String::length;   // returns raw int, no boxing
IntSupplier randomInt = () -> new Random().nextInt(100);
IntUnaryOperator increment = n -> n + 1;
IntBinaryOperator addInts = (a, b) -> a + b;
```

These matter most in performance-sensitive code processing large volumes of primitive data — inside `IntStream` operations (Chapter 34/35), for example, using `IntPredicate` instead of `Predicate<Integer>` avoids boxing every single element.

## Key Takeaways

- `Predicate`, `Function`, `Supplier`, `Consumer` are the four foundational shapes: test, transform, produce, consume.
- `Function.andThen()`/`compose()` and `Predicate.and()`/`or()`/`negate()` let you build complex behavior from small, composable pieces.
- `UnaryOperator`/`BinaryOperator` communicate "same input and output type" more precisely than the generic `Function`/`BiFunction`.
- Primitive-specialized interfaces (`IntPredicate`, `ToIntFunction`, etc.) avoid autoboxing overhead in numeric-heavy code.

## Interview Questions

**1. What are the four foundational functional interfaces in `java.util.function`, and what does each represent?**
`Predicate<T>` tests a condition and returns a boolean. `Function<T, R>` transforms an input of type `T` into an output of type `R`. `Supplier<T>` takes no input and produces a value of type `T`. `Consumer<T>` takes an input of type `T` and returns nothing, typically performing a side effect with it.

**2. What's the difference between `Function.andThen()` and `Function.compose()`?**
Given `f.andThen(g)`, `g` is applied *after* `f` — the combined function computes `g(f(x))`. Given `f.compose(g)`, `g` is applied *before* `f` — the combined function computes `f(g(x))`. Both produce a new `Function` representing the pipeline, without needing to write nested calls by hand.

**3. What do `Predicate.and()`, `or()`, and `negate()` do?**
They combine predicates using standard boolean logic while returning new `Predicate` instances: `p1.and(p2)` is true only if both are true, `p1.or(p2)` is true if either is true, and `p1.negate()` inverts the result of `p1`. This lets you build complex conditions by composing small, independently-testable predicates rather than writing one large, monolithic boolean expression.

**4. What's the difference between `UnaryOperator<T>` and `Function<T, T>`?**
They're functionally identical in terms of behavior — `UnaryOperator<T>` actually extends `Function<T, T>` and adds no new abstract methods. The distinction is purely about communicating intent: `UnaryOperator<T>` signals explicitly, at the type level, that the input and output types are the same, which is clearer to a reader than the more general `Function<T, T>` for that specific same-type-transformation case.

**5. Why would you use `IntPredicate` instead of `Predicate<Integer>` in a performance-sensitive loop?**
`Predicate<Integer>` requires boxing every raw `int` value into an `Integer` object before it can be passed to `test()`, incurring allocation overhead on every single call in a tight loop. `IntPredicate` accepts a raw `int` parameter directly (`boolean test(int value)`), avoiding that autoboxing entirely, which can meaningfully improve performance when processing large volumes of primitive numeric data, such as inside `IntStream` pipelines.

**6. What is `BiFunction`, and when would you reach for it instead of `Function`?**
`BiFunction<T, U, R>` takes two input arguments (of potentially different types `T` and `U`) and produces a result of type `R`, unlike `Function<T, R>`'s single input. You'd use it whenever a lambda-based operation genuinely needs two independent inputs to compute its result, such as combining two values or comparing two arguments in a reduction operation.

**7. Can a lambda implement more than one of `Predicate`, `Function`, `Supplier`, or `Consumer` simultaneously?**
No — a single lambda instance implements exactly one specific functional interface, determined entirely by its target type at the point of assignment or use. However, the same lambda *expression syntax* could be written multiple times, each assigned to a different functional interface type, since the lambda itself carries no fixed type of its own until the compiler resolves it against a target context.

**8. What is `Consumer.andThen()` used for, and how does its composition differ conceptually from `Function.andThen()`?**
It chains two consumers so that both execute in sequence, given the exact same input value, purely for their side effects — unlike `Function.andThen()`, there's no "passing the result of the first into the second," since `Consumer` never produces a return value to pass along; both consumers simply act independently on the same original input, one after the other.

**9. Why does the JDK provide separate primitive-specialized interfaces like `IntFunction<R>`, `ToIntFunction<T>`, and `IntUnaryOperator`, rather than just one generic `IntFunction`?**
Each addresses a different combination of primitive and reference types to avoid boxing wherever possible: `IntFunction<R>` takes a raw `int` and returns a reference type `R`; `ToIntFunction<T>` takes a reference type `T` and returns a raw `int`; `IntUnaryOperator` takes and returns a raw `int` with no boxing on either side at all. Providing distinct interfaces for each shape lets the JDK avoid boxing wherever the actual data flow allows it, rather than forcing a single generic interface that would need boxing somewhere regardless of the specific use case.

**10. If you need a functional interface representing "takes three arguments and returns a result," does `java.util.function` provide one directly?**
No — the standard library only provides zero, one, and two-argument variants (`Supplier`, `Function`/`Predicate`/`Consumer`, `BiFunction`/`BiPredicate`/`BiConsumer`). For three or more arguments, you'd need to define your own custom functional interface, since there's no built-in `TriFunction` or similar in the JDK.

**11. What's the benefit of composing small `Predicate`/`Function` pieces with `and()`/`andThen()` rather than writing one large lambda that does everything inline?**
Each small predicate or function becomes independently named, testable, and reusable in different combinations, improving readability and reducing duplication — for example, `isActive.and(hasValidSubscription).and(isNotSuspended)` clearly documents each condition being checked, versus a single dense boolean expression mixing all three conditions inline with no individual names to anchor a reader's understanding.

**12. Why might overusing method chaining with many composed functional interfaces reduce debuggability compared to a straightforward imperative implementation?**
Stepping through a long chain of composed lambdas in a debugger can be harder to follow than a simple sequential method body, since stack traces and breakpoints on heavily-composed functional pipelines often show synthetic, less-informative frame names, and it can be less obvious at a glance which specific piece of the composition is executing at a given point — a trade-off worth weighing against the readability and reuse benefits composition otherwise provides, especially for particularly complex chains.
