## What Encapsulation Actually Buys You

Encapsulation means hiding an object's internal state and only allowing controlled access to it through a well-defined public interface (methods). The point isn't secrecy for its own sake — it's that the class can **enforce its own invariants**, because nothing outside the class can mutate its state in ways the class hasn't explicitly allowed.

```java
public class BankAccount {
    private double balance;   // hidden — cannot be touched directly from outside

    public BankAccount(double initialBalance) {
        if (initialBalance < 0) {
            throw new IllegalArgumentException("Initial balance cannot be negative");
        }
        this.balance = initialBalance;
    }

    public void withdraw(double amount) {
        if (amount > balance) {
            throw new IllegalStateException("Insufficient funds");
        }
        balance -= amount;
    }

    public double getBalance() {
        return balance;
    }
}
```

Without encapsulation (a public `balance` field), any code anywhere could set `account.balance = -500;` directly, bypassing every rule the class exists to enforce.

## The Four Access Modifiers

| Modifier | Same class | Same package | Subclass (different package) | Everywhere |
|---|---|---|---|---|
| `private` | ✅ | ❌ | ❌ | ❌ |
| *(default/package-private)* | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

```java
package com.example.account;

public class BankAccount {
    private double balance;          // only BankAccount itself
    String accountType;              // package-private — anything in com.example.account
    protected String branchCode;     // package + subclasses anywhere
    public String accountNumber;     // accessible from anywhere
}
```

A common convention: fields are almost always `private`; methods are `public` only when they're meant to be part of the class's external contract, and `private` when they're internal helper logic.

## Getters and Setters — With Judgment, Not by Default

```java
public class Employee {
    private String name;
    private int age;

    public String getName() {
        return name;
    }

    public void setAge(int age) {
        if (age < 18) {
            throw new IllegalArgumentException("Employee must be at least 18");
        }
        this.age = age;
    }
    // Deliberately no setName() — name is immutable after construction
}
```

A setter isn't required just because a getter exists. Exposing a setter for every private field defeats much of the purpose of encapsulation — it's exactly equivalent to a public field with extra ceremony. Only add a setter when mutation genuinely needs to be supported, and validate inside it.

## Defensive Copying for Mutable Fields

Encapsulation can leak through mutable objects (like arrays or `Date`) even when the field itself is `private`, if you hand out or accept a direct reference.

```java
public class Schedule {
    private final Date meetingTime;

    public Schedule(Date meetingTime) {
        this.meetingTime = new Date(meetingTime.getTime());  // defensive copy on the way in
    }

    public Date getMeetingTime() {
        return new Date(meetingTime.getTime());  // defensive copy on the way out
    }
}
```

Without these copies, external code holding the original `Date` reference — or the reference returned by the getter — could mutate `meetingTime` after the fact, silently breaking the object's encapsulation despite the field being `private`.

## Key Takeaways

- Encapsulation is about enforcing invariants through controlled access, not just hiding fields cosmetically.
- Access modifiers form a strict hierarchy: `private` < package-private < `protected` < `public`.
- Don't generate a setter for every field automatically — only expose mutation you actually intend to support, with validation.
- Mutable field types (arrays, `Date`, collections) need defensive copying on the way in and out to keep encapsulation intact.

## Interview Questions

**1. What is encapsulation, and why is it more than just "making fields private"?**
Encapsulation is bundling an object's state with the methods that operate on it, and restricting direct external access to that state so the object can enforce its own rules (invariants) about how it can change. Making a field `private` is the mechanism, but the actual benefit only materializes if the public methods that *do* expose access include real validation and controlled behavior — a class with a private field but a trivial public getter/setter pair for every field gains little over a public field.

**2. What are the four access modifiers in Java, ordered from least to most restrictive?**
From most restrictive to least: `private` (class only), package-private/default (no modifier — same package only), `protected` (same package plus subclasses anywhere), `public` (accessible from anywhere). Each level is a strict superset of the more restrictive one before it.

**3. What's the difference between `protected` and package-private (default) access?**
Package-private access is limited strictly to classes in the same package. `protected` extends that same package-level access and additionally allows subclasses in *other* packages to access the member (through inheritance), though even then, a subclass can typically only access a protected member through its own instance or subclass references, not through an arbitrary instance of the superclass from outside the package.

**4. Why is it generally bad practice to auto-generate a public getter and setter for every private field?**
Doing so effectively recreates a fully public field with extra method-call syntax, defeating the actual purpose of encapsulation — the class gains no ability to enforce invariants, since external code can still set any value it wants through the setter. A well-encapsulated class only exposes setters where mutation is genuinely intended, and validates inside them; fields that shouldn't change after construction should have no setter at all.

**5. What is a defensive copy, and when is it necessary?**
A defensive copy is creating an independent duplicate of a mutable object rather than storing or returning a direct reference to it. It's necessary whenever a class accepts a mutable object (like an array, `Date`, or a mutable custom type) in its constructor or setters, or returns one from a getter — without copying, external code holding the original reference (or the returned reference) can mutate the class's internal state from the outside, bypassing all of the class's own validation logic.

**6. Can a `private` member of a class be accessed by another class in the same file?**
No — `private` access is scoped strictly to the declaring class itself, regardless of whether other classes are defined in the same source file or even nested within it (with the notable exception of inner/nested classes, which do have special access to their enclosing class's private members — covered in Chapter 14).

**7. If a field has no access modifier at all, what is its visibility?**
It has package-private (default) access — visible to any class within the same package, but invisible to any class outside that package, including subclasses in other packages. This is distinct from, and more restrictive than, `protected`.

**8. How does encapsulation support the ability to change a class's internal implementation without breaking external code?**
Because external code interacts only with the class's public method contracts, not its internal field representations, the class is free to change *how* it stores or computes its state internally — swapping a `List` for a `Set`, or changing a computed field into a cached one — as long as the public method behavior and signatures remain the same. If fields were public, external code could depend directly on their exact type and structure, making any internal change a breaking change.

**9. What's an example of an invariant that encapsulation can enforce which a public field cannot?**
A `BankAccount.balance` field should never go negative. With `balance` private and only mutable through a `withdraw()` method that checks `amount <= balance` before subtracting, the class guarantees this invariant always holds. If `balance` were a public field, any external code could simply assign it a negative value directly, with no way for the class to prevent it.

**10. Why does returning a mutable field directly from a getter break encapsulation, even if the field itself is private?**
Because the caller receives the *actual reference* to the internal object, not a copy — any mutation the caller makes to that returned object (e.g., adding to a returned `List`) directly changes the class's own internal state, completely bypassing whatever validation the class's own methods would normally enforce on state changes.

**11. Is `protected` access considered part of a class's public API? Why does that matter for library design?**
Effectively yes, in the sense that any subclass anywhere (including in code you don't control, if your class is used as a library) can depend on `protected` members, and removing or changing them later is a breaking change just like removing a `public` member would be. This is why library authors are often just as conservative about widening access to `protected` as they are about `public`.

**12. What access modifier should constructors typically have if a class is meant to only be instantiated via a static factory method?**
`private` (or package-private if factory methods live in a companion class within the same package) — this prevents external code from calling `new` directly, forcing all instantiation through the designated factory method(s), which can then apply validation, caching, or return a subtype without external code needing to know the difference.
