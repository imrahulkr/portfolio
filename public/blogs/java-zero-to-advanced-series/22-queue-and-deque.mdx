## `Queue` — Two Method Families: Throwing vs. Returning a Sentinel

`Queue` deliberately offers two parallel sets of methods for the same operations — one throws an exception on failure, the other returns a special value (`null` or `false`).

| Operation | Throws exception | Returns sentinel value |
|---|---|---|
| Insert | `add(e)` | `offer(e)` |
| Remove | `remove()` | `poll()` |
| Examine | `element()` | `peek()` |

```java
Queue<String> queue = new LinkedList<>();
queue.offer("first");
queue.offer("second");

System.out.println(queue.poll());   // "first" — removes and returns the head
System.out.println(queue.peek());   // "second" — looks without removing

Queue<String> empty = new LinkedList<>();
empty.poll();      // returns null — no exception
// empty.remove(); // throws NoSuchElementException
```

Prefer the `offer`/`poll`/`peek` family for normal queue processing where an empty queue is an expected, ordinary condition rather than an error.

## `Deque` — Double-Ended Queue

A `Deque` (pronounced "deck") supports insertion and removal at **both** ends, making it capable of acting as a queue, a stack, or a genuine double-ended structure.

```java
Deque<Integer> deque = new ArrayDeque<>();
deque.addFirst(1);
deque.addLast(2);
deque.addFirst(0);
System.out.println(deque);   // [0, 1, 2]

deque.pollFirst();   // removes 0
deque.pollLast();    // removes 2
```

### Using `Deque` as a Stack (LIFO)

```java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);   // equivalent to addFirst
stack.push(2);
stack.push(3);
System.out.println(stack.pop());   // 3 — LIFO: last in, first out
```

`ArrayDeque` is explicitly the JDK-recommended replacement for the legacy `java.util.Stack` class (which, like `Vector` and `Hashtable`, is a synchronized, pre-Collections-Framework relic) — it's faster and has none of `Stack`'s unnecessary locking overhead.

![Diagram: ArrayDeque shown as a circular buffer array with head and tail pointers, supporting O(1) insertion/removal at both ends](/diagrams/ch22-arraydeque-circular-buffer.svg)

`ArrayDeque` is backed by a resizable circular array (not a linked structure), giving it better cache locality and lower per-element overhead than `LinkedList` for both queue and stack use — which is why the JDK documentation recommends `ArrayDeque` over `LinkedList` for both roles.

## `PriorityQueue` — Ordering by Priority, Not Insertion

`PriorityQueue` is backed internally by a **binary heap** (an array-based, complete binary tree structure), always keeping the smallest (or, with a custom `Comparator`, the "highest priority") element accessible in O(1) at the head, with O(log n) insertion and removal.

```java
Queue<Integer> minHeap = new PriorityQueue<>();
minHeap.offer(5);
minHeap.offer(1);
minHeap.offer(3);

System.out.println(minHeap.poll());   // 1 — smallest first
System.out.println(minHeap.poll());   // 3
System.out.println(minHeap.poll());   // 5
```

```java
// Max-heap using a custom Comparator
Queue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
maxHeap.offer(5);
maxHeap.offer(1);
maxHeap.offer(3);
System.out.println(maxHeap.poll());   // 5 — largest first
```

**Important gotcha:** iterating a `PriorityQueue` directly (via a for-each loop or its `Iterator`) does **not** visit elements in priority order — only repeated `poll()` calls guarantee sorted extraction. The internal array only guarantees the heap property (parent ≤ children for a min-heap), not a fully sorted layout.

## Key Takeaways

- Prefer the `offer`/`poll`/`peek` method family over `add`/`remove`/`element` for routine queue processing, since an empty queue isn't exceptional.
- `ArrayDeque` is the modern, recommended choice for both stack and queue use — faster than `LinkedList`, and a direct replacement for the legacy `Stack` class.
- `PriorityQueue` guarantees the minimum (or comparator-defined highest-priority) element is always at the head, but does *not* guarantee fully sorted iteration order.
- All of `Queue`, `Deque`, and `PriorityQueue` are, like most `java.util` collections, not thread-safe by default.

## Interview Questions

**1. What's the difference between `add()`/`remove()`/`element()` and `offer()`/`poll()`/`peek()` on a `Queue`?**
They perform the identical logical operations (insert, remove-and-return-head, examine-head), but differ in failure behavior: `add`/`remove`/`element` throw exceptions (`IllegalStateException` for a full bounded queue on `add`, `NoSuchElementException` for `remove`/`element` on an empty queue), while `offer`/`poll`/`peek` return a sentinel value instead (`false` for a failed `offer`, `null` for `poll`/`peek` on empty) — making them better suited for routine processing loops where an empty queue is an expected condition, not an error.

**2. Why is `ArrayDeque` recommended over both `LinkedList` and the legacy `Stack` class for stack/queue use?**
`ArrayDeque` is backed by a resizable circular array, giving it better cache locality and lower per-element memory overhead than `LinkedList`'s node-based structure, while offering the same O(1) amortized insertion/removal at both ends. Compared to the legacy `Stack` class, which extends `Vector` and inherits its full method-level synchronization, `ArrayDeque` has no such locking overhead at all, making it faster for the overwhelmingly common single-threaded case.

**3. How would you implement a LIFO stack using `Deque`, and which methods would you use?**
Use `push(e)` to add to the top (internally equivalent to `addFirst`) and `pop()` to remove and return the top element (internally equivalent to `removeFirst`), with `peek()` to examine the top without removing it — `Deque` provides these stack-oriented method names directly so the code reads naturally as stack usage rather than deque usage.

**4. What data structure backs `PriorityQueue`, and what specific ordering guarantee does it actually provide?**
A binary heap, stored internally as a plain array representing a complete binary tree. It guarantees that the element at the head (index 0 internally) is always the minimum according to natural ordering or a supplied `Comparator` — it does **not** guarantee that the rest of the internal array or an iteration over the whole queue is fully sorted; only repeated `poll()` calls extract elements in fully sorted order.

**5. Why does iterating a `PriorityQueue` with a for-each loop not produce elements in priority order?**
The heap property a binary heap maintains only guarantees that each parent node is `<=` (for a min-heap) its children — it says nothing about the relative order between sibling subtrees or non-adjacent nodes deeper in the tree. A for-each loop simply walks the underlying array in its raw storage order, which satisfies the heap property but is not a fully sorted sequence; only the repeated "remove the current minimum, let the heap re-settle" process that `poll()` performs guarantees fully sorted extraction.

**6. What is the time complexity of `PriorityQueue.offer()` and `PriorityQueue.poll()`, and why?**
Both are O(log n). `offer()` places the new element at the next open array slot then "sifts it up" the tree, swapping with its parent while it violates the heap property — at most the tree's height, O(log n), swaps. `poll()` removes the root, moves the last element into the root position, then "sifts it down," swapping with the smaller child while it violates the heap property — again at most O(log n) swaps.

**7. How do you create a max-heap using `PriorityQueue`, given that its natural default behavior is a min-heap?**
Supply `Comparator.reverseOrder()` (or an equivalent custom comparator that inverts the natural ordering) to the `PriorityQueue` constructor — `new PriorityQueue<>(Comparator.reverseOrder())` — which causes the heap's internal comparisons to treat "larger" values as higher priority, surfacing the maximum element at the head instead of the minimum.

**8. Is `PriorityQueue` thread-safe? What's the concurrent alternative if needed?**
No — like most standard `java.util` collections, `PriorityQueue` has no internal synchronization and is unsafe for uncoordinated concurrent access. `PriorityBlockingQueue` (in `java.util.concurrent`) provides a thread-safe, blocking-capable equivalent for producer-consumer scenarios across multiple threads.

**9. What's the practical difference between `Deque.offerFirst()`/`offerLast()` and `Deque.addFirst()`/`addLast()`?**
Functionally, for `ArrayDeque` specifically (which has no fixed capacity limit), they behave identically in practice since `ArrayDeque` grows as needed and never "fails" an insertion. The distinction matters for capacity-bounded `Deque` implementations, where `addFirst`/`addLast` throw `IllegalStateException` if the deque is full, while `offerFirst`/`offerLast` instead return `false` — following the same throwing-vs-sentinel pattern as the basic `Queue` methods.

**10. Why does the JDK documentation explicitly discourage using the legacy `Stack` class for new code?**
`Stack` extends `Vector` and therefore inherits full method-level synchronization on every operation, imposing locking overhead even in single-threaded code that never needs thread safety, and its API predates the Collections Framework's more consistent `Deque`-based design. `ArrayDeque` provides equivalent (and additional) stack functionality with better performance and no unnecessary synchronization, which is why it's the JDK's own recommended replacement.

**11. Can a `PriorityQueue` contain `null` elements?**
No — `PriorityQueue` throws `NullPointerException` on an attempt to insert `null`, because the heap must be able to compare every element against others to maintain heap order, and comparing against `null` has no defined meaning (much like the reasoning behind `TreeSet`/`TreeMap` rejecting `null` keys, covered in Chapters 20 and 21).
