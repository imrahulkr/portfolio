Chapter 37 covered a runtime scheduling improvement that requires no build changes. This chapter covers the opposite kind of optimization: changing *how the application is compiled entirely*, trading a significantly heavier build process for a dramatically different runtime startup profile.

## JIT compilation vs. ahead-of-time compilation

A normal Spring Boot JAR (everything through Chapter 35) runs on the JVM, which **interprets** bytecode initially and progressively **JIT-compiles** (Just-In-Time) the hottest code paths to native machine code as the application runs — this is why a JVM application's peak throughput is excellent, but why it takes some time after startup to reach that peak, and why startup itself involves real overhead (class loading, JIT warm-up).

**GraalVM native image** compiles the entire application — your code, Spring Boot, every dependency — into a single, standalone native executable **ahead of time**, at build time, with no JVM, no interpretation, and no warm-up needed at startup.

```
JVM (JIT):                              Native Image (AOT):
┌─────────────────────────┐            ┌─────────────────────────┐
│ Startup: load classes,     │            │ Startup: run the         │
│  interpret bytecode,       │            │  already-compiled         │
│  JIT-compile hot paths     │            │  native executable        │
│  (seconds)                 │            │  directly (milliseconds)  │
├─────────────────────────┤            ├─────────────────────────┤
│ Peak throughput: excellent, │            │ Peak throughput: good,    │
│  after JIT warm-up          │            │  but the JIT's runtime    │
│                            │            │  adaptive optimization    │
│                            │            │  never happens             │
└─────────────────────────┘            └─────────────────────────┘
```

## Building a native image

```xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
</plugin>
```

```bash
./mvnw -Pnative native:compile
```

```dockerfile
FROM ghcr.io/graalvm/native-image-community:21 AS builder
WORKDIR /app
COPY . .
RUN ./mvnw -Pnative native:compile

FROM debian:bookworm-slim
COPY --from=builder /app/target/demo /app/demo
ENTRYPOINT ["/app/demo"]
```

The resulting artifact isn't a JAR at all — it's a native, OS-specific executable, run directly with no `java -jar` involved. The build itself takes considerably longer (minutes, not seconds) than a normal JAR build, since the GraalVM compiler performs whole-program static analysis to determine everything the application could possibly need at runtime.

## Why the startup difference is so dramatic — and what it costs to get there

```
Typical Spring Boot JVM startup:    ~1.5–3 seconds
Typical Spring Boot native image:   ~0.05–0.1 seconds
```

This isn't a marginal improvement — it's roughly a 20–50x reduction in startup time, plus a substantial reduction in memory footprint (no JIT compiler running in the background, no bytecode interpretation machinery). This specifically matters for **serverless functions** (where startup time is often directly billed, and a cold start happens on every scale-to-zero event) and **rapid horizontal auto-scaling** (Chapter 35's `replicas` scaling out to meet a sudden traffic spike benefits enormously from new instances being ready in milliseconds rather than seconds).

The cost is the build process itself: GraalVM's static analysis needs to know, ahead of time, everything the application could possibly do — but Spring's extensive use of reflection (for `@Autowired`, JPA entity proxies, Jackson serialization) is fundamentally difficult for static analysis to fully see through, since reflective calls aren't visible in the same way direct method calls are.

## Reflection hints — closing the gap static analysis can't see

```json
// src/main/resources/META-INF/native-image/reflect-config.json
[
  {
    "name": "com.example.demo.Order",
    "allDeclaredFields": true,
    "allDeclaredMethods": true
  }
]
```

Spring Boot 3's native support (built on Spring's **AOT — Ahead-Of-Time — processing engine**) automatically generates most of these reflection hints during the build by analyzing the application context at build time, covering the overwhelming majority of standard Spring Boot usage without manual configuration. Manual hints like the one above become necessary specifically for less-common reflective usage the AOT engine's analysis doesn't automatically discover — a third-party library doing its own dynamic reflection, for instance.

```
Build time:
┌────────────────────────────────────────┐
│ Spring AOT engine analyzes the           │
│ ApplicationContext AT BUILD TIME          │
│ (not runtime!) and generates:             │
│  - reflection hints                       │
│  - proxy configuration                    │
│  - resource inclusion lists               │
└──────────────────┬───────────────────────┘
                    ▼
       GraalVM compiles everything into
       one native executable, using those hints
```

## Best practices & gotchas

- **Test the native image build early and often, not just before a release.** A reflection gap or an incompatible library discovered the day before a deployment is a much worse time to find it than during regular development.
- **Not every third-party library is native-image-compatible.** Libraries doing heavy, dynamic reflection or class-path scanning outside Spring's own AOT-aware mechanisms may need explicit hints, a compatible alternative library, or may simply not work correctly under native image at all — check compatibility before committing an architecture to it.
- **Native images trade a slower, heavier build for a faster runtime — this is the right trade specifically when startup time and memory footprint genuinely matter** (serverless, rapid autoscaling), and often not worth the added build complexity and reduced peak-throughput ceiling for a long-running, steady-state service where JVM warm-up cost is a one-time, insignificant fraction of total uptime.
- **Debugging a native image is meaningfully different from debugging a normal JVM application** — many familiar JVM diagnostic tools (certain profilers, some `jstack`/`jmap`-style tooling) don't work identically or at all against a native executable, which is a real operational cost to weigh.
- **This is not the default choice for most Spring Boot applications.** It's a deliberate, targeted optimization for a specific deployment profile — most of what this series has built (a typical, long-running microservice per Part 7) doesn't need it, and the standard JAR-plus-JVM approach from Chapter 35 remains entirely appropriate.

## Quick reference

| Concept | Summary |
|---|---|
| JIT compilation | JVM's runtime, progressive compilation of hot code paths |
| Ahead-of-time (AOT) compilation | Compiling the entire application to native code at build time |
| GraalVM native image | A standalone, OS-specific executable requiring no JVM at runtime |
| Spring AOT engine | Analyzes the application context at build time, generating most needed reflection hints automatically |
| Best fit | Serverless functions, rapid autoscaling — not general-purpose long-running services |

## Wrapping up

Native images are a genuinely powerful, narrowly-targeted optimization — dramatic startup and memory improvements for a real, added build-complexity cost, worthwhile specifically where cold-start time is a first-class concern. **Chapter 39** closes out the series' advanced topics with reactive programming and Spring WebFlux — the alternative concurrency model Chapter 37 repeatedly referenced without yet fully explaining.

## Interview Questions

**1. What's the fundamental difference between how a normal Spring Boot JAR runs and how a GraalVM native image runs?**
A normal JAR runs on the JVM, which interprets bytecode initially and progressively JIT-compiles frequently-executed code paths to native machine code *at runtime*, incurring startup and warm-up overhead but reaching excellent peak throughput once warmed up. A GraalVM native image is compiled entirely to native machine code *ahead of time*, at build time — the resulting executable requires no JVM, no interpretation, and no runtime warm-up at all, starting almost instantly, though without the JIT's ability to adaptively optimize based on actual runtime behavior.

*Follow-up: Why might a long-running, steady-state application actually reach higher sustained peak throughput on the JVM than the same application compiled as a native image?* The JVM's JIT compiler can perform runtime-adaptive optimizations based on the application's actual, observed execution patterns and hot paths during real operation — optimizations that can exceed what's determinable through purely static, ahead-of-time analysis, since the JIT has the benefit of real runtime profiling data a native image's build-time compilation process doesn't have access to; for an application that runs for a long time and reaches a stable, well-optimized steady state, this runtime-adaptive advantage can result in higher sustained peak throughput than an equivalent native image, even though the native image starts dramatically faster.

**2. Why does GraalVM's ahead-of-time compilation struggle specifically with Spring's extensive use of reflection?**
Ahead-of-time static analysis needs to determine, at build time, everything the application could possibly do at runtime — but reflective calls (like Spring's `@Autowired` dependency injection, JPA's dynamic proxy generation, or Jackson's field/method introspection for serialization) aren't visible to static analysis the same way direct, explicit method calls are, since reflection determines *what to call* dynamically at runtime based on class metadata rather than being hardcoded into the compiled bytecode in an obviously analyzable way — this makes it fundamentally harder for a static analyzer to correctly and completely determine everything reflection might need access to ahead of time.

*Follow-up: How does this connect to Spring's own architectural reliance on annotations and dependency injection, a pattern established as early as Chapter 2 of this series?* Chapter 2 established that `@Component`/`@Autowired`-based dependency injection and Spring's broader use of annotations for configuration (Chapters 4–5) is fundamentally built on reflection-based mechanisms under the hood — the very feature that makes Spring Boot so convenient and low-boilerplate to use is precisely the feature that creates the most friction for ahead-of-time native compilation, which is exactly why Spring needed to build a dedicated AOT processing engine specifically to bridge this gap, rather than native image support simply working automatically with no additional Spring-side effort.

**3. What is Spring's AOT (Ahead-Of-Time) processing engine, and what does it do at build time?**
It's Spring's own build-time analysis engine that inspects the application's `ApplicationContext` — the beans, their configuration, and how they're wired together — and automatically generates the reflection hints, proxy configuration, and resource-inclusion metadata that GraalVM's native image compiler needs in order to correctly compile the application, covering the overwhelming majority of standard Spring Boot usage patterns without requiring the developer to manually write these hints themselves.

*Follow-up: Why is it significant that this analysis happens at build time, examining the actual, concrete `ApplicationContext`, rather than attempting to statically analyze the raw, unexecuted source code for potential reflective usage?* Spring's AOT engine can actually build and inspect a real, fully-wired `ApplicationContext` during the build process (since Spring Boot applications are capable of standing up their context outside of just serving live traffic) — this gives it concrete, accurate information about exactly which beans exist, how they're actually wired, and what reflective access they genuinely need, rather than needing to speculatively guess at every theoretically possible reflective usage pattern purely from static source code analysis, which would be a much harder and less accurate problem to solve generically.

**4. Why does this chapter specifically identify serverless functions as a strong use case for native images?**
Many serverless platforms bill based on execution time and can scale a function down to zero instances during idle periods, meaning a "cold start" (spinning up a brand new instance to handle an incoming request after scaling to zero) happens frequently and its latency directly and visibly affects both cost and the requester's perceived response time; a native image's dramatically faster startup (milliseconds versus seconds) directly and substantially reduces this cold-start penalty, which is a first-class, frequently-recurring cost in a serverless deployment model in a way it typically isn't for a long-running, steadily-traffic service that rarely if ever restarts.

*Follow-up: Why is this same cold-start concern much less significant for the microservices architecture built throughout Part 7, assuming those services run as long-lived, continuously-running instances?* If a service's instances are provisioned once and run continuously for extended periods (hours, days) handling ongoing traffic — as the `replicas`-based deployment model from Chapter 35 typically implies for a long-running microservice — the one-time JVM startup and warm-up cost is incurred just once per instance's lifetime, and is amortized across a very large number of subsequently-handled requests, making it a comparatively insignificant fraction of that instance's total useful uptime, unlike a serverless function that might start, handle a single request, and then be torn down again shortly afterward, repeating that startup cost far more frequently relative to actual useful work performed.

**5. Why might rapid horizontal autoscaling (per Chapter 35's Kubernetes coverage) also benefit meaningfully from native images, even for a non-serverless, traditionally-deployed service?**
When a sudden traffic spike triggers Kubernetes' Horizontal Pod Autoscaler (mentioned in Chapter 35) to rapidly add new replicas, each new replica's ability to actually start handling traffic depends on how quickly it can start up and pass its readiness probe (Chapter 19/35) — a native image's dramatically faster startup means newly-scaled-out instances become available to handle the traffic spike far more quickly than JVM-based instances would, which can matter significantly during a genuinely sudden, sharp spike where the speed of scaling out directly determines how well the system handles the surge before those new instances are actually ready to help.

*Follow-up: Would this same benefit apply equally to a service that scales gradually and predictably, rather than experiencing sudden, sharp traffic spikes?* Less so — a service that scales gradually and predictably (allowing time for new instances to start and warm up well ahead of when the additional capacity is actually needed) doesn't depend as critically on extremely fast startup time, since there's already comfortable lead time for even a slower-starting JVM-based instance to become ready before it's genuinely needed; the native image startup-speed benefit is most valuable specifically for scenarios with sudden, unpredictable spikes where every second of startup delay directly translates into a period of insufficient capacity during the surge.

**6. What's a genuine operational cost of adopting native images that this chapter specifically flags, beyond just the longer build time?**
Debugging a native image is meaningfully different from debugging a standard JVM application — many familiar JVM diagnostic and profiling tools (certain profilers, some traditional `jstack`/`jmap`-style tooling built around JVM-specific internals) don't work identically, or at all, against a native, non-JVM executable, meaning a team adopting native images needs to also adopt different, native-image-specific diagnostic approaches and tooling, representing a real, ongoing operational cost beyond just the one-time build-configuration effort.

*Follow-up: How might this operational cost specifically affect a team's ability to respond to an incident, compared to a JVM-based deployment?* A team accustomed to specific, familiar JVM diagnostic workflows (attaching a profiler, taking a heap dump with `jmap`, examining thread state with `jstack`) during an incident investigation might find some or all of those exact tools unavailable or behaving differently against a native image, potentially slowing down incident diagnosis if the team hasn't separately built familiarity with the different diagnostic approaches and tooling native images require — this is a genuine, practical readiness gap a team should proactively address (through training and establishing native-image-specific diagnostic runbooks) before relying on native images for critical production services, rather than discovering the gap for the first time during an actual live incident.

**7. Why does this chapter caution that "not every third-party library is native-image-compatible," and what's the practical risk of not checking this before committing to native images?**
Libraries that perform their own dynamic reflection, class-path scanning, or bytecode generation outside of mechanisms Spring's AOT engine is specifically aware of and can generate hints for may not work correctly (or at all) when compiled into a native image — discovering this incompatibility late, after significant development effort has already gone into a project assuming native image deployment, could mean either a costly effort to find and configure the necessary additional hints manually, replacing the incompatible library with an alternative, or in the worst case, abandoning the native image approach entirely after having already invested significant effort assuming it would work.

*Follow-up: What's a practical way to reduce this risk early in a project's development, rather than discovering incompatibility issues late?* Attempting a native image build early in the project's development — ideally as part of the regular CI pipeline, building and even testing the native image on every change alongside the normal JAR build — surfaces any reflection gaps or library incompatibilities immediately as they're introduced, rather than allowing them to accumulate silently until a much larger, harder-to-diagnose set of issues is discovered all at once much later, right before an intended release or deployment.

**8. Why does the chapter frame native images as "not the default choice for most Spring Boot applications," given the impressive startup-time numbers shown?**
The dramatic startup and memory improvements come with real, non-trivial costs — significantly longer and more complex builds, potential library compatibility issues requiring extra configuration effort, a different and less mature diagnostic/debugging tooling ecosystem, and a lower ceiling for JIT-driven peak throughput optimization — for the large majority of typical, long-running microservices (the kind built throughout Part 7 of this series) where startup time is a one-time, amortized cost rather than a frequently-recurring one, these added costs generally aren't justified by benefits (fast cold starts, minimal footprint) the application doesn't actually need in that deployment context.

*Follow-up: Under what circumstance would you specifically recommend a team invest the effort to adopt native images for a service, despite these added costs?* Specifically when the deployment context makes startup time and memory footprint genuinely first-class, recurring concerns — a serverless function experiencing frequent cold starts, a system that needs to handle very sudden, sharp autoscaling events where fast instance startup meaningfully improves resilience during the spike, or an environment with strict, tightly-constrained memory budgets where the reduced memory footprint alone justifies the added build complexity — outside of these specific, concrete scenarios, the standard JAR-plus-JVM deployment model from Chapter 35 remains the more practical, lower-risk default choice.

**9. How does the reflection-hints configuration shown in this chapter (the JSON file) relate to what Spring's AOT engine automatically generates?**
Spring's AOT engine automatically generates the large majority of needed reflection hints, proxy configuration, and resource inclusion metadata by analyzing the actual, concrete `ApplicationContext` at build time — the manually-written JSON hint file shown in this chapter represents the smaller, remaining gap: reflective usage patterns the AOT engine's analysis doesn't automatically discover, typically because that reflection is happening inside a third-party library's own code in a way that isn't visible through analyzing the Spring application context itself.

*Follow-up: Why might a team need to add a manual hint for a specific class even if that class is a completely ordinary, standard Spring-managed `@Entity` or `@Component`?* If Spring's AOT engine's analysis is genuinely comprehensive for standard, ordinary Spring-managed beans (which the chapter states is the common case), a manual hint typically wouldn't actually be needed for such a class — the more realistic scenario requiring a manual hint would be a class that a *third-party library* accesses reflectively in a way Spring's own AOT analysis has no visibility into (the library operating independently of Spring's dependency injection and configuration mechanisms), which is exactly the gap this chapter identifies manual hints as being for, rather than ordinary, standard Spring-managed application classes needing hints under typical circumstances.

**10. Why is the build process for a native image described as taking "minutes, not seconds," and why is that trade-off generally acceptable?**
GraalVM's native image compiler performs comprehensive, whole-program static analysis across the entire application and all its dependencies to determine everything the compiled executable could possibly need at runtime — this is a fundamentally more thorough and computationally expensive process than a normal JAR build (which mostly just compiles source code and packages already-compiled dependencies together); this trade-off is generally acceptable because the build happens once per release/deployment (as part of a CI/CD pipeline, not something a developer waits on interactively during every single local code change), while the resulting startup-time benefit is realized on *every single instance start* for the life of that deployed version, a favorable trade-off when instances start frequently (serverless, rapid autoscaling) relative to how often a new build/release happens.

*Follow-up: Would this same build-time trade-off be favorable for a local development inner loop, where a developer wants to quickly restart the application after every small code change to test it?* No — for local, iterative development where a developer wants to make a small change and quickly see its effect, the JVM-based approach (with its much faster build/restart cycle, especially combined with the `spring-boot:run` fast-iteration approach from Chapter 3) is far more practical than repeatedly enduring a multi-minute native image build for every small change; native image builds are generally reserved for actual release/deployment artifacts rather than the everyday local development inner loop, where fast iteration matters far more than the runtime startup characteristics of the final deployed artifact.

**11. What's the relationship between native images (this chapter) and virtual threads (Chapter 37) — are they mutually exclusive, complementary, or unrelated optimizations?**
They're complementary and address genuinely different aspects of an application's runtime behavior — virtual threads (Chapter 37) improve how efficiently a running application handles high concurrent I/O-bound load once it's already up and running, while native images (this chapter) specifically improve how quickly an application actually starts up and how much memory its baseline footprint requires; a Spring Boot application can adopt both together (a native image application can use virtual threads for its concurrency model), each addressing its own specific, independent performance dimension without conflicting with the other.

*Follow-up: For the serverless use case this chapter specifically highlights, would virtual threads' benefit be as significant as it would be for a long-running, high-concurrency service?* Likely less significant in a typical serverless context — many serverless deployment models handle requests with relatively limited or even single-request-at-a-time concurrency per instance (since the platform itself often handles scaling by creating additional instances rather than one instance handling many concurrent requests simultaneously), meaning the specific "many concurrent I/O-bound operations competing for a limited platform thread pool" problem virtual threads solve may simply not be as prominent a concern in that particular deployment model — native image's fast-startup benefit remains highly relevant for serverless regardless, but virtual threads' concurrency benefit is more specifically tied to a different deployment characteristic (high, sustained concurrent load on a single, long-running instance) that doesn't always describe a typical serverless workload.

**12. Why might a team choose to maintain both a standard JAR-based build and a native-image build of the same application, rather than committing exclusively to one or the other?**
Different deployment contexts within the same organization might have genuinely different needs — perhaps the same core application logic is deployed as a long-running microservice in one context (where the standard JVM/JAR approach, per Chapter 35, remains the more practical, lower-risk default) and also deployed as a serverless function or CLI tool in another context (where native image's fast-startup benefit is specifically valuable) — maintaining both build variants lets the same codebase serve both deployment models appropriately, rather than forcing one deployment context to accept a trade-off (slow serverless cold starts, or unnecessary native-image build complexity for a long-running service) that doesn't actually fit its specific needs.

*Follow-up: What would be the added maintenance cost of supporting both build variants, and how might a team decide whether it's worth that cost?* Maintaining both means ensuring ongoing compatibility with native image constraints (avoiding or properly hinting any reflection-heavy patterns that would otherwise be a non-issue for the JAR-only build) as a continuous discipline across all future development, plus maintaining two separate build/CI pipeline configurations and potentially two sets of deployment-specific testing and validation — a team would reasonably weigh this ongoing cost against how genuinely valuable having both deployment options actually is for their specific, concrete use cases, following the same evidence-based, driver-justified decision-making theme established throughout this series (echoing Chapter 23's guidance on justifying architectural decisions with genuine, present needs rather than speculative future flexibility).

**13. How does the concept of "ahead-of-time" compilation in this chapter connect to or differ from the "AOT" processing Spring itself performs, as distinct from GraalVM's own AOT compilation?**
These are two related but distinct concepts operating at different levels: Spring's own AOT engine performs build-time *analysis and configuration generation* — inspecting the application context and producing the reflection hints, proxy definitions, and other metadata GraalVM needs — while GraalVM's native image compiler performs the actual ahead-of-time *compilation of bytecode to native machine code*, using (among other inputs) the metadata Spring's AOT engine already generated; Spring's AOT processing is a necessary preparatory step that feeds into, but is distinct from, GraalVM's own separate compilation process.

*Follow-up: Could Spring's AOT engine's generated hints and configuration be useful even for an application that isn't ultimately compiled with GraalVule at all, staying on the standard JVM?* Spring's AOT processing was specifically introduced to support native image compilation as its primary motivating use case, so its most direct, tangible value is realized specifically when the application is subsequently compiled with GraalVM — for an application remaining on the standard JVM (not pursuing native image compilation at all), Spring's AOT-generated artifacts generally aren't a necessary or particularly beneficial part of that application's runtime behavior, though Spring's broader AOT infrastructure has also been leveraged for some JVM-specific startup optimizations in certain contexts, a more specialized and secondary benefit compared to its primary native-image-enabling purpose.

**14. Why does this chapter explicitly recommend testing native image builds "early and often" as a specific best practice, rather than treating it as a final pre-release step?**
Because native image compatibility issues (missing reflection hints, incompatible third-party libraries) tend to surface specifically in relation to whatever code and dependencies exist in the application *at the time of the build* — as a codebase evolves with new features, new dependencies, and new reflective usage patterns being introduced incrementally over time, incompatibilities can be introduced incrementally as well; testing the native build regularly (ideally in CI, on every change) catches each new incompatibility close to when it was actually introduced, when it's fresh in a developer's mind and typically much easier and faster to diagnose and fix, rather than allowing many such issues to accumulate silently until a single, much larger, and harder-to-untangle problem is discovered right before an intended release.

*Follow-up: How does this recommendation reflect a broader theme this series has emphasized regarding catching problems early, echoing similar advice from earlier chapters?* This mirrors the same underlying principle behind Chapter 17/18's emphasis on writing tests throughout development rather than only right before release, and Chapter 12's emphasis on small, frequent, reviewable database migrations rather than large, infrequent ones — catching a specific, isolated problem close to when it was introduced is consistently easier, faster, and lower-risk to diagnose and fix than allowing problems to silently accumulate and only be discovered much later, in a much larger, more tangled, and higher-pressure batch; this chapter's native-image-testing advice is simply this same general engineering principle applied to a new, specific context.

**15. Summarize the trade-off native images represent, and how a team should decide whether to adopt them for a specific service.**
Native images trade a significantly heavier, slower build process and some added operational/debugging complexity for a dramatic (20–50x) reduction in startup time and a meaningfully smaller memory footprint at runtime, with a slightly lower ceiling for JIT-driven peak-throughput optimization compared to a fully warmed-up JVM. This trade-off is clearly worthwhile specifically for deployment contexts where startup time and memory footprint are genuine, frequently-recurring, first-class concerns — serverless functions experiencing regular cold starts, or services needing to scale out very rapidly in response to sudden traffic spikes — and is generally not worth the added complexity for the more common case of a long-running, steadily-traffic microservice where the one-time JVM startup cost is an insignificant fraction of that instance's total useful operational lifetime.

*Follow-up: Looking back at the capstone system design from Chapter 34, would you recommend native images for any of its four services (order-service, inventory-service, payment-service, notification-service), and why or why not?* Based on that design's description, none of the four services were characterized as needing rapid, frequent scale-to-zero or serverless-style deployment — they're described as long-running, independently-scaled services (via Kubernetes `replicas`, per Chapter 35) handling ongoing, continuous traffic, which is exactly the profile this chapter identifies as not particularly benefiting from native images' specific trade-offs; unless a future requirement specifically introduced a serverless or extremely bursty, scale-to-zero deployment need for one of these services, the standard JAR-plus-JVM approach (optionally combined with virtual threads from Chapter 37 for concurrency efficiency) would remain the more practical, lower-risk choice for this particular system as designed.
