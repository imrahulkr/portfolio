This is the first of four consolidated interview-prep chapters. Rather than repeating the 120+ questions already embedded in Chapters 1–8, this chapter is organized for rapid review and synthesis — grouped by topic, answered concisely, with cross-references back to the full chapter where deeper detail lives. Use it to drill recall the week before an interview, not as your first exposure to any of these topics.

## Spring Core & IoC

**1. What's the one-sentence difference between IoC and DI?**
IoC is the principle (objects don't create their own dependencies); DI is the technique Spring uses to implement it (constructor/setter/field injection). *(Chapter 2)*

**2. Why is constructor injection preferred?**
Immutable, explicit, testable without a container, and fails fast at startup if a dependency is missing. *(Chapter 2)*

**3. Default bean scope, and when would you change it?**
`singleton`. Change to `prototype` only when a bean genuinely needs fresh, isolated mutable state per use — rare, since most beans should be stateless. *(Chapter 2)*

**4. `@Component` vs `@Bean` — when do you reach for each?**
`@Component` for classes you own, discovered via component scanning. `@Bean` for explicit construction, especially third-party classes you can't annotate. *(Chapter 2)*

## Auto-Configuration

**5. In one sentence, how does auto-configuration decide what to activate?**
It evaluates conditional annotations (`@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`) against the classpath, existing beans, and properties. *(Chapter 4)*

**6. How do you find out why something wasn't auto-configured?**
Run with `--debug` and read the auto-configuration report's negative matches. *(Chapter 4)*

**7. How does defining your own `DataSource` bean "override" the default?**
It doesn't override anything explicitly — the auto-configured bean is guarded by `@ConditionalOnMissingBean`, so it simply doesn't activate once yours exists. *(Chapter 4)*

## Configuration & Profiles

**8. Rank these by precedence: `application.yml`, command-line args, environment variables, `application-{profile}.yml`.**
Command-line args > environment variables > `application-{profile}.yml` > `application.yml`. *(Chapter 5)*

**9. `@Value` vs `@ConfigurationProperties` — when does the choice actually matter?**
Once you have more than 2–3 related properties — `@ConfigurationProperties` groups them into one validated, type-safe object; `@Value` scatters string-keyed lookups. *(Chapter 5)*

**10. Why use a Java record for `@ConfigurationProperties`?**
Immutability plus native Spring Boot constructor-binding support, with no boilerplate getters/setters. *(Chapter 5)*

## REST APIs & Validation

**11. `@RestController` vs `@Controller`?**
`@RestController` = `@Controller` + `@ResponseBody` on every method — return values are serialized directly instead of resolved as a view. *(Chapter 6)*

**12. What status code should a successful `POST` that creates a resource return, and what header should accompany it?**
`201 Created`, with a `Location` header pointing at the new resource. *(Chapter 6)*

**13. What triggers `MethodArgumentNotValidException`, and how do you customize its response?**
A failed `@Valid` check on a controller argument; customize via a `@ExceptionHandler(MethodArgumentNotValidException.class)` inside a `@RestControllerAdvice`. *(Chapter 7)*

**14. Why should a `@RestController` never return a JPA entity directly?**
Risk of lazy-loading exceptions outside a transaction, accidental exposure of sensitive fields, and coupling the public API contract to the database schema. *(Chapters 6, 9)*

**15. What is `ProblemDetail`, and why was it introduced?**
A built-in, RFC 7807–compliant standardized error response shape (Spring 6+), replacing the need to hand-roll a bespoke error format per project. *(Chapter 7)*

## Spring MVC Internals

**16. What is `DispatcherServlet`, in one sentence?**
The front controller that receives every request, delegates to `HandlerMapping` to find the matching controller, and uses `HttpMessageConverter`s to build the response. *(Chapter 8)*

**17. Filter vs. `HandlerInterceptor` — what's the deciding factor?**
Whether the logic needs to run regardless of routing (Filter — auth, CORS) or needs access to the matched handler method's metadata (Interceptor). *(Chapter 8)*

**18. Why doesn't `@RestControllerAdvice` catch an exception thrown inside a `Filter`?**
Filters run entirely outside `DispatcherServlet`'s own processing boundary, which is the only scope `@ExceptionHandler` methods cover. *(Chapters 7, 8)*

## Rapid-fire recap

- Bean lifecycle order: instantiate → inject dependencies → `@PostConstruct` → ready → `@PreDestroy` → destroyed.
- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`.
- A fat/executable JAR contains your code + every dependency + the embedded server.
- `@PathVariable` = URL segment; `@RequestParam` = query string; `@RequestBody` = deserialized payload.
- `@Modifying` is required on any non-`SELECT` `@Query`.
- Spring Security's filter chain runs entirely before `DispatcherServlet`.

## Cross-topic synthesis question

**19. Trace a single `POST /api/orders` request end to end, naming every mechanism involved from Chapters 1–8.**
`DispatcherServlet` receives the request → `HandlerMapping` resolves it to `OrderController.create()` → `@RequestBody` is deserialized via a Jackson `HttpMessageConverter` → `@Valid` triggers Bean Validation; a failure short-circuits to a `@RestControllerAdvice` handler producing a `ProblemDetail` → on success, the constructor-injected `OrderService` (a singleton bean, resolved via the `ApplicationContext` built at startup by auto-configuration) executes business logic → the controller returns a `ResponseEntity` with `201 Created` and a `Location` header.

**20. If that same endpoint suddenly starts returning `500` for every request after a deployment, what's your triage order?**
Check recent config changes (Chapter 5) → run with `--debug` to rule out an auto-configuration regression (Chapter 4) → check the `@RestControllerAdvice`'s catch-all handler's logs for the actual underlying exception (Chapter 7) → confirm the deployed JAR's dependency layer didn't silently change (Chapter 35, if containerized).
