## Spring Data JPA

**1. JPA vs. Hibernate vs. Spring Data JPA — one line each?**
JPA: the specification. Hibernate: the implementation that turns it into SQL. Spring Data JPA: generates repository implementations so you never call `EntityManager` directly. *(Chapter 9)*

**2. Why is `ddl-auto: update` dangerous in production, and what replaces it?**
It lets Hibernate silently alter your schema based on entity changes, with no review step. Flyway/Liquibase migrations, with `ddl-auto: validate`, is the safe replacement. *(Chapters 9, 12)*

**3. Why always `@Enumerated(EnumType.STRING)`?**
The default, `ORDINAL`, stores an enum's position as an integer — reordering constants later silently corrupts existing data with no error. *(Chapter 9)*

**4. Derived query methods vs. `@Query` — where's the line?**
Once a query needs more than 2–3 conditions or a join/aggregation the naming convention can't express, switch to `@Query`. *(Chapters 9, 10)*

**5. What's the N+1 problem, and the two standard fixes?**
Fetching N parent rows then triggering N additional queries for a lazy association. Fix with `@EntityGraph` or an explicit `JOIN FETCH`. *(Chapter 10)*

**6. Interface projection vs. DTO projection?**
Interface: simpler, Spring generates the proxy. DTO (via a JPQL constructor expression): more explicit control over exactly which columns are selected. *(Chapter 10)*

**7. What's the point of a `Specification`?**
Building dynamic, optional, composable `WHERE` clauses at runtime — for search endpoints where any subset of filters might be present. *(Chapter 10)*

## Transactions

**8. Does `@Transactional` roll back on a checked exception by default?**
No — only unchecked exceptions, unless `rollbackFor` is explicitly set. This is the single most common transaction bug. *(Chapter 11)*

**9. Why does calling a `@Transactional` method from within the same class not work?**
Self-invocation bypasses the AOP proxy that implements the transactional behavior — the call never reaches the proxy. *(Chapter 11)*

**10. `REQUIRED` vs. `REQUIRES_NEW` — give the canonical use case for the second.**
`REQUIRED` joins an existing transaction. `REQUIRES_NEW` always starts an independent one — classic use case: audit logging that must persist even if the surrounding transaction rolls back. *(Chapter 11)*

## Migrations & NoSQL

**11. What happens if you edit an already-applied Flyway migration file?**
Flyway detects the checksum mismatch on next startup and refuses to proceed — write a new migration instead. *(Chapter 12)*

**12. When does MongoDB genuinely fit better than a relational database?**
Naturally document-shaped, self-contained data with few real cross-entity joins, and genuine need for schema flexibility. *(Chapter 13)*

**13. Embedding vs. referencing in MongoDB — the deciding factor?**
Embed data always read together with its parent; reference data that's independently queried, large, or shared across many parents. *(Chapter 13)*

## Spring Security

**14. Authentication vs. authorization — one line each?**
Authentication: who are you. Authorization: what are you allowed to do. Sequential, and distinct. *(Chapter 14)*

**15. Why does adding `spring-boot-starter-security` secure every endpoint immediately?**
"Secure by default" — forces explicit `permitAll()` decisions rather than risking an accidentally unsecured endpoint. *(Chapter 14)*

**16. 401 vs. 403?**
401: no valid authentication at all. 403: authenticated, but not authorized for this specific action. *(Chapter 14)*

**17. Why is a JWT's payload not confidential, only tamper-evident?**
It's Base64-encoded, not encrypted — readable by anyone holding the token. The signature only proves it hasn't been altered. *(Chapter 15)*

**18. When do you need an OAuth2/OIDC provider instead of hand-rolled JWT?**
"Log in with X" delegation, SSO across multiple apps, or standardized tokens other systems need to validate without custom code. *(Chapter 15)*

**19. CORS vs. CSRF — what does each actually protect against, and who enforces each?**
CORS (browser-enforced): stops a malicious site's JS from reading your API's responses cross-origin. CSRF (server-enforced token check): stops a malicious site from triggering state-changing actions using a victim's session cookie. *(Chapter 16)*

**20. Why is disabling CSRF correct for a stateless, JWT-authenticated API?**
CSRF exploits automatic cookie attachment; a bearer-token API has no session cookie for an attacker to exploit that way. *(Chapters 15, 16)*

**21. `@PreAuthorize` vs `@PostAuthorize`?**
`@PreAuthorize` checks before the method runs (arguments only). `@PostAuthorize` checks after (has access to the return value), at the cost of the method already having executed. *(Chapter 16)*

## Testing

**22. Why does a plain Mockito test need no Spring context at all?**
Constructor injection means the class under test can be instantiated directly with `new`, passing in mocks — no container required. *(Chapter 17)*

**23. `@WebMvcTest` vs. `@SpringBootTest` — the deciding factor?**
`@WebMvcTest` loads only the web layer (fast, mocked service dependencies). `@SpringBootTest` loads everything (slow) — reserve it for genuine cross-bean wiring verification. *(Chapter 17)*

**24. What does Testcontainers solve that a shared test database doesn't?**
Real, disposable, per-test-run infrastructure matching production's actual database engine — no shared state, no version drift. *(Chapter 18)*

**25. Why combine `@DataJpaTest` with Testcontainers rather than its default H2?**
H2's SQL dialect can differ subtly from production's real database — testing against the same engine catches issues H2 would miss. *(Chapter 18)*

## Cross-topic synthesis question

**26. A code review flags: a service method does `@Transactional` + `@Cacheable`, calls itself internally from another method in the same class, and the cached value sometimes goes stale after an update elsewhere. Diagnose all the issues.**
(1) Self-invocation between methods in the same class bypasses *both* the `@Transactional` and `@Cacheable` AOP proxies — neither annotation takes effect on that internal call (Chapters 11, 20). (2) "Goes stale after an update elsewhere" suggests a missing `@CacheEvict`/`@CachePut` on the update path — every write path touching cached data needs a corresponding cache update (Chapter 20). (3) Fix: extract the internally-called method into a separate bean, and audit every write path for cache invalidation, backed by a sensible TTL as a safety net regardless.
