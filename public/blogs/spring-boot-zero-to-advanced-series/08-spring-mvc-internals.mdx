You've written controllers and handled errors globally — this chapter closes Part 2 by explaining the actual request pipeline those controllers sit inside, and the two mechanisms (filters and interceptors) you'll reach for whenever behavior needs to run *around* every request rather than inside one specific handler.

## The `DispatcherServlet`

Every request into a Spring MVC application passes through a single front controller: `DispatcherServlet`. Spring Boot auto-configures and registers it for you (`DispatcherServletAutoConfiguration`, gated `@ConditionalOnWebApplication`, per Chapter 4) — this is why nothing in Chapters 6–7 required any manual servlet registration.

```
                 HTTP Request
                       │
                       ▼
              ┌──────────────────┐
              │  DispatcherServlet │
              └─────────┬─────────┘
                         │  1. Ask HandlerMapping which
                         │     controller method matches
                         ▼
              ┌──────────────────┐
              │   HandlerMapping   │
              └─────────┬─────────┘
                         │  2. Invoke the matched
                         │     controller method
                         ▼
              ┌──────────────────┐
              │   Your Controller  │
              └─────────┬─────────┘
                         │  3. Convert return value
                         │     (e.g. to JSON via Jackson)
                         ▼
              ┌──────────────────┐
              │ HttpMessageConverter│
              └─────────┬─────────┘
                         │
                         ▼
                 HTTP Response
```

`HandlerMapping` is what matches an incoming URL and HTTP method to the correct `@RequestMapping`-annotated method — this is the component doing the work when you write `@GetMapping("/{id}")`. `HttpMessageConverter` implementations (Jackson's, for JSON) handle converting between the raw HTTP body and Java objects for both `@RequestBody` and `@ResponseBody`/`@RestController` return values.

## Filters vs interceptors

Both let you run code before/after a request reaches your controller, but they operate at different layers and are used for different kinds of concerns.

| | Servlet `Filter` | Spring `HandlerInterceptor` |
|---|---|---|
| Layer | Servlet API (below Spring MVC) | Spring MVC (has access to the matched handler) |
| Sees Spring beans? | Only if registered as a Spring bean itself | Yes — it's a Spring MVC component |
| Typical use | Authentication, CORS, request/response logging at the raw HTTP level | Logging tied to a specific controller, authorization checks needing handler metadata |
| Runs relative to `DispatcherServlet` | Before and after `DispatcherServlet` entirely | Inside `DispatcherServlet`'s processing, around the handler call |

```java
@Component
class RequestLoggingFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                     FilterChain chain) throws ServletException, IOException {
        long start = System.currentTimeMillis();
        chain.doFilter(request, response);   // pass control to the next filter / DispatcherServlet
        long duration = System.currentTimeMillis() - start;
        log.info("{} {} - {}ms", request.getMethod(), request.getRequestURI(), duration);
    }
}
```

```java
@Component
class AuditInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // handler here is a HandlerMethod — you can inspect the matched controller method,
        // read custom annotations on it, etc. — filters can't do this.
        return true;   // false would stop the request from reaching the controller
    }
}

@Configuration
class WebConfig implements WebMvcConfigurer {
    private final AuditInterceptor auditInterceptor;

    WebConfig(AuditInterceptor auditInterceptor) {
        this.auditInterceptor = auditInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(auditInterceptor).addPathPatterns("/api/**");
    }
}
```

The key practical distinction: an interceptor's `preHandle` receives the actual matched `HandlerMethod`, so it can inspect the controller method itself — its annotations, its declaring class — which a raw servlet `Filter` has no visibility into at all. This is exactly the mechanism Spring Security's method-level authorization checks build on (Chapter 16).

## Where this fits with what you already know

Spring Security (Part 4) is implemented as a chain of servlet `Filter`s registered ahead of `DispatcherServlet` — this is *why* authentication happens before your controller code ever runs, and why a security filter can reject a request (returning `401`/`403`) without Spring MVC's routing machinery being involved at all. The `@RestControllerAdvice` from Chapter 7, by contrast, only handles exceptions thrown *inside* the `DispatcherServlet`'s processing (controllers, interceptors) — it never sees an exception thrown from a filter, since filters run entirely outside that boundary.

## Best practices & gotchas

- **Use a `Filter` for concerns that need to run regardless of whether a matching controller exists** — CORS handling, raw request/response logging, and authentication are the canonical examples, since they should apply (or reject the request) before routing even happens.
- **Use a `HandlerInterceptor` for concerns that need to know *which* controller method was matched** — reading a custom annotation on the handler, or logic that's meaningful only for specific endpoints.
- **Order matters when you have multiple filters.** Use `@Order` (or implement `Ordered`) to control sequencing explicitly — Spring Security's filter chain, for instance, depends heavily on internal filter ordering to work correctly.
- **An exception thrown inside a `Filter` won't be caught by `@RestControllerAdvice`.** It happens outside `DispatcherServlet`'s try/catch boundary entirely; filters need their own error handling if they can fail.
- **Don't put business logic in either mechanism.** Both are for cross-cutting, request-pipeline concerns — routing, security, logging, request timing — not for anything specific to one feature's business rules.

## Quick reference

| Component | Role |
|---|---|
| `DispatcherServlet` | Front controller — receives every request, delegates to `HandlerMapping` and back to a `HttpMessageConverter` |
| `HandlerMapping` | Matches a request to the correct `@RequestMapping` method |
| `HttpMessageConverter` | Converts between raw HTTP body and Java objects (Jackson for JSON) |
| `Filter` | Servlet-level, runs before/after `DispatcherServlet` entirely, no visibility into the matched handler |
| `HandlerInterceptor` | Spring MVC-level, runs around the handler call, has access to the matched `HandlerMethod` |

## Interview Questions

**1. What is `DispatcherServlet`, and what role does it play in Spring MVC?**
It's the front controller for every Spring MVC application — a single servlet that receives all incoming HTTP requests, delegates to a `HandlerMapping` to find the matching controller method, invokes it, and uses `HttpMessageConverter`s to convert the return value into the HTTP response body. Spring Boot auto-configures and registers it automatically for any application with `spring-boot-starter-web` on the classpath.

**2. What is `HandlerMapping`, and what does it do?**
It's the component responsible for matching an incoming request's URL and HTTP method against the registered `@RequestMapping` (and shorthand `@GetMapping`/`@PostMapping`/etc.) methods across all controllers, determining which specific method should handle a given request.

**3. What is an `HttpMessageConverter`, and give an example.**
It converts between the raw HTTP request/response body and Java objects. Jackson's `MappingJackson2HttpMessageConverter` is the default for JSON — it deserializes an incoming JSON body into a `@RequestBody` parameter's type, and serializes a controller's return value (or `ResponseEntity` body) back into JSON for the response.

**4. What's the fundamental difference between a servlet `Filter` and a Spring `HandlerInterceptor`?**
A `Filter` operates at the raw Servlet API layer, running before and after `DispatcherServlet` entirely, with no knowledge of Spring MVC's routing or which controller method will handle the request. A `HandlerInterceptor` operates inside `DispatcherServlet`'s own processing and has access to the actual matched `HandlerMethod`, letting it inspect the specific controller method and its annotations.

**5. Give a concrete example of when you'd choose a `Filter` over an interceptor.**
CORS handling and authentication are classic filter use cases — both need to potentially reject a request (with a `403`, or handling a CORS preflight `OPTIONS` request) before any routing to a specific controller has even happened, which is exactly the point in the pipeline where filters run and interceptors don't yet apply.

**6. Give a concrete example of when you'd choose a `HandlerInterceptor` over a filter.**
Reading a custom annotation placed on a specific controller method (e.g., a hypothetical `@RequiresAudit` annotation) to conditionally log or authorize that specific endpoint — this requires access to the matched `HandlerMethod`'s metadata, which only an interceptor's `preHandle` provides.

**7. What does returning `false` from `HandlerInterceptor.preHandle()` do?**
It stops the request from proceeding any further — the target controller method is never invoked, and none of the remaining interceptors' `preHandle` methods run either. This is commonly used for authorization checks that should short-circuit the request with an error response before any business logic executes.

**8. Why doesn't `@RestControllerAdvice` catch exceptions thrown from a `Filter`?**
`@RestControllerAdvice`'s `@ExceptionHandler` methods only intercept exceptions thrown during `DispatcherServlet`'s own processing — controller method execution and interceptor callbacks. A `Filter` runs entirely outside that boundary (before `DispatcherServlet` is even invoked, or after it returns), so an exception thrown there needs its own explicit handling within the filter chain itself.

**9. How is Spring Security implemented in relation to `DispatcherServlet`?**
As a chain of servlet `Filter`s registered ahead of `DispatcherServlet` in the servlet container's filter chain. This is precisely why authentication and authorization decisions happen — and can reject a request with `401`/`403` — before Spring MVC's routing and your controller code ever run at all.

**10. How do you register a custom `Filter` in a Spring Boot application?**
Either register it as a `@Component` implementing `Filter` (or extending `OncePerRequestFilter`) directly, which Spring Boot auto-registers into the filter chain, or explicitly declare a `FilterRegistrationBean` bean for finer control over ordering and URL patterns:
```java
@Bean
FilterRegistrationBean<RequestLoggingFilter> loggingFilter() {
    FilterRegistrationBean<RequestLoggingFilter> reg = new FilterRegistrationBean<>(new RequestLoggingFilter());
    reg.addUrlPatterns("/api/*");
    reg.setOrder(1);
    return reg;
}
```

**11. What is `OncePerRequestFilter`, and why is it preferred over implementing `Filter` directly?**
`OncePerRequestFilter` is a Spring-provided base class that guarantees its filtering logic executes exactly once per request, even in servlet environments where a request might otherwise be internally forwarded/included multiple times (which could cause a plain `Filter` implementation to run more than once for the same logical request). It's the standard base class for custom filters in Spring applications for this reason.

**12. How do you register a `HandlerInterceptor`?**
Implement `WebMvcConfigurer` in a `@Configuration` class and override `addInterceptors`, registering the interceptor bean along with the URL patterns it should apply to:
```java
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(auditInterceptor).addPathPatterns("/api/**");
}
```

**13. What are the three lifecycle callback methods on `HandlerInterceptor`, and when does each run?**
`preHandle` runs before the controller method is invoked (and can short-circuit the request by returning `false`); `postHandle` runs after the controller method completes but before the view is rendered (rarely relevant for pure REST APIs, since there's no view to render); `afterCompletion` runs after the complete request has finished, including after the response has been sent — useful for cleanup logic that should run regardless of whether the request succeeded or failed.

**14. If you needed to add a correlation/trace ID to every incoming request and ensure it's available for the duration of that request's processing, would you use a filter or an interceptor?**
A `Filter` is the more natural fit, since a correlation ID typically needs to be established as early as possible — before routing, before any interceptor runs, and ideally available even to other filters (like a logging filter) further down the chain. It's commonly stored in a `ThreadLocal` (or, in a virtual-threads/reactive context, propagated via context mechanisms) for the duration of request processing, then cleared in a `finally` block once the response has been sent.

**15. Why is understanding the `DispatcherServlet` pipeline valuable even though Spring Boot auto-configures all of it for you?**
Because cross-cutting behavior — security, logging, request tracing, CORS — has to be inserted at the correct point in this pipeline to work correctly. Without understanding where filters, interceptors, and the `DispatcherServlet` itself sit relative to each other, it's easy to add logic in the wrong place (e.g., expecting a filter to see the matched controller method's annotations, or expecting `@RestControllerAdvice` to catch a filter's exception) and be confused when it silently doesn't behave as expected.
